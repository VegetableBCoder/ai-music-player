# 1. 开工前还缺什么

## 1.1 必须先做的技术验证（风险消解）

| # | 风险 | 为什么危险 | 验证方式 | 不通过的退路 |
| --- | --- | --- | --- | --- |
| V1 | **KSP 无法挂上 AGP 9 的内置 Kotlin** | Room 的注解处理全靠 KSP。AGP 9 改变了插件应用方式（`org.jetbrains.kotlin.android` 已废弃），KSP 是否仍能正常注册编译器插件**从未验证**。若不通，整个 `:core:data` 无法落地 | 临时在 `:app` 加 `ksp` 插件 + 一个 `@Entity`/`@Database`，跑 `assembleDebug` | ① 用 AGP 9 的 `android.builtInKotlin=false` 退回旧 Kotlin 插件模式；② 暂时手写 SQL + 自管 schema（代价大，尽量不用） |
| V2 | **Hilt 无法挂上 AGP 9** | Hilt 的 Gradle 插件依赖 KGP 集成；新 DSL + 内置 Kotlin 下行为未知 | 加 `hilt` 插件 + `@HiltAndroidApp`，跑构建 | ① 退回 `android.builtInKotlin=false`；② 用 KSP 版 Hilt（`hilt-compiler` 已走 KSP）；③ 最坏用纯手写 DI 容器（会偏离文档 10 §5.4） |
| V3 | **测试依赖版本未经验证** | 版本目录里**没有** JUnit / Turbine / MockK / kotlinx-coroutines-test / Robolectric / androidx.test。文档 11 §8 的测试策略全压在这些上面 | 逐个查 Google Maven / Maven Central 确认存在，并跑通一个真实测试 | 换等价库（如 Turbine 换手写 Flow 断言） |
| V4 | **Room 运行期配置**未验证 | `exportSchema` 目录、`foreign_keys=ON`、6 个 TypeConverter、事务行为——文档 03 依赖这些才能保证 I1–I12 | 写出 13 张表后跑 Room 测试（§1.2 的 T1） | 按 03 §9 逐条定位 |
| V5 | **Compose 编译器插件**是否覆盖全部模块 | 仅在 `:app` 验证过；`core:ui`、`feature:*` 都要 Compose | 铺开模块后构建即可覆盖 | — |

> **V1/V2 已于 Phase 0.2/0.3 验证通过**（结论见 §0.2）—— 数据层与 DI 方案可以照文档做，不需要退路方案。
> 剩余待验证：**V3 测试依赖版本**（Phase 0.4）、**V4 Room 运行期配置**（随 Phase 2 的不变量测试一起）、**V5 多模块 Compose**（Phase 0.5 铺开模块时自然覆盖）。

# 2. 开发顺序

**原则**：按依赖方向自底向上（`core` → `feature`），因为底层契约（`02 §5`）一旦实现错，上层全部返工。
每阶段必须**同时交付实现 + 测试**，并通过该阶段验收才进入下一阶段。

## Phase 0 — 风险消解 + 结构落地【当前】

| 步骤 | 内容 | 产出 / 验收 |
| --- | --- | --- |
| 0.1 | 装到真机跑起来 | `./gradlew :app:installDebug`，真机看到占位页 —— 打通「构建→安装→运行」全链路 |
| 0.2 | 验证 V1（KSP + Room） | 临时实体能被 KSP 处理，构建通过；结论记入 `01 §2.2` |
| 0.3 | 验证 V2（Hilt） | `@HiltAndroidApp` 构建通过 |
| 0.4 | 确认 V3 测试依赖版本 | 版本目录补齐；跑通 1 个单测 + 1 个 Room 测试 |
| 0.5 | 建 10 个模块 + 依赖守卫 | `./gradlew projects` 列出 11 模块；写一个 `checkModuleDependencies` 脚本/任务，**故意加一条反向依赖能被拦住** |
| 0.6 | 定夺 S3（`core:test`）、提交 E1 | 文档 02/11 口径一致 |

**验收**：11 模块构建通过 + 三个验证各有实证 + 反向依赖守卫生效。

## Phase 1 — `:core:common` + 错误模型

- 内容：`Result`/`AppError` sealed 层次（文档 11 §3.1）、`failureKind` 映射（11 §3.2）、`Dispatchers`、`Logger`（11 §3.5）、时间与文本规范化（`artists_key` 用的 `\u001F` 拼接、路径规范化）。
- 依据：`11 §3`、`02 §8`。
- **验收**：错误模型单测；`AppError` 覆盖 `02 §8` 全部 `FailureKind`；文案映射表（11 §5.1）逐条有测试。

## Phase 2 — 数据层 `:core:data` + `:core:storage`

- 内容：13 张表 Entity + TypeConverter（03 §2.2/§2.3）；各表 DAO（03 §3）；6 个关键事务（03 §4.1–4.6）；Repository 实现要点（03 §5）；DataStore（03 §6）；敏感数据加密（03 §7，`EncryptedSharedPreferences`）。
- **验收（硬性）**：**不变量 I1–I12 逐条有对应 Room 测试并通过**（03 §9 + 11 §8.2）。这是全项目的正确性地基。

## Phase 3 — 文件扫描（`04`）

- 内容：`FileStorageSource`、`MmrMetadataReader`、`.lrc` 索引、差异比对、`ScanOrchestrator`（扫描会话状态机 02 §6.2）。
- 验收：`04 §8` 测试要点；权限门禁与降级（10 §4.2/§4.3）；空状态对齐 `05 §1`。

## Phase 4 — 分析 + LLM 归一化（`05`）

- 内容：`:core:llm`（`DirectProvider`、`PromptBuilder`、`NormalizeParser`、`RetryingLlmNormalizer`、`CachingLlmNormalizer`、`llm_cache`）、`AnalysisOrchestrator`、`entityKey` 计算。
- 验收：`05 §8` 测试要点；**全部用假 provider**（E3）；429 退避、缓存命中、幂等（I4）各有测试。

## Phase 5 — 歌曲库与标签（`06`）

- 内容：`SongListItem` 等投影装配（防 N+1）、四维浏览、排序/筛选 SQL 映射、搜索、歌曲详情、`DeletionService` 三操作、标签 CRUD 与删除保护（I12）、封面懒加载。
- 验收：`06 §8`；列表装配有性能测试（防 N+1 回归）。

## Phase 6 — 播放器（`07`）

- 内容：Media3 集成（`ExoPlayer` + `MediaSessionService`）、`QueueEngine`（内存队列 ↔ `queue_item` 同步）、**三种播放模式**（列表循环 / 单曲循环 / 随机）、会话统计（进度 85%/15%）、状态持久化与**冷启动恢复但不自动播放**、文件失效处理。
- 验收：`07 §8`；真机验证后台播放、通知栏、锁屏、耳机拔出、音频焦点抢占/恢复。

## Phase 7 — 歌词（`08`）

- 内容：三级匹配算法、冲突处理、编码探测（UTF-8 BOM / GBK）、LRC 解析器、同步展示、删除关联。
- 验收：`08 §8`；用**真实 GBK/UTF-8 歌词文件**做夹具。

## Phase 8 — 界面层（`09`）

- 内容：导航图、统一交互三件套、mini 播放条 + 底部导航、列表通用能力（多选/排序/⋯面板）、空状态映射、可访问性。
- 验收：`09 §8` Compose UI Test；空状态映射表逐条。

## Phase 9 — 系统集成（`10`）+ 可观测性（`11`）

- 内容：Manifest 完整声明、启动序列、权限引导、通知渠道、WorkManager、前台服务、Hilt DI 模块划分、诊断导出。
- 验收：`10 §8`；`11 §8.4` 真机手工验收清单全过。

# 3. 每阶段的完成定义（DoD）

一个阶段算"完成"，必须同时满足：

1. 实现按文档对应章节落地，**契约签名与 `02 §5` 逐字一致**（不得自创命名，见 `02 §3.2` / `§11`）。
2. 该文档 §8「测试要点」的项目有对应测试且通过。
3. `./gradlew assembleDebug` 与 `./gradlew test` 全绿。
4. 涉及数据库的，`I1–I12` 不受破坏。
5. 真机能跑通该阶段涉及的用户路径（无 UI 的阶段可用 adb/logcat 验证）。
6. 文档与实现不一致处，**改文档**（文档是锁定的契约，不能默默偏离）。
