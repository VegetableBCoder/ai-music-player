# 1. 模块职责与边界

## 1.1 做

- **候选发现（交接点）**：接收扫描阶段索引出的 `.lrc` 候选集合（同源目录 + 外部歌词目录），补齐同源判定所需的实体侧信息。
- **三级匹配**：`LyricsMatcher` 按 ①同源同名 → ②外部目录同名 → ③`[ti:]/[ar:]/[length:]` 标签匹配 的顺序执行（§4.3），全程**轻量、不走 LLM**（需求 `03` §3.6）。
- **冲突裁决**：`.lrc` 1:1（I7）；一个 `.lrc` 命中多个实体 / 一个实体命中多个 `.lrc` → 放弃关联（需求 `03` §3.5）。
- **编码探测**：UTF-8（含 BOM）与 GBK 判定（需求 `03` §3.7）。
- **LRC 解析**：时间标签变体、双语多行、元数据标签、容错（§4.6）。
- **同步展示**：按播放进度高亮 / 自动滚动 / 双语并列（需求 `03` §4）。
- **状态与删除**：歌曲详情展示「✓ 已关联 / × 未找到」；删除歌词关联（只删 `lyric` 行，不动磁盘）；失效检测与文案。

## 1.2 不做

- 在线歌词搜索 / 自动下载（需求 `03` §2.3、§7）。
- **一期不提供手动选择 / 更换歌词入口**（需求 `03` §5.3）——匹配不到即「未关联歌词」。
- 歌词编辑、时间轴修正、悬浮歌词、AI 翻译 / 解析 / 情绪分析（需求 `03` §7）。
- **不监听歌词文件变化**：用户新增 / 修改 `.lrc` 需**重新扫描**才会（重新）匹配（需求 `03` §3.6、§6）。
- 匹配阶段**不调用 LLM**（歌手别名归一等语义能力不参与歌词匹配）。

## 3.1 Room：`lyric` 表与 `LyricEntity`

复用 `03` §2.2 的表定义，**字段与命名不得改动**：

```sql

  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  entity_id   INTEGER NOT NULL REFERENCES song_entity(id) ON DELETE CASCADE,
  path        TEXT    NOT NULL UNIQUE,   -- 磁盘 .lrc 绝对路径
  source      TEXT    NOT NULL,          -- SAME_DIR | EXTERNAL_DIR | TAG_MATCH
```

# 4. 核心流程

## 4.1 扫描期总流程与候选索引交接点

**数据来源**（需求 `00` §4.1、`03` §3.7）：`ScanOrchestrator` 在扫描阶段按 `scan_source` 遍历两类来源：

- `scan_source.kind = MUSIC` 的音乐来源目录 → 产出音频文件（`music_file`）；
- `scan_source.kind = LYRICS` 的外部歌词目录 → 产出 `.lrc`；
- **同源目录**的 `.lrc` 随音乐来源目录遍历一并索引（音频目录下的 `.lrc`）。

扫描阶段对每个 `.lrc` 产出 `LrcCandidate`：`path / fileName(基名) / parentDir / size / header`。
`header` 由 `LrcDecoder.decode` + `LrcParser.parseHeader` 预解析（轻量，仅读头部标签）。

> 交接约定（供 `04` 落地时实现）：扫描器只需交付 `List<LrcCandidate>` 与 `Set<String> externalDirs`（`scan_source.kind=LYRICS` 的目录集合）。**同源判定不预置**，由匹配器按「`.lrc` 的 `parentDir` == 代表文件所在目录」现算，避免两处口径不一致。

**流程（时序）**：

```
ScanOrchestrator.commit()
  │  ① 汇总本次入库/已存在的实体（含代表文件与时长）
  │  ② LyricDao.entitiesWithoutLyric() → 仅「尚无歌词」的实体（需求 03 §3.6）
  │  ③ occupiedPaths = LyricDao.allMatchedPaths()   （I7：已被占用的 .lrc 不再分配）
  │  ④ externalDirs  = scan_source(kind=LYRICS).map{ it.path }
  │  ⑤ report = LyricsMatcher.match(pendingEntities, lrcCandidates, occupiedPaths, externalDirs)  ← 纯函数
  │  ⑥ 落库：@Transaction { report.matches.forEach { LyricDao.insert(...) } }   （ABORT 兜底 I7）
  └─⑦ 未匹配 → 实体保持「未关联歌词」，不产生 lyric 行（一期无手动入口）
```

**同源目录判定方式**：`lrc.parentDir == entity.representativeDir`（等值字符串比较）。`representativeDir = representativeFilePath.substringBeforeLast('/')`，与 `LrcCandidate.parentDir` 取同一算法，确保可比较。

## 4.2 归一化规则实现（复用实体身份键）

对齐 `00` §1.2 实体身份键的规范化规则，`TextNormalizer` 为**唯一实现**（`03` §4.1 的 `::normalize` 亦指向它）：

```kotlin
object TextNormalizer {
    private val WHITESPACE = Regex("\\s+")
    // 全角/半角统一用 NFKC；大小写折叠用 lowercase；基础拉丁 + CJK 通用
    private val PUNCT_SPACES = Regex("\\s*([()\\[\\]（）【】\\-–—:：,，、/&])\\s*")
    // 轻量演绎实体身份键的「归一化演唱者」：分隔符与角色词（00 §1.2）
    private val ARTIST_SPLIT = Regex(
        """\s*(?:[&/;、,，]|\b(?:feat\.?|ft\.?|with|vs\.?)\b)\s*""",
        RegexOption.IGNORE_CASE
    )

    fun normalizeToken(raw: String): String {
        val nfkc = java.text.Normalizer.normalize(raw, java.text.Normalizer.Form.NFKC) // 全角→半角
        val lowered = nfkc.lowercase()                                                  // 统一大小写
        val collapsed = WHITESPACE.replace(lowered, " ").trim()                          // 去首尾空格 + 折叠
        return PUNCT_SPACES.replace(collapsed) { it.groupValues[1] }                     // 去掉标点两侧空格
    }

    fun normalizeTitle(raw: String): String = normalizeToken(raw)   // 版本语义词「不剥离」，原样保留

    fun splitArtists(raw: String): List<String> =
        ARTIST_SPLIT.split(raw).map(::normalizeToken).filter { it.isNotEmpty() }.distinct().sorted()

    fun artistsKey(artists: List<String>): String =
        artists.map(::normalizeToken).distinct().sorted().joinToString("\u001F")   // 与 03 artists_key 同构
}
```

要点：

- **版本语义词保留**：`normalizeTitle` 不删除 `Live/Remix/伴奏/现场/翻唱/原唱/Instrumental` 等词（需求 `03` §3.4），故 `晴天 (Live)` 归一化为 `晴天 (live)`，与 `晴天` 不等 → 级别②③不匹配。
- **全半角**：`Normalizer.NFKC` 覆盖 `${J}→Jay`、全角括号/数字等。
- **歌手集合**：两侧都经 `artistsKey` 归一 → 与 `song_entity.artists_key` 直接字符串比较，确定性、可精确比较。
- 已知限制：`.lrc` 的 `[ar:]` 若为别名（`Jay Chou`）而实体为规范名（`周杰伦`），级别③歌手不等 → 不匹配。别名归一属 LLM 职责，扫描期不走 LLM（需求 `03` §3.6），故**一期接受该限制**。

## 4.3 三级匹配完整算法（伪代码）

```kotlin
fun match(entities, lrcFiles, occupiedPaths, externalDirs): MatchReport {
    val report = MatchReport(mutableListOf(), mutableListOf())
    val matchedEntities = mutableSetOf<Long>()
    val usedLrcPaths    = occupiedPaths.toMutableSet()                 // 已占用 .lrc 一律不可分配（I7）
    val availableLrcs   = lrcFiles.filter { it.path !in usedLrcPaths }

    // 逐级降级：高优先级先分配，命中即从后续级别的可选集合中移除
    for (level in 1..3) {
        val pendingEntities = entities.filter { it.entityId !in matchedEntities }
        val pendingLrcs     = availableLrcs.filter { it.path !in usedLrcPaths }
        if (pendingEntities.isEmpty() || pendingLrcs.isEmpty()) continue

        // ① 构建本级别二部图边
        val edges = buildList {
            for (e in pendingEntities) for (l in pendingLrcs)
                if (matchesAt(level, e, l, externalDirs)) add(Edge(e.entityId, l.path, level))
        }
        // ② 冲突裁决：仅保留「实体度 == 1 且 .lrc 度 == 1」的边（§4.4）
        val accepted = adjudicate(edges)

        // ③ 落定
        for (edge in accepted) {
            report.matches += LyricMatch(edge.entityId, edge.lrcPath, sourceOf(edge.level), edge.level)
            matchedEntities += edge.entityId
            usedLrcPaths    += edge.lrcPath
        }
        // ④ 记录本级别因冲突而落空的实体原因（最终未命中者用最后一次记录）
        rememberConflictReasons(edges, accepted, report)
    }

    // ⑤ 汇总未匹配原因
    for (e in entities) if (e.entityId !in matchedEntities)
        report.misses += LyricMiss(e.entityId, reasonOf(e, /* 若无任何候选 */ NO_CANDIDATE))
    return report
}

/* ── 级别谓词 ── */

fun matchesAt(level, e, l, externalDirs): Boolean = when (level) {
    // ① 同源目录 + 文件名精确相等（不做版本推断、不做大小写折叠——「精确相等」）
    1 -> e.representativeDir != null
        && l.parentDir == e.representativeDir
        && l.fileName == e.representativeFileName          // 原生字符串精确比较

    // ② 外部歌词目录 + 歌名归一化相等（版本语义词保留）
    2 -> l.parentDir in externalDirs
        && TextNormalizer.normalizeTitle(l.fileName) == TextNormalizer.normalizeTitle(e.canonicalTitle)

    // ③ 标签匹配：[ti:]/[ar:]/[length:] 对比 canonicalTitle / artistsKey / 代表文件时长
    3 -> l.header != null
        && TextNormalizer.normalizeTitle(l.header.title ?: "") == TextNormalizer.normalizeTitle(e.canonicalTitle)
        && TextNormalizer.artistsKey(TextNormalizer.splitArtists(l.header.artist ?: "")) == e.artistsKey
        && durationOk(l.header.lengthMs, e.representativeDurationMs)

    else -> false
}

/** 时长容差：仅当 .lrc 含 [length:]；±5s，边界 5.0s 命中、5.1s 不命中 */
fun durationOk(lrcLengthMs: Long?, repDurationMs: Long?): Boolean = when {
    lrcLengthMs == null -> true          // 无 [length:]：不强加时长门槛，
    repDurationMs == null -> true        // 代表文件时长缺失：降级（歌名 + 歌手仍已精确匹配）
    else -> kotlin.math.abs(lrcLengthMs - repDurationMs) <= 5_000L
}

fun sourceOf(level: Int) = when (level) {
    1 -> LyricSource.SAME_DIR
    2 -> LyricSource.EXTERNAL_DIR
    else -> LyricSource.TAG_MATCH
}
```

**级别①「多个实体同名文件」的处理**：
级别①以 `(parentDir, fileName)` 为键。文件系统中同一目录下同名（含相同扩展名）文件唯一，但**不同扩展名可同名**（`晴天.mp3` 与 `晴天.flac` 同处一目录），若二者因元数据不同归属两个实体，则 `晴天.lrc` 会同时命中两个实体 → 由 §4.4 的冲突裁决判定 `.lrc` 度 > 1 → **放弃关联**（宁缺毋滥）。即：级别①本身**不做版本推断、不比较元数据**，多实体同名一律交给冲突裁决丢弃。

**级别②是否需要与实体歌名比对？——需要，且只比对歌名**：
- 外部歌词目录与音频**不共址**，无法像级别①那样靠文件名与音频文件配对，故必须拿 `.lrc` 基名去和**实体歌名**比对。
- 需求 `03` §3.2 的措辞是「外部歌词目录 **+ 同名**」，仅「同名」，未提歌手；且 §3.4 明确只有级别①享有「文件名精确相等、不做版本推断」的例外，因此级别②按实体身份键的**归一化规则**比较歌名（`normalizeTitle`，版本语义词保留）。
- **不比较歌手**：歌手维度由级别③（`[ar:]`）承担。级别②若歌名撞车导致一个 `.lrc` 命中多个实体，交由冲突裁决丢弃（§4.4），不额外引入歌手比对以保持级别语义清晰。

## 4.4 冲突处理算法与数据结构

**两种冲突**（需求 `03` §3.5）：

| 冲突 | 定义 | 结果 |
| --- | --- | --- |
| 一个 `.lrc` 命中多个实体 | `lrc → {e1, e2, …}`，`|set| > 1` | 该 `.lrc` 对**所有**候选实体放弃关联 |
| 一个实体命中多个 `.lrc` | `entity → {l1, l2, …}`，`|set| > 1` | 该实体对**所有**候选 `.lrc` 放弃关联 |

**数据结构（按级别独立构建，保证优先级语义）**：

```kotlin
data class Edge(val entityId: Long, val lrcPath: String, val level: Int)

fun adjudicate(edges: List<Edge>): List<Edge> {
    // 两个方向的索引：Map 的去向由冲突类型决定
    val entityToLrcs: Map<Long, List<Edge>>   = edges.groupBy { it.entityId }   // 一个实体命中多个 .lrc
    val lrcToEntities: Map<String, List<Edge>> = edges.groupBy { it.lrcPath }   // 一个 .lrc 命中多个实体
    val entityDeg = entityToLrcs.mapValues { it.value.size }
    val lrcDeg    = lrcToEntities.mapValues { it.value.size }

    // 判定顺序：先按 .lrc 度过滤，再按实体度过滤；两者取交集 ⇒ 双边度都为 1 才保留
    return edges.filter { e -> entityDeg[e.entityId] == 1 && lrcDeg[e.lrcPath] == 1 }
}
```

**判定顺序说明**：
1. 先对每个级别分别建 `entityDeg` / `lrcDeg`（**度只在本级别的待分配集合内统计**，含已占用集合外的候选）。
2. 保留 `entityDeg == 1 && lrcDeg == 1` 的边：等价于「该实体在本级别只有一个候选 `.lrc`，且该 `.lrc` 在本级别只被这一个实体认领」。
3. **优先级**：级别①先裁决并占用；落定后该 `.lrc` 与实体从级别②的可选集合移除；以此类推。这样「实体 E 在级别①命中唯一 `.lrc` X」不会被级别②的另一候选 `Y` 干扰（不会被误判为「E 命中多个 `.lrc`」）。
4. 同级别内被丢弃的边不跨级别复活：被丢弃的只是该边，实体若在本级别**有候选但全部落空**，仍会进入下一级别（更宽松的假设）再试一次；若三级均无「双边度=1」的边 → 记为未找到。

> 说明（可测试性）：级别内冲突裁决是纯集合运算，`adjudicate` 可对任意 `edges` 独立单测。是否允许「实体在高级别因冲突落空后继续降级」在需求中未显式规定；本文档采用**允许降级**（更符合优先级降级语义）。若后续要求更严格的「宁缺毋滥」，只需在步骤 4 追加：本级别有候选但落空的实体**冻结、不进入下一级别**——不影响其余算法结构。

## 4.5 编码探测（UTF-8 含 BOM / GBK）

判定顺序：**UTF-8 BOM → 严格 UTF-8 解码校验 → 退化 GBK**（需求 `03` §3.7）。

```kotlin
object LrcDecoder {
    private val UTF8_BOM = byteArrayOf(0xEF.toByte(), 0xBB.toByte(), 0xBF.toByte())

    fun decode(raw: ByteArray): DecodedText? {
        // 1) UTF-8 BOM：直接去除前缀，严格解码
        if (raw.size >= 3 && raw[0] == UTF8_BOM[0] && raw[1] == UTF8_BOM[1] && raw[2] == UTF8_BOM[2]) {
            return strictDecode(raw, 3, raw.size, Charsets.UTF_8)?.let { DecodedText(it, "UTF-8 BOM") }
        }
        // 2) 严格 UTF-8：任何非法字节序列都会抛异常 ⇒ 不是 UTF-8
        strictDecode(raw, 0, raw.size, Charsets.UTF_8)?.let { return DecodedText(it, "UTF-8") }
        // 3) 退化 GBK
        return strictDecode(raw, 0, raw.size, Charset.forName("GBK"))?.let { DecodedText(it, "GBK") }
    }

    /** 关键：CharsetDecoder 必须 REPORT，绝不能默认 REPLACE（否则错字不报错） */
    private fun strictDecode(raw: ByteArray, off: Int, len: Int, cs: Charset): String? = try {
        val dec = cs.newDecoder()                                  // 每次新建：CharsetDecoder 非线程安全且有状态
            .onMalformedInput(CodingErrorAction.REPORT)
            .onUnmappableCharacter(CodingErrorAction.REPORT)
        dec.decode(ByteBuffer.wrap(raw, off, len)).toString()
    } catch (e: CharacterCodingException) {
        null                                                        // 校验失败 → 尝试下一编码
    }
}
```

要点：

- **BOM 必须在严格解码前剥离**，否则 `\uFEFF` 会污染 `[ti:]` 首字符导致级别③误判。
- **严格校验**：`CodingErrorAction.REPORT` 使非法 UTF-8 序列抛 `MalformedInputException`；GBK 中文（字节 > 0x7F）通常不是合法 UTF-8，故纯 UTF-8 校验能把二者分开。纯 ASCII 文件两者结果一致（不影响）。
- **线程安全**：`CharsetDecoder` 有内部状态且非线程安全，**每次调用新建**（不要缓存实例）；解码在 `Dispatchers.IO`。
- GBK 解码失败 → `DecodeFailed`（§5、§6），不写 `lyric` 行。
- 范围外：UTF-16 BOM（`FF FE` / `FE FF`）不在需求范围（需求只列 UTF-8/GBK）；如遇之，BOM 不匹配、严格 UTF-8 必失败、GBK 亦乱码 → 判 `DecodeFailed` 并记录诊断，属已知边界。

## 4.6 LRC 解析器

**支持的时间标签变体**：`[mm:ss]`、`[mm:ss.xx]`、`[mm:ss.xxx]`、`[mm:ss:xx]`（毫秒可用 `.` 或 `:` 分隔）。

```kotlin
object LrcParser {
    // mm(1-3 位):ss(1-2 位) ，分隔符 . 或 : 后跟 1-3 位小数（LRC 中按十分/百分/毫秒解释）
    private val TIME_TAG   = Regex("""\[(\d{1,3}):(\d{1,2})(?:[.:](\d{1,3}))?]""")
    private val META_TAG   = Regex("""^\[([a-zA-Z]+):(.*)]$""")   // [ti:][ar:][al:][offset:][length:]...
    private val LENGTH_MMSS = Regex("""^\s*(\d{1,3}):(\d{1,2})(?:[.:](\d{1,3}))?\s*$""")

    fun parse(text: String): LrcDocument {
        val lines = text.lineSequence().toList()
        val meta  = parseMeta(lines)
        val offset = meta.offsetMs ?: 0L
        val acc = mutableListOf<LrcLine>()
        val warnings = mutableListOf<String>()

        for (raw in lines) {
            val trimmed = raw.trim()
            if (trimmed.isEmpty()) continue                                   // 空行：跳过
            val tags = TIME_TAG.findAll(trimmed).toList()
            if (tags.isEmpty()) {
                if (META_TAG.matches(trimmed)) continue                       // 元数据行：已单独解析
                warnings += "非法行: $trimmed"                                 // 非法行：容错跳过
                continue
            }
            // 一行可含多个时间标签 [00:12.00][01:30.00]text ⇒ 同一文本复制到多个时间点
            val content = trimmed.substring(tags.last().range.last + 1).trim()
            if (content.isEmpty()) continue                                   // 仅标签无文本：跳过
            for (t in tags) acc += LrcLine(toMs(t, offset), listOf(content))
        }
        return LrcDocument(mergeSameTime(acc), meta, warnings)                // 归并同时间点 + 排序
    }

    private fun toMs(m: MatchResult, offsetMs: Long): Long {
        val min = m.groupValues[1].toLong(); val sec = m.groupValues[2].toLong()
        val ms  = fracToMs(m.groupValues[3])
        return (min * 60_000 + sec * 1_000 + ms + offsetMs).coerceAtLeast(0L)  // [offset:] 处理
    }

    /** 1 位=十分之一，2 位=百分之一，3 位=毫秒；统一还原为毫秒 */
    private fun fracToMs(frac: String): Long = when (frac.length) {
        0 -> 0L
        1 -> frac.toLong() * 100
        2 -> frac.toLong() * 10
        else -> frac.padEnd(3, '0').substring(0, 3).toLong()
    }

    /** 排序 + 同时间点归并成多文本（双语） */
    private fun mergeSameTime(src: List<LrcLine>): List<LrcLine> =
        src.sortedBy { it.timeMs }                                   // 稳定排序：同值保留文件顺序
            .groupBy { it.timeMs }
            .map { (t, group) -> LrcLine(t, group.flatMap { it.texts }) }
}
```

**元数据解析与 `[offset:]` / `[length:]`**：

```kotlin
private fun parseMeta(lines: List<String>): LrcMetadata {
    fun firstOf(key: String): String? =
        lines.firstNotNullOfOrNull { META_TAG.find(it.trim())?.takeIf { m -> m.groupValues[1].equals(key, true) }
            ?.groupValues?.get(2) }
    return LrcMetadata(
        title    = firstOf("ti")?.trim()?.takeIf { it.isNotEmpty() },
        artist   = firstOf("ar")?.trim()?.takeIf { it.isNotEmpty() },
        album    = firstOf("al")?.trim()?.takeIf { it.isNotEmpty() },
        offsetMs = firstOf("offset")?.trim()?.let { it.toLongOrNull() },      // 可为 +/-
        lengthMs = firstOf("length")?.let(::parseLengthMs),                   // 见下
        by       = firstOf("by")?.trim()
    )
}

/** [length:] 两种常见写法：mm:ss(.ff) 或纯毫秒；无法解析 → null（降级） */
private fun parseLengthMs(v: String): Long? {
    val s = v.trim()
    s.toLongOrNull()?.let { return it }                                       // "[length:215000]"
    LENGTH_MMSS.find(s)?.let { m ->
        return m.groupValues[1].toLong() * 60_000 + m.groupValues[2].toLong() * 1_000 +
               fracToMs(m.groupValues[3])
    }
    return null                                                              // 格式异常 → 忽略时长门槛
}
```

**`[offset:]` 约定**：`effectiveMs = rawMs + offsetMs`（正 offset 使歌词整体延后），全局一次性施加，并在 `coerceAtLeast(0)` 后参与排序。该符号约定在文档与测试中固定，其他分支不得再各自解释。

**解析要点**：

- `[mm:ss]` 小时不出现（LRC 通常不足 100 分钟），分钟位限制 1–3 位足以覆盖长音频。
- `[mm:ss:xx]` 与 `[mm:ss.xx]` 统一由 `TIME_TAG` 的 `[.:]` 处理。
- **双语**：两种形态都支持——① 两行同时间戳（需求 `03` §4.2 示例）；② 一行多时间标签。归并后 `LrcLine.texts` 含多行，渲染时并列。
- **容错**：空行、非法行、仅标签无文本均跳过，`warnings` 记录诊断；不因个别坏行导致整份歌词失败。
- **排序**：`sortedBy { timeMs }`（Kotlin 稳定排序，同时间点保留文件顺序）。

## 4.7 同步展示逻辑（播放期）

```kotlin
// 二分查找：定位「最后一个 timeMs <= positionMs」的行
fun indexAt(lines: List<LrcLine>, positionMs: Long): Int {
    var lo = 0; var hi = lines.size - 1; var ans = -1
    while (lo <= hi) {
        val mid = (lo + hi) ushr 1
        if (lines[mid].timeMs <= positionMs) { ans = mid; lo = mid + 1 } else hi = mid - 1
    }
    return ans          // -1 表示尚未到首行（前奏）
}
```

- **触发**：`snapshotFlow { positionMs }`（播放进度，`PlaybackController.state`）→ 计算 `index`；`index` 变化时高亮并请求滚动到该行。
- **自动滚动暂停**：用户手动滚动后暂停自动滚动 **N 秒**（常量 `AUTO_SCROLL_PAUSE_MS = 3_000`）；监听 `LazyListState.isScrollInProgress` 且非程序性滚动时置 `userScrolled = true` 并记录时间戳，`LaunchedEffect` 在 `now - lastUserScroll > AUTO_SCROLL_PAUSE_MS` 后恢复。
- **高亮**：`index` 行使用主色 + 放大字号，其余为次级文字；`index == -1` 不高亮（前奏）。
- **双语并列**：`LrcLine.texts` 多行在**同一列表项内**纵向并列渲染，高亮整项（两行同时高亮），不拆成两行独立高亮。
- **点击 seek**（可选增强）：点击某行 `playbackController.seekTo(line.timeMs)`。
- **空状态 / 失效态**（需求 `05` §5）：

# 5. 状态与边界条件

## 5.1 匹配期边界

| 场景 | 处理 |
| --- | --- |
| 级①同目录同名，但 `晴天.mp3` / `晴天.flac` 分属两实体 | `.lrc` 命中两个实体 → `CONFLICT_MULTI_ENTITY` → 放弃（§4.4） |
| 实体命中两个同名 `.lrc`（不同目录） | `CONFLICT_MULTI_LRC` → 放弃 |
| `晴天 (Live)` 实体 vs `晴天.lrc` | `normalizeTitle` 保留版本词 → 不等 → 不匹配（级别②③）；级别①只看文件名 |
| `.lrc` 无 `[length:]` | 级别③必须**歌名 + 歌手精确匹配**（二者一致），不校验时长 |
| `representativeDurationMs == null` | 级别③跳过时长门槛，仍要求歌名 + 歌手精确（降级） |
| `[length:]` 格式异常（如 `abc`） | `parseLengthMs` 返回 null → 等同「无 `[length:]`」降级 |
| `.lrc` 为空 / 无有效行 | 级别①②仍可关联（按文件名）；级别③必须标签存在 → 空文件不匹配。关联后展示 `Empty` |
| `.lrc` 头部解析失败（编码失败） | `header = null` → 级别③不可用；不会被关联（诊断 `PARSE_FAILED`） |
| 时长边界 5.0s / 5.1s | `<= 5000` 命中；`5001`（≈5.1s）不命中 |

## 5.2 展示期状态

| 条件 | 状态 | 展示 | 动作 |
| --- | --- | --- | --- |
| 有 `lyric` 行且文件可解析 | `Ready` | 同步歌词 | 高亮 / 自动滚动 / 点击 seek |
| 无 `lyric` 行 | `NotLinked` | 「未关联歌词」 | 一期**无**手动选择入口（需求 `03` §5.3） |
| 有 `lyric` 行但文件缺失 | `FileMissing` | 「歌词文件已失效」 | 「移除关联」（§5.3） |
| 有 `lyric` 行但文件无歌词行 | `Empty` | 「歌词内容为空」 | — |
| 文件存在但编码不可解码 | `Error(PARSE)` | 「歌词文件无法解析」 | 「移除关联」 |

```
歌词：× 未找到
```

- 数据来源：`LyricsRepository.observeLyric(entityId)` → 非 null 显示「✓ 已关联」，null 显示「× 未找到 / 未关联歌词」。
- **文件失效文案**（需求 `05` §5）：「歌词文件已失效」。
  需求 `05` §5 原文曾同时列「重新选择歌词」/「移除关联」，与 `03` §5.3「一期不提供手动选择 / 更换歌词」冲突。**已按 `03` 收敛**：需求 `05` §5 已改为只保留「移除关联」，本文档同步只实现「移除关联」。

## 5.4 失效检测与处理

```
loadDocument(entityId):
  1. lyric = LyricDao.findByEntity(entityId) ?: return NotLinked
  2. if (!StorageSource.exists(lyric.path)) return FileMissing     // .lrc 不存在
  3. raw = StorageSource.readBytes(lyric.path)                     // 上限 1 MB（02 §5.1）
  4. text = LrcDecoder.decode(raw) ?: return DecodeFailed(path)
  5. doc = LrcParser.parse(text)
  6. return if (doc.lines.isEmpty()) Empty else Loaded(doc, path)
```

- 失效**不自动删除**关联；由用户「移除关联」触发 `deleteLyric`。
- 失效检测在**打开歌词页时**执行（不进扫描流水线）。

## 5.5 删除与实体级联

| 操作 | 对 `lyric` 的影响 | 磁盘 `.lrc` |
| --- | --- | --- |
| `LyricsRepository.deleteLyric(entityId)` | 删除该实体的 `lyric` 行 | **保留**（I8） |
| `DeletionService.deleteSong(entityId)` | 外键 `ON DELETE CASCADE` 自动清 `lyric` | **保留**（I8） |

# 6. 错误处理（映射 `02` §8 FailureKind）

| 场景 | FailureKind | 自动恢复 | 用户可见动作 | 落库 |
| --- | --- | --- | --- | --- |
| `.lrc` 不存在（失效） | `NOT_FOUND` | 否 | 「移除关联」 | 不删关联（由用户决定） |
| 编码不可解码（非 UTF-8/GBK） | `PARSE` | 否 | 「移除关联」 | 不写 `lyric` 行 |
| `[length:]` / `[offset:]` 格式异常 | — | — | 无（静默降级） | 关联照常（级别③退回歌名+歌手） |
| 读盘 IO 失败 | `IO` | 否 | 「重试」 | 不写 |
| `lyric` 唯一索引冲突（插入撞 `path`） | `CONFLICT` | — | 无（内部兜底） | 放弃该次插入，保留原关联 |
| 三期均无候选 | —（非错误） | — | 「未关联歌词」（`03` §5.3） | 无 |

- 文案统一在 `11-错误处理与可观测性.md` 维护，模块内不硬编码（`02` §8）。
- 匹配期不产生用户可见错误：未匹配即「未找到」，是正常业务结果而非错误。

# 7. 性能与并发

| 关注点 | 约定 |
| --- | --- |
| 匹配复杂度 | 级别①建 `(dir,fileName) → 实体` 索引，`O(E + L)`；级别②③对剩余候选各一次遍历 + Map 度数统计，整体 `O(L·R)`（R 为待匹配实体数，量级百~千），纯内存、无嵌套 IO |
| 头部解析 | `parseHeader` 只扫描 `[key:value]` 元数据行，遇到首个时间标签行即可提前返回；读盘上限 1 MB（对齐 `02` §5.1 `readBytes(maxBytes = 1 shl 20)`） |
| 线程 | 编码探测 / 解析在 `Dispatchers.IO`；`LyricsMatcher.match` 为纯函数，可在任意线程调用，无锁 |
| 写事务 | 全部 `report.matches` 的插入包在单个 `@Transaction`（对齐 `02` §7「跨表写入必须事务」）；`OnConflictStrategy.ABORT` 兜底 I7 |
| 单写者 | `lyric` 表只由 `LyricsRepository.matchOnScan` / `deleteLyric` 与 `DeletionService.deleteSong` 写入；UI 只读 |
| 扫描互斥 | 匹配作为扫描提交阶段的一部分，受 `ScanOrchestrator` 全局 `Mutex` 保护（`02` §7），天然单次执行 |
| 歌词页渲染 | 行列表一次性载入内存（`LazyColumn`）；`indexAt` 二分 `O(log N)`，随进度高频调用但不重解析 |
