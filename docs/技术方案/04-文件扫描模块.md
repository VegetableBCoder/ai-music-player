# 1. 模块职责与边界

## 1.1 做

| 职责 | 落点 |
| --- | --- |
| 管理扫描来源：音乐目录（`scan_source.kind = MUSIC`）与外部歌词目录（`kind = LYRICS`）的增删与启用 | `ScanSourceRepository` |
| 权限门禁：检测「所有文件访问」、引导授权、未授权时降级 | `StorageAccessChecker` |
| 目录遍历：按扩展名白名单发现音乐文件与 `.lrc` | `FileStorageSource.listFiles` |
| 元数据提取：标题 / 歌手 / 专辑 / 专辑歌手 / 日期 / 时长 / 内嵌封面存在性 | `MmrMetadataReader` |
| `.lrc` 索引：**只登记路径候选**，匹配交给 `08` | `LrcCandidate` |
| 差异比对：新增 / 已存在跳过 / 已删除清理 | `ScanOrchestrator.diff` |
| 扫描会话状态机与进度上报、取消 | `ScanOrchestrator.state` |
| 提交事务：写 `music_file(UNANALYZED)` + 建 `analysis_run` + 写 `analysis_run_file` + 清理已删记录 | `ScanOrchestrator.commit` |

## 1.2 不做（边界，必须守住）

1. **不写实体**：扫描**不重建实体**，不写 `song_entity` / `song_artist` / `entity_tag`。实体最早的写入点是 `AnalysisOrchestrator.attach`（`03` §4.1）。扫描只写 `music_file` 与 `analysis_run*`。
2. **不做匹配**：`.lrc` 与歌曲的匹配、`lyric` 表写入、I7（`lyric.path` 唯一）由 `08-歌词模块` 负责。本模块只产出候选列表。
3. **不做分析**：`analysis_status` 的 `UNANALYZED → ANALYZING → LINKED/FAILED` 流转只由 `AnalysisOrchestrator` 驱动（`02` §7 单写者原则；本模块仅写入初值 `UNANALYZED`）。本模块只**触发**分析（调用 `analyzePending(runId)`），不修改状态。
4. **不访问磁盘细节**：文件访问一律经 `StorageSource`（`02` §5.1，只读 `FileRef`），模块内禁止直接 `java.io.File`（唯一例外是 `FileStorageSource` 自身与 `PathNormalizer`）。
5. **不硬编码文案**：所有用户可见文案由 `11-错误处理与可观测性.md` 统一维护；本模块只产出 `FailureKind` / 计数。
6. **不处理媒体库以外的写操作**：物理删除属 `DeletionService`（`03` §4.4），扫描只在清理已删记录时**复用**其内部序列，不直接 `StorageSource.delete`。

# 4. 核心流程

## 4.1 扫描会话状态机落地（`02` §6.2）

```
IDLE ──scan()──▶ SCANNING ──提取元数据完成──▶ DIFFING ──比对完成──▶ AWAITING_USER
                                                                    │
                             ┌──────────────────────────────────────┴───────────────────────────┐
                             │「分析并添加」                                                     │「放弃」
                             ▼                                                                   ▼
                        COMMITTING ──写库成功──▶ ANALYZING ──分析 Flow 完成──▶ DONE          DISCARDED
                             │                         │                                       │（不写库，不产生 analysis_run）
                    cancel 于批次边界                  └─ cancel/全部失败 ─▶ ABORTED(run) ─▶ IDLE
                             ▼
                          IDLE（已提交批次保留）
```

| 转移 | 触发 | 守卫 | 副作用 |
| --- | --- | --- | --- |
| `IDLE→SCANNING` | `scan()` | 取到 `Mutex` 且存在 enabled `MUSIC` 来源 且 `accessLevel != NONE` | 清空上一轮 `diff`，重置进度 |
| `SCANNING→DIFFING` | 遍历 + 元数据提取 + lrc 收集完成 | 未取消 | — |
| `DIFFING→AWAITING_USER` | 比对完成且（有新文件或需清理） | — | `state.diff = result` |
| `SCANNING/DIFFING→IDLE` | 异常 / 取消 | — | **不写库** |
| `AWAITING_USER→COMMITTING` | `commit()`（用户「分析并添加」） | `diff != null` | 进入事务序列 §4.8 |
| `AWAITING_USER→DISCARDED` | `discard()`（用户「放弃」） | — | `diff = null`，**无任何持久化**（与不存在一致） |
| `COMMITTING→ANALYZING` | 写库完成 | — | 建 `analysis_run`（RUNNING），触发 `analyzePending(runId)` |
| `ANALYZING→DONE` | 分析 Flow 完成 | — | `analysis_run.status = COMPLETED`（由 `05` 落地） |
| `COMMITTING/ANALYZING→IDLE` | `cancel()` | 仅在批次/事务边界生效 | `analysis_run.status = ABORTED` |

**「放弃」不写库的实现**：`discard()` 仅把内存态 `pendingDiff` 置空、`phase = DISCARDED`；**不调用** `analysisRunDao.createRun`，**不写** `music_file` → 无 `analysis_run` 记录、无批次文件、无文件行（`00` §4.4）。下次 `scan()` 因 `scan_source` 未变、磁盘未变，会重新把这些文件比对为「新增」再提示一次。

**会话持久性**：`AWAITING_USER` 的 diff 只在内存（`ScanSessionState`）。进程被杀 → 回到 `IDLE`；因 diff 幂等，重新扫描即可复现。V1 不为 AWAITING_USER 做落库（避免出现「放弃后仍留记录」的违规态）。

> **落地补充（Phase 3d）：守卫不通过时返回什么**
>
> §4.1 的表格规定了 `IDLE→SCANNING` 的两个守卫，但没说守卫不通过时 `scan()` 返回什么。
> 本期的取法：
>
> | 情况 | 返回 | 理由 |
> | --- | --- | --- |
> | `accessLevel == NONE` | `Failed(PERMISSION, null)` | 确实是权限问题，要引导去授权 |
> | **没有 enabled 的 `MUSIC` 来源** | `NoChanges(全 0)` + `state.warnings` 记一条 | 这只是「还没选来源」，**不能**报 `PERMISSION` —— 那会把用户骗去授权。空状态的区分由 UI 用「来源列表是否为空」做（§5.1） |
> | 全部来源都不可读 | `Failed(PERMISSION, null)` | §4.3 规则 2：只有**全部**根目录拿不到时才升级为致命 |
>
> 另外两点：`discard()` 后 `phase = DISCARDED` 且**不写任何库**（批次与文件都是 0 行），
> 下次扫描会把同样的文件重新比成「新增」；`cancel()` 在 `SCANNING`/`DIFFING` 下直接回 `IDLE`，
> 在 `COMMITTING` 下返回 `CommitResult.Cancelled`（已提交批次保留 + `ABORTED`）。

## 4.2 权限门禁

```
currentLevel(context):
  if SDK >= 30 (Android 11+):
      if Environment.isExternalStorageManager()            -> FULL           // 「所有文件访问」
      else if grant(READ_MEDIA_AUDIO  |  READ_EXTERNAL_STORAGE) -> MEDIA_LIBRARY_ONLY
      else                                                 -> NONE
  else (SDK 26..29):                                        // 无 MANAGE_EXTERNAL_STORAGE 概念
      if grant(READ_EXTERNAL_STORAGE)                      -> FULL           // 该版本即为广读
      else                                                 -> NONE
```

**授权引导**：`allFilesAccessIntent(context)` 返回
`Intent(Settings.ACTION_MANAGE_ALL_FILES_ACCESS_PERMISSION, Uri.fromParts("package", pkg, null))`；
从设置页返回时调 `refreshAccessLevel()`（`onResume`）。若返回后仍未授权，**不再反复弹窗**——用 `dataStore.permission_hint_shown` 抑制（`03` §6，`05` §7「拒绝后不再反复弹窗，保留入口可再触发」）。

**降级策略**

| Level | 扫描范围 | 可用功能 | 置灰功能 |
| --- | --- | --- | --- |
| `FULL` | 任意来源目录 DFS；同源 `.lrc`；外部歌词目录 | 全部 | — |
| `MEDIA_LIBRARY_ONLY` | 仅 `MediaStore.Audio.Media.EXTERNAL_CONTENT_URI` 查询（`IS_MUSIC=1`），`_DATA` 合成 `FileRef` | 扫描 / 分析 / 播放 | 自定义目录来源、`.lrc` 索引、「物理删除文件」、播放列表外路径展示 |
| `NONE` | 不扫描 | 引导授权 | 全部 |

- `MEDIA_LIBRARY_ONLY` 下 `StorageSource.listFiles` **不被调用**，改走 `MediaStoreAudioSource.query()`，其 `AudioMetadata` 直接由 `MediaStore` 列（`DURATION`/`TITLE`/`ARTIST`/`ALBUM`）合成，**跳过 `MetadataReader`**（省一次解码）。
- `NONE` 时 `scan()` 立即返回 `ScanOutcome.Failed(PERMISSION, null)`，不进入 `SCANNING`。

## 4.3 目录遍历算法（`FileStorageSource.listFiles`）

```kotlin
object AudioFormats {
    val AUDIO_EXTS = setOf("mp3", "flac", "m4a", "aac", "ogg", "wav", "wma", "ape")
    val LRC_EXTS   = setOf("lrc")
}

private const val MAX_DEPTH = 12
// 系统目录黑名单（按目录名或相对根路径匹配）
private val SYSTEM_DIRS = setOf("Android/data", "Android/obb", ".thumbnails", ".trash", "LOST.DIR")

fun listFiles(roots: List<String>, exts: Set<String>, onProgress: (Int) -> Unit): Sequence<FileRef> = sequence {
    val extSet = exts.mapTo(HashSet()) { it.lowercase() }
    val visited = HashSet<String>()                 // canonical 目录路径 → 软链/重复根防护
    val stack = ArrayDeque<Pair<File, Int>>()       // DFS：(目录, 深度)
    roots.forEach { r -> File(r).takeIf { it.isDirectory }?.let { stack.addLast(it to 0) } }

    var found = 0
    while (stack.isNotEmpty()) {
        val (dir, depth) = stack.removeLast()
        if (depth > MAX_DEPTH) continue                          // 深度限制
        if (dir.name.startsWith(".")) continue                   // 隐藏目录
        if (isSystemDir(dir)) continue                           // 系统目录
        val canon = dir.canonicalPathOrNull() ?: dir.absolutePath
        if (!visited.add(canon)) continue                        // 软链成环 / 重复根 → 跳过

        val children = try {
            dir.listFiles()
        } catch (e: IOException) { logger.warn("skip dir $dir", e); null }   // 错误目录跳过，不中断
        if (children == null) continue                           // 不可读目录

        for (f in children) {
            if (f.name.startsWith(".")) continue                 // 隐藏文件/目录
            when {
                f.isDirectory -> if (!isSystemDir(f)) stack.addLast(f to depth + 1)
                f.isFile      -> {
                    val ext = f.name.substringAfterLast('.', "").lowercase()
                    if (ext in extSet) { found++; onProgress(found)   // onProgress = 「已发现 N」
                        yield(FileRef(f.absolutePath, f.name, f.length(), f.lastModified())) }
                }
                else -> Unit                                     // FIFO/设备文件等非普通文件，忽略
            }
        }
    }
}
```

**关键规则**

1. **符号链接防护**：`visited` 记录每个进入目录的 `canonicalPath`；`canonicalPath != absolutePath` 即含软链（如 `/sdcard` → `/storage/emulated/0`），重复即跳过。配合 `MAX_DEPTH` 双保险，绝不因软链成环死循环。
2. **错误目录跳过不中断**：`SecurityException` / `IOException`（`EACCES`、挂载点移除）→ 记 warning、`continue`，**不终止整次扫描**；仅在根目录全部不可读时升级为 `ScanOutcome.Failed`。
3. **隐藏项**：目录名或文件名以 `.` 开头一律跳过（`.thumbnails`、`.nomedia` 同目录即天然隔离）。
4. **扩展名白名单**：`extSet` 大小写不敏感（`.MP3` / `.Flac` 命中）；音频 `mp3/flac/m4a/aac/ogg/wav/wma/ape`，歌词 `lrc`。`roots` 由调用方给出。
5. **多根并联**：一次调用传入全部来源目录，公用 `visited` 去重（同一目录被两个来源覆盖只扫一次）。
6. **辅助方法**：`StorageSource.exists(path)` / `size(path)` 用于差异比对阶段的存在性/大小复核（MediaStore 场景下用查询结果）。

## 4.4 元数据提取（`MmrMetadataReader`）

```kotlin
class MmrMetadataReader(
    private val parallelism: Int = 4,
    private val timeoutMs: Long = 5_000,
    private val fallback: MetadataReader? = null,   // jaudiotagger，懒加载兜底
    private val extractors: MediaExtractorPool        // duration 兜底
) : MetadataReader {

    private val pool = MmrPool(parallelism)           // 每个并发槽独占 1 个 MediaMetadataRetriever

    override fun read(ref: FileRef): AudioMetadata {
        val slot = pool.borrow()
        val mmr = slot.retriever
        return try {
            mmr.setDataSource(ref.path)
            val duration = mmr.extract(METADATA_KEY_DURATION)?.toLongOrNull()
                ?: extractors.durationMs(ref.path)     // MediaExtractor 兜底
                ?: 0L                                  // 仍缺失 → 0（入库时写 NULL，见下）
            AudioMetadata(
                title           = mmr.extract(METADATA_KEY_TITLE),
                artist          = mmr.extract(METADATA_KEY_ARTIST),
                album           = mmr.extract(METADATA_KEY_ALBUM),
                albumArtist     = mmr.extract(METADATA_KEY_ALBUMARTIST),
                date            = mmr.extract(METADATA_KEY_DATE) ?: mmr.extract(METADATA_KEY_YEAR),
                durationMs      = duration,
                hasEmbeddedPicture = mmr.embeddedPicture != null
            )
        } catch (t: Throwable) {
            logger.warn("meta parse failed: ${ref.path}", t)
            degrade(ref)                              // 解析失败 → 降级，不阻断扫描
        } finally {
            // 超时/异常过的实例可能处于僵死态 → 丢弃而非回收，由池补位
            pool.recycle(slot)
        }
    }

    private fun degrade(ref: FileRef) = AudioMetadata(
        title = ref.name.substringBeforeLast('.').ifBlank { ref.name },  // 文件名兜底
        artist = null, album = null, albumArtist = null, date = null,
        durationMs = 0L, hasEmbeddedPicture = false
    )
}
```

**约定**

| 关注点 | 做法 |
| --- | --- |
| **实例复用** | `MediaMetadataRetriever` **非线程安全**，按并发槽（≤4）**独占复用**，绝不跨线程共享；`finally` 中 `release()` 或归还池 |
| **超时保护** | MMR 无超时 API。**超时归 `MmrMetadataReader` 自己**：读取提交给内部工作线程，`future.get(timeoutMs)` 超时即作废该实例并补位。见下方落地补充（原「调用侧 `withTimeoutOrNull`」的写法已废） |
| **并发度** | `parallelism = min(4, Runtime.availableProcessors())`，经 `Dispatchers.IO.limitedParallelism(parallelism)` 限流（§7） |
| **解析失败降级** | 返回 `degrade(ref)`（标题取文件名去扩展名，其余 null，`durationMs=0`）；文件照样入库为 `UNANALYZED`，不阻断、不计失败 |
| **`durationMs` 缺失** | 顺序：MMR `METADATA_KEY_DURATION` → `MediaExtractor` → `0L`。入库时 `durationMs.takeIf { it > 0 }`，即 `music_file.duration_ms = NULL`（语义：未知）。非致命：播放时长由 Media3 提供；歌词匹配用代表文件时长，缺失时由 `08` 另定策略 |
| **jaudiotagger 兜底** | 仅当 MMR 未取到 `date` 或 `hasEmbeddedPicture=false` 时**按需**调用（成本高），结果并入 `AudioMetadata`；**选型未定，当前只是挂点**（见落地补充） |

> **落地补充（Phase 3b）：超时为什么不能放在调用侧**
>
> 本节原先写「在**调用侧**用 `withTimeoutOrNull(timeoutMs)` 包裹 `withContext(Dispatchers.IO)`（见 §4.5）」，
> 但同一张表又要求「该槽标记 `tainted` 并 `discard`」—— **这两条不可能同时成立**：
> `MetadataReader.read` 是给定的**非 suspend 阻塞**签名，协程超时打断不了正在跑的原生调用，
> 调用侧既不返回、也不知道哪个槽脏了，`discard` 成了死条文；而池只有 4 个槽，
> 连续 4 次超时就会把池**饿死**。所以超时移进 `MmrMetadataReader`：读取跑在自己的工作线程上，
> `get(timeout)` 超时后能**真正**把实例作废、下次借出时补新实例。§4.5 的 `withTimeoutOrNull`
> 随之去掉 —— 同值的两层超时只会互相打架。
>
> 两条释放纪律：**异常路径立即 `release()`**（任务已结束，安全）；**超时路径推迟到任务真正结束
> 再 `release()`** —— 原生调用可能仍在跑，此刻 `release` 会把那个线程打死。
>
> **jaudiotagger 兜底只是挂点**：`01 §3` 只说「不足时补 jaudiotagger」，没有锁定 artifact 与版本，
> 所以 `tagFallback` 参数存在、默认 `null`。选型定了再接上。
>
> **可测性**：真机 MMR 被换成 `MmrRetriever` 窄缝（出口是 `RawTags`，不是逐个 MMR 键 ——
> 键常量属平台细节，暴露出去会让假实现也得模拟一套键，测的东西就漂移了）。于是回退顺序、
> 解析失败降级、超时作废、实例独占全部在 JVM 上测（14 条）；真机只留「MMR 读得对不对」的冒烟（6 条）。

```
suspend fun extractMetadataPipelined(refs: Sequence<FileRef>): List<ScannedFile> =
  coroutineScope {

    refs.map { ref ->
      async(gate) {
        ensureActive()
        val meta = metadataReader.read(ref)                       // 超时归 reader 自己管（§4.4 落地补充）
        updateProgress { it.copy(metadataProcessed = it.metadataProcessed + 1) }

    }.awaitAll()

```
- 遍历是 `Sequence`（惰性），与元数据 `async` 交错消费，**边发现边解析**，避免先全量扫路径再全量解析。
- 单文件失败/超时**不影响**其它文件（`async` 内 catch，不外抛）。

## 4.6 差异比对（唯一键 = 规范化绝对路径）

**路径规范化 `PathNormalizer.normalize(path, primaryRoot)`**

```
1) 分隔符统一：'\' → '/'
2) Unicode 归一：Normalizer.normalize(p, NFC)      // 处理 macOS 拷入的 NFD 文件名
3) 折叠重复斜杠：Regex("/{2,}") → "/"
4) 去尾部斜杠（长度 > 1 时）
5) 别名解析：/sdcard、/storage/self/primary、/mnt/sdcard → primaryRoot（主存储根）
6) 软链解析（best-effort）：File(p).canonicalPath，失败降级为 p；**仅对绝对路径做**
```

> **落地补充（Phase 3a）**：主存储根**不是**在 `PathNormalizer` 内部读环境常量，而是作为
> `primaryRoot` 参数传入 —— 由 `FileStorageSource` 在真机上把
> `Environment.getExternalStorageDirectory()` 的值传进来。理由：`Environment` 是 Android API，
> 一读这套规则在 JVM 上就测不了，而别名归并恰好是最容易写错的一段（本机 **37 条** JVM 单测覆盖）。
> 步骤 6 只对绝对路径生效：相对路径在这里 `canonicalize` 会悄悄拼上进程工作目录，
> 把一个相对路径变成绝对路径，那不是归一化。多用户设备上主存储根形如
> `/storage/emulated/<userId>`，参数化后天然支持。

**键的选取规则**

| 规则 | 结论 |
| --- | --- |
| 大小写 | **保持原大小写**（Android 主存储 ext4/FUSE 区分大小写）；仅**扩展名匹配**忽略大小写。SD/exFAT 等大小写不敏感卷上，规范化后大小写可能不一致 → 去重时对 `newFiles` 内部做一次大小写不敏感兜底（`LinkedHashMap<String, ScannedFile>` + `equalsIgnoreCase` 回退），减少重复入库尝试（唯一索引兜底，不会脏写） |
| 绝对路径 vs 相对 | 一律存**规范化后的绝对路径**（`music_file.path` 即此值） |
| 软链等价 | 经 `canonicalPath` 归并，同一文件的不同别名（`/sdcard/...` vs `/storage/emulated/0/...`）视为同键 |

**三类比对**

```kotlin
suspend fun diff(scanned: List<ScannedFile>, lrc: List<LrcCandidate>): ScanDiff {
    val existing = musicFileDao.allPaths().toHashSet()          // Set<规范化 path>
    val seen = HashSet<String>()
    val newFiles = ArrayList<ScannedFile>()
    val skipped  = ArrayList<String>()
    for (sf in scanned) {
        val key = sf.normalizedPath
        if (key in existing || !seen.add(key)) skipped += key   // 已存在 或 本轮重复 →跳过
        else newFiles += sf
    }
    // 已删除清理：**仅在完整权限下做**（见下方落地补充）
    val cleaned = if (accessLevel == FULL) existing.filterNot { storage.exists(it) }
                  else emptyList()          // 降级通道下「媒体库查不到」≠「磁盘上没了」
    return ScanDiff(newFiles, skipped, cleaned, lrc)
```

> **落地补充（Phase 3d）：降级通道下必须放弃清理 —— 原公式会毁库**
>
> 本节原先的写法是 `onDisk = existing.intersect(scanned)`、`cleaned = existing - onDisk`。
> 这在 `MEDIA_LIBRARY_ONLY` 下是**破坏性**的：媒体库查不到，并不等于磁盘上没了
> （自定义目录来源的文件本来就不在媒体库里）。丢失「所有文件访问」的那一刻，用户整个
> 自定义目录的 `music_file` 会被判为「已删除」清掉，再经 I3（清理不留 0 文件实体）
> 连带删掉实体与标签、历史 —— **整个库消失**。
>
> 判断「磁盘上还在不在」需要遍历，而降级通道**没有遍历能力**（§4.3 的 `listFiles` 不调用）。
> 验证不了存在性就不动库：降级下 `cleanedPaths` 恒为空。降级是权限问题，
> 不该由它来删数据。
- **新增** = 磁盘有、库里无（含本轮去重后）。
- **已存在跳过** = 库里有（含 `LINKED`，`I4` 保证不会被重分析）。
- **已删除清理** = 库里有、磁盘无 → 在 `COMMITTING` 阶段删记录（§4.8）。清理**与用户是否点「分析并添加」无关**（`02` §6.2），故亦可能单独触发清理。
- **被过滤跳过** = 通过扩展名白名单、但没过过滤规则（需求 `../需求文档/01-歌曲库管理.md` §2.5：时长 < `scan_min_duration_ms` 或体积 < `scan_min_size_bytes`，**0 = 不启用**）。它**从不进入比对**：不计入 `discovered`、不进 `newFiles`、也不计 `skipped_count`（后者是「已在库里」的计数，语义不同）。

  **执行位置**：体积检查放在**遍历阶段**（`FileRef.size` 现成，先挡掉再谈元数据 —— 省掉大量小文件的无谓解码）；时长检查放在**元数据之后**（`durationMs` 只有解出来才知道）。两处都在 `ScanOrchestrator` 内，规则值从 `SettingsRepository` 实时读取。

  **只作用于新扫描**：已入库的 `music_file` 不因规则变化而移除（删除只发生在「磁盘上不存在」时）。

## 4.7 `.lrc` 索引（边界交接）

1. 扫描阶段只做**候选登记**：对 `kind=MUSIC` 的启用来源（同源）+ `kind=LYRICS` 的启用来源（外部歌词目录），用 `LRC_EXTS` 调一次 `listFiles`，得到 `LrcCandidate`（`origin` 标 `SAME_DIR` / `EXTERNAL_DIR`）。
2. 候选**不写库**；`lyric` 表写入属 `08`（I7：`lyric.path` 唯一由 08 保证）。
3. 交接：`COMMITTING` 后（分析开始前）调用 `LyricMatcher.ingest(candidates)`（`08` 提供；候选发现语义归 08，本模块只负责「发现并登记路径」）。
4. `MEDIA_LIBRARY_ONLY` 下降级：**不产出** lrc 候选（无法遍历同源目录），歌词相关功能置灰。

## 4.9 进度上报与取消

- 进度源：遍历阶段 `listFiles` 的 `onProgress(found)` → `state.discovered`（「已发现 N」）；元数据阶段 `state.metadataProcessed`。
- 上报：`ScanOrchestrator.state: StateFlow<ScanSessionState>`，ViewModel 转 `ScanUiState`（`09`）。
- 取消：`cancel()` 通过 `currentCoroutineContext().job.cancel()` 取消当前 Job。

| 取消时机 | 事务一致性 |
| --- | --- |
| `SCANNING` / `DIFFING` | 无写库 → 直接回 `IDLE`，无任何影响 |
| `COMMITTING` | 仅在**批次边界**检查 `ensureActive()`；单批次是 `@Transaction`，要么整批提交要么整批回滚。已提交批次**保留**（`path` 唯一 + `INSERT OR IGNORE` → 幂等）；`analysis_run.status = ABORTED`。重新扫描时已入库文件落入「已存在跳过」，不会重复 |
| `ANALYZING` | 由 `AnalysisOrchestrator` 处理（`analysis_run.status = ABORTED`，文件置 `FAILED`/保持 `UNANALYZED`，见 `05`） |

# 5. 状态与边界条件

## 5.1 空状态（对齐 `05` §1）

| 场景 | 判定 | 展示 / 后续 |
| --- | --- | --- |
| 无权限 / 未指定来源 | `accessLevel == NONE` 或 enabled `MUSIC` 来源为空 | 引导「选择音乐来源」/「去授权」；**未选前不启动扫描** |
| 扫描中 | `phase == SCANNING` | 进度「已发现 N 首」；可后台、可「取消」 |
| 扫描到新文件 | `ScanOutcome.AwaitingUser` | 「发现 N 个新文件」+ 摘要（新增 N / 已存在跳过 M / 已删除清理 K）；「分析并添加」/「放弃」 |
| 扫描无新文件 | `ScanOutcome.NoChanges` 且无清理 | 「未发现新文件」+「重新扫描」 |
| 扫不到任何歌曲 | `NoChanges` 且 `discovered == 0` | 「没有扫描到音乐」+ 提示检查来源/权限；「重新选择来源」/「重新扫描」 |

## 5.2 边界与幂等

| 边界 | 处理 |
| --- | --- |
| 重复触发扫描 | `Mutex` 未获取到 → `ScanOutcome.AlreadyRunning`（「扫描进行中」） |
| 来源目录被移除 | `remove(id)` 只删 `scan_source` 行；已入库 `music_file` **不受影响**（扫描不重建实体）；下次扫描不再覆盖该目录 |
| 来源目录路径不存在 | `add` 返回 `Invalid`；已有来源路径失效 → 扫描时跳过并计 warning |
| 空目录 / 全部为系统目录 | `discovered == 0` → `NoChanges` |
| 同一文件被多个来源覆盖 | `visited` 去重 + 差异键去重 → 只入库一次（`music_file.path` UNIQUE，I1） |
| 已 `LINKED` 文件重现 | 归入「已存在跳过」，**不重置状态**（I4） |
| 文件被移动 / 重命名 | 视为「旧路径已删除 + 新路径新增」；新文件分析后按 `entityKey` 自动挂回（`00` §4.5、`01` §3.6） |
| `AWAITING_USER` 期间磁盘再变化 | 提交时以**当前**磁盘存在性为准（`cleanMissingFile` 对已消失路径静默跳过；新增路径留待下次扫描） |
| 提交时并发扫描 | 不可能：`commit` 与 `scan` 共用同一 `Mutex` |
| `MEDIA_LIBRARY_ONLY` 下降级项 | 自定义目录来源、`.lrc` 索引、物理删除 → UI 置灰并说明原因 |

# 6. 错误处理

## 6.1 映射到 `FailureKind`（`02` §8）

| 情形 | `FailureKind` | 是否致命 | 处理 |
| --- | --- | --- | --- |
| 无「所有文件访问」且无法降级（`accessLevel == NONE`） | `PERMISSION` | **是**（`ScanOutcome.Failed`） | 不写库；引导「去授权」（`05` §7） |
| 根目录不可读 / `SecurityException`（`EACCES`） | `PERMISSION` | 视来源数：全不可读→是；部分→否 | 跳过该来源并计 warning |
| 单个子目录 `IOException` / 挂载点被移除 | `IO` | 否 | 记 warning，继续（§4.3） |
| 元数据读取 / 解析异常、超时 | `IO` | 否 | 降级为 `degrade(ref)`，文件仍入库（§4.4） |
| 写库 I/O 错误（SQLite 失败） | `IO` | **是**（`CommitResult.Failed`） | 事务回滚；`analysis_run` 不落库或置 `ABORTED` |
| 磁盘空间/权限导致无法建文件行以外错误 | `UNKNOWN` | **是** | 记录日志，提示「扫描失败，请重试」 |
| 其它未预期异常 | `UNKNOWN` | **是** | 兜底 catch → `ScanOutcome.Failed`，回到 `IDLE` |

> 文案统一由 `11` 从 `FailureKind` 映射；本模块**不硬编码**用户文案，仅上抛 `AppError { kind, cause }` 与计数。
> 非致命问题（跳过目录、降级元数据）不上抛 `FailureKind`，而是进入 `ScanSessionState.warnings`，在摘要旁以「N 个目录无法读取 / N 个文件元数据缺失」呈现。

## 6.2 部分失败不阻断原则

- `SCANNING` 阶段的**每个来源目录**独立 try/catch：单目录失败不终止全扫描。
- `extractMetadataPipelined` 的**每个 `async`** 独立 catch：单文件失败不终止流水线。
- `COMMITTING` 阶段**每批次**独立事务：单批失败 → 该批回滚 + `analysis_run.status = ABORTED`，已成功批次保留（幂等可重跑）。

# 7. 性能与并发

| 关注点 | 约定 |
| --- | --- |
| **单例 + `Mutex`** | `ScanOrchestrator` 为单例（Hilt `@Singleton`），`scan()` / `commit()` / `cancel()` 共用一把 `Mutex`，同一时刻仅一次扫描；重复触发返回 `AlreadyRunning`（`02` §7） |
| **IO 调度** | 遍历、元数据、写库一律 `Dispatchers.IO`；DAO `suspend` 由 Room 调度 |
| **有界并发** | 元数据解析 `Dispatchers.IO.limitedParallelism(min(4, cores))`——受限于 MMR 实例数与解码内存，**不盲目放大** |
| **流式处理** | 遍历用 `Sequence`（不把 N 万路径一次性读入），与元数据 `async` 交错，边发现边解析 |
| **分批提交** | `INSERT_BATCH = 200` 行/事务；`analysis_run_file` 批量 `linkFiles`；避免单事务过大导致 WAL 膨胀与锁等待 |
| **内存控制** | 每个 `ScannedFile`（路径 + 元数据）约 0.3–0.5 KB；万级文件 ≈ 数 MB，可接受。若需支撑 5 万+，改为「分批解析 → 分批比对 → 分批入库」，仅在内存保留待提交 `chunk` |
| **批处理边界** | 大库扫描经 `WorkManager`（`CoroutineWorker`），避免前台阻塞；进程于扫描中被杀 → 重新扫描（差异幂等，已入库部分自动「跳过」） |
| **数据量假设** | 目标百~千级（`03` §5）；不在扫描期做 N+1 查询，`allPaths()` 一次取全量已入库路径集合 |

**与 WorkManager 的对接边界（细节在 `10`，此处仅定接口）**

```kotlin
class ScanWorker(appContext: Context, params: WorkerParameters) : CoroutineWorker(appContext, params) {
    override suspend fun doWork(): Result = when (val o = scanOrchestrator.scan()) {
        is ScanOutcome.AwaitingUser -> { scanNotifier.notifyNewFiles(o.summary); Result.success() }
        is ScanOutcome.NoChanges    -> Result.success()
        is ScanOutcome.Failed       -> if (o.kind == FailureKind.PERMISSION) Result.failure() else Result.retry()
        ScanOutcome.Cancelled, ScanOutcome.AlreadyRunning -> Result.success()
    }
    // 退避：BackoffPolicy.EXPONENTIAL（01 §2）
}
```
- **边界原则**：`Worker` 只执行**无用户交互的 headless 扫描 + 比对**，并把 `AWAITING_USER` 结果**通知**给用户；`commit()` / `discard()` **永远由前台用户动作触发**（保证「放弃不写库」语义）。`ANALYZING` 的调度（`AnalysisWorker` / 前台服务）属 `10`。

# 8. 测试要点

| 测试 | 覆盖 | 期望 |
| --- | --- | --- |
| **I1 — 路径唯一** | `music_file.path` UNIQUE + 差异去重 | 同一路径两次入库只产生 1 行；本轮重复的文件只计 1 次「新增」 |
| **I1 — 别路径归并** | `/sdcard/x.mp3` 与 `/storage/emulated/0/x.mp3` | 规范化后同键，只入库一次 |
| **I3 — 清理不留 0 文件实体** | `cleanMissingFile` 删掉某实体最后一个文件 | 该实体被级联删除（无 0 文件实体残留）；有其它文件时代表文件重选（I2/I11 联动） |
| **I4 — 已关联不重分析** | 重扫含 `LINKED` 文件的目录 | 该文件落入「已存在跳过」，状态不变、不触发分析 |
| **扫描状态机 — 正常** | `scan`→`commit` 全链路 | `IDLE→SCANNING→DIFFING→AWAITING_USER→COMMITTING→ANALYZING`；**`DONE` 与 `analysis_run.status = COMPLETED` 的断言挪到 Phase 4** —— 编排器只**触发**分析（`analyzePending` 是本期注入的 no-op），把它置为完成的写者属 `05`（`02 §7` 单写者原则）。Phase 3 的验收止于 `ANALYZING` + 批次落库 + 交棒被调用 |
| **扫描状态机 — 放弃** | `discard()` | `phase==DISCARDED`；`analysis_run` 表 **0 行**、`music_file` 新增 **0 行**；下次 `scan()` 重现为「新增」 |
| **扫描状态机 — 取消** | 于 `COMMITTING` 中 `cancel()` | 已提交批次保留、`analysis_run.status == ABORTED`；重跑不重复入库（幂等） |
| **权限门禁** | 三级 `StorageAccessLevel` 判定（API 30 有/无 MANAGE；API 33 仅 `READ_MEDIA_AUDIO`；API <30） | 分别得到 `FULL` / `MEDIA_LIBRARY_ONLY` / `NONE`；`NONE` 不启动扫描并返回 `PERMISSION` |
| **目录遍历** | 白名单、隐藏/系统目录跳过、`MAX_DEPTH`、软链成环、不可读目录 | 仅命中白名单扩展名；不陷入死循环；不可读目录记 warning 且扫描继续 |
| **元数据降级** | MMR 抛异常 / 超时 | 返回 `degrade`（标题=文件名），文件仍入库 `UNANALYZED` |
| **时长缺失** | 无 DURATION 标签 | `AudioMetadata.durationMs == 0` → `music_file.duration_ms == NULL`，不报错 |
| **差异计数** | 新增 X / 已存在 Y / 已删除 Z | 三项计数准确映射 `analysis_run.new_count/skipped_count/cleaned_count` |
| **lrc 边界** | `scan` 产出 `LrcCandidate` | 本模块**不写** `lyric` 表；候选 `origin` 正确区分 `SAME_DIR`/`EXTERNAL_DIR`（I7 由 08 测） |
| **提交事务原子性** | 单批写库中途抛错 | 该批整体回滚，无半行；`analysis_run` 不残留「运行中」孤儿（置 `ABORTED`） |
| **来源管理** | `add` 重复路径 / 非目录 / 移除来源 | 重复 → `AlreadyExists`；非目录 → `Invalid`；移除来源后已入库文件不变（扫描不重建实体） |
