# 歌曲库与标签模块 · V1.0

> 版本：V1.0
> 上游依据：`../需求文档/01-歌曲库管理.md`（主依据）、`../需求文档/04-智能标签.md`（标签体系/删除/展示）、`../需求文档/00-总览.md`（实体/代表文件/删除模型/术语）、`../需求文档/05-空状态与异常处理.md`（§3/§4/§6 空状态）
> 契约依据：`02-详细设计总纲.md`（接口、标识符、不变量、章节结构）、`03-数据层设计.md`（表结构、DAO、事务、排序/筛选 SQL —— **本模块直接复用，不再重复定义 DDL**）
> 覆盖需求：需求文档 01 全部；04 §5 §6；05 §3 §4 §6。

**锁定决策（不得冲突，本模块全程遵守）**：排序仅 **名称 / 最近播放 / 完播次数**（无拼音、无分组）；搜索仅 **歌曲 + 歌手**（标签搜索只在「分类 & 标签」页）；标签名**全局唯一**、**只增删**（不改名、不改分类）；分类下有标签不可删、标签下有歌不可删；**0 首歌的标签仍展示**；**内置分类/标签可删除**；主要分类**多选不互斥**、**预置「音乐类型 + 情绪」**；**不可用歌曲不入队**；三类删除各有确认级别（详见 §4.6）。

# 1. 模块职责与边界

## 1.1 做什么

| 职责 | 说明 |
| --- | --- |
| 列表查询与装配 | 四个浏览维度（歌曲/歌手/专辑/标签）的查询、聚合、`SongListItem` 装配 |
| 排序与筛选 | 三种排序、按名称筛选、按歌词筛选的 SQL 映射 |
| 搜索 | 歌曲（`canonical_title`）与歌手（`song_artist.artist_name`）**合并为统一不分组列表**；搜索历史 |
| 歌曲详情 | 实体信息 + 完整标签（可增删）+ 歌词状态 + **管理的文件列表** |
| 实体/文件删除 | `DeletionService` 三操作的确认级别与事务编排 |
| 标签 CRUD | 分类/标签的新建、删除保护、主要分类、批量加/减标签 |
| 封面 | `CoverRepository` 懒提取内嵌图、缓存失效、并发去重 |
| 不可用歌曲 | 置灰、点击提示、**所有入队路径过滤**（I3） |
| 空状态 | 对应 05 号文档 §3/§4/§6 的触发条件与 UI 动作 |

## 1.2 不做什么

- **不做扫描/分析**：文件入库、`analysis_status` 流转归 `04-文件扫描模块`、`05-分析与 LLM 归一化模块`（`ScanOrchestrator` / `AnalysisOrchestrator`）。本模块只消费其产出。
- **不做播放**：队列、播放模式、会话统计、入队的物理执行归 `07-播放器模块`（`QueueEngine` / `MediaSessionService`）。本模块只提供 `isPlayable` 判定与**入队前的过滤契约**（§4.10 交接点）。
- **不做歌词匹配/展示**：候选发现、匹配算法、LRC 解析归 `08-歌词模块`。本模块只读 `lyric` 关联状态并展示「已关联 / 未关联 / 文件失效」。
- **不做标签生成**：标签由 LLM 在分析阶段产出（04 号文档 §3）。本模块只做用户侧的增删与展示。
- **不做拼音/分组/标签改名**（需求已明确排除）。
- **不落库派生字段**：`isPlayable` 由可用文件数派生，绝不写库（§4.1）。

# 4. 核心流程

## 4.1 列表查询的数据装配（`SongListItem` 装配 + 避免 N+1 + `isPlayable` 派生）

**三步查询、两次批量、零 N+1**（严格遵循 03 §5.2 策略）：

```
Step 1  取实体行（一次查询，含排序/筛选/scope）
        └─ 得到 List<SongEntity>（含 entityId 列表）
Step 2  用 entityId 列表**批量**取可播性 → Map<entityId, playableCount>
Step 3  用 entityId 列表**批量**取标签（onlyMain = true）→ Map<entityId, List<TagProjection>>
        合并为 List<SongListItem>
```

```kotlin
override fun observeSongs(scope: SongScope, sort: SongSort, filter: SongFilter):
    Flow<List<SongListItem>> =
    entityRowsFlow(scope, sort, filter)                 // Step 1：@RawQuery(observedEntities=song_entity)
        .distinctUntilChanged()                         // 行集未变则不重订阅
        .flatMapLatest { rows ->
            val ids = rows.map { it.id }
            if (ids.isEmpty()) return@flatMapLatest flowOf(emptyList())
            combine(
                musicFileDao.observePlayableCounts(ids),        // Step 2
                tagRepo.observeTagsOfSongs(ids, onlyMain = true) // Step 3（I6：只取主要分类）
            ) { playableRows, tagMap ->
                val playableIds = playableRows.mapTo(HashSet()) { it.entityId }
                rows.map { e ->
                    SongListItem(
                        entityId       = e.id,
                        title          = e.canonicalTitle,
                        displayArtists = e.displayArtists,
                        artistNames    = /* 由 song_artist 批量取，见下 */ artistNameCache[e.id].orEmpty(),
                        albumName      = e.albumName,
                        albumArtist    = e.albumArtist,
                        coverCachePath = e.coverCachePath,
                        tags           = tagMap[e.id].orEmpty(),
                        isPlayable     = e.id in playableIds      // 派生，不落库
                    )
                }
            }
        }
```

**`isPlayable` 派生规则（不落库）**：
- 定义 = 实体存在**至少一条可用文件记录**（`music_file.analysis_status = 'LINKED'`）。由 §3.7 的 `observePlayableCounts` 批量聚合得到，空集 → 不可用。
- **永不写入 `song_entity`**：避免脏字段；文件增删后无需手工同步（Flow 自动重算）。
- 与 03 §5.3 一致：即 `playableCount > 0`。

**为什么不用 `LEFT JOIN + COUNT` 单查询**：可播性依赖 `music_file`、标签依赖 `entity_tag`，两者是**独立的写入源**（文件删除 vs 标签增删）。分两次批量查询 + `combine`，任一源变化都能精确触发重算，且不会因 JOIN 使排序行集膨胀。若未来数据量增大，可退化为单条 `LEFT JOIN` 聚合。

**`artistNames`**：由 `SongArtistDao` 按 `entityId IN (:ids)` 批量取（一次查询），在 `flatMapLatest` 内做一次 `groupBy`。同样每页固定次数查询。

> **N+1 反面**：禁止在 `map { e -> dao.tagsOf(e.id) }` 里逐行查询。本模块所有 `*Of(entityId)` 单行查询只允许用于详情页（单个实体）。

## 4.2 四个浏览维度

### 4.2.1 WHERE 片段（scope 决定；全部为绑定参数，无字符串拼接）

| Scope | WHERE 片段 |
| --- | --- |
| `Songs` | `1 = 1` |
| `Artist(name)` | `EXISTS (SELECT 1 FROM song_artist a WHERE a.entity_id = s.id AND a.artist_name = :name)` |
| `Album(albumName, albumArtist)` | `s.album_name IS :albumName AND s.album_artist IS :albumArtist`（`IS` 同时处理 NULL 相等） |
| `Tag(name)` | `EXISTS (SELECT 1 FROM entity_tag et WHERE et.entity_id = s.id AND et.tag_id = :name)` |
| `SearchResult(query)` | `(s.canonical_title LIKE '%'\|\|:q\|\|'%' OR EXISTS(SELECT 1 FROM song_artist a WHERE a.entity_id = s.id AND a.artist_name LIKE '%'\|\|:q\|\|'%'))` |

> 复用 03 §5「筛选映射」：多歌手歌曲**计入其涉及的每个歌手**（01 §6.3），`EXISTS` 天然满足；专辑由「专辑名 + 专辑歌手」共同确定（01 §7.4），`IS` 保证同名不同歌手区分。

### 4.2.2 各维度的聚合与查询

| 维度 | 列表查询 | 进入歌曲列表 |
| --- | --- | --- |
| **歌曲** | `observeSongs(Songs, sort, filter)` | —（本页即列表） |
| **歌手** | `observeArtists()` = 03 §3.3 `observeArtistList()`：`SELECT artist_name name, COUNT(*) songCount FROM song_artist GROUP BY artist_name ORDER BY artist_name` | `observeSongs(Artist(name), sort)` |
| **专辑** | `observeAlbums()` = §3.7 新增 `observeAlbumList()`：`GROUP BY album_name, album_artist`，`COUNT(*)` 为歌曲数，`releaseDate` 取代表文件内嵌（缺省 null） | `observeSongs(Album(albumName, albumArtist), sort)` |
| **标签** | ① `observeCategories()`（03 §3.4，带 `tagCount` 子查询）；② 进入分类 → `observeTags(categoryId)`（03 §3.4，`LEFT JOIN entity_tag` + `COUNT`，**无 `HAVING`，0 首标签保留**）；③ 标签搜索仅此页用 `searchTags(query)` | `observeSongs(Tag(name), sort)` |

> 专辑封面的取用：`MAX(s.cover_cache_path)` 只为「有一个可用封面」的确定性取值；空值由 `CoverRepository` 在某首歌上按需重建（§4.9），AlbumListItem 的封面缺失时展示占位。

## 4.3 排序与筛选（SQL 映射 + NULL 处理）

**排序映射**（复用 03 §5 并补 tie-break，保证**稳定排序**）：

| `SongSort` | ORDER BY | NULL 处理 |
| --- | --- | --- |
| `NAME` | `s.canonical_title COLLATE NOCASE ASC, s.id ASC` | 无 NULL（`canonical_title NOT NULL`）；中文按 Unicode 码位，**不做拼音** |
| `RECENT_PLAYED` | `(s.last_played_at IS NULL) ASC, s.last_played_at DESC, s.canonical_title COLLATE NOCASE ASC` | **未播放（NULL）排最后**：`last_played_at IS NULL` 为 0/1，ASC 使 0（已播放）在前 |
| `COMPLETE_COUNT` | `s.complete_count DESC, s.canonical_title COLLATE NOCASE ASC, s.id ASC` | 无 NULL（默认 0），0 次并列按名称 |

> SQLite 无 `NULLS LAST` 语法，故用 `(col IS NULL) ASC` 等价实现；与 03 §5 的「`last_played_at IS NULL, last_played_at DESC`」写法一致。
> **排序只作用于歌曲列表**，含歌曲库与各分类歌曲列表（01 §5.2）。歌手/专辑/标签**列表本身**固定按名称排序，不受 `SongSort` 影响。

**筛选映射**：

| 条件 | SQL | 语义 |
| --- | --- | --- |
| 按名称 | `AND s.canonical_title LIKE '%'\|\|:q\|\|'%'` | 子串匹配 `canonical_title`（归一化后歌名） |
| 按歌词 | `AND EXISTS (SELECT 1 FROM lyric l WHERE l.entity_id = s.id)` | **语义：过滤出「已关联歌词」的歌曲**（仅对已关联歌词的歌曲有效）。V1 **不检索歌词文本**——判定条件是「`lyric` 表中存在该实体的关联行」。**未关联歌词的歌曲被排除**。未来若需歌词全文检索，另上 FTS4/5（02 §6.3 预留）。 |

> 筛选与排序叠加时，`WHERE` 片段追加，`ORDER BY` 不变；两者可同时生效（01 §5.3）。

**实现要点**：排序项来自固定枚举，WHERE 由 scope/filter 映射，全部参数以**绑定参数**注入 —— 用 Room `@RawQuery`（`observedEntities = [SongEntity::class]`）动态拼装，**ORDER BY 子句不含任何用户输入**，无注入风险。

## 4.4 搜索（歌曲 + 歌手合并为统一不分组列表）

**范围（锁定决策）**：仅 **歌曲（按 `canonical_title`）** 与 **歌手（按 `song_artist.artist_name`）**；**标签搜索不在此页**（只在「分类 & 标签列表」页，§4.2）。结果**不分组、统一列表**（01 §9.2）。

**两路结果合并为一个 Flow（稳定排序 + 去重）**：

```kotlin
private val SEARCH_COMPARATOR =
    compareBy<SongListItem> { it.title.lowercase() }   // 主序：歌名（NOCASE 语义）
        .thenBy { it.entityId }                        // 次序：id，保证确定性

override fun observeSearch(query: String): Flow<List<SongListItem>> =
    if (query.isBlank()) flowOf(emptyList())
    else combine(
        entityRowsFlow(SearchScope.ByTitle(query), SongSort.NAME),
        entityRowsFlow(SearchScope.ByArtist(query), SongSort.NAME)
    ) { byTitle, byArtist ->
        val ids = (byTitle + byArtist).map { it.id }.distinct()
        assembleSongListItems(ids)                      // 复用 §4.1 的批量装配
            .distinctBy { it.entityId }                 // 同一首歌命中两类只出现一次
            .sortedWith(SEARCH_COMPARATOR)              // 稳定排序
    }.flowOn(Dispatchers.IO)
```

- **"同一个 Flow 里合并"**：`combine` 两路 Room Flow（`song_entity` 的标题匹配、`song_artist` 的歌手匹配），各自变化都会重算；合并后再走一遍 §4.1 的批量装配（标签/可播性），避免 N+1。
- **稳定排序**：`SEARCH_COMPARATOR` 为全序（歌名 + entityId 双键），合并顺序无关，结果确定。**不分组**：两类结果直接混排。
- **可选的“歌名命中优先”**：若产品希望歌名命中的更靠前，可在合并前对每条打 `rank`（title 命中=0，仅歌手命中=1），排序改 `compareByDescending{...}`；默认不启用（需求只要求不分组统一列表）。
- **等价简化实现**：也可用单条 OR 查询（§4.2.1 `SearchResult`）天然去重、单 Flow、稳定；本模块选合并实现以保留“两类来源、将来可分别排序”的扩展点，并避免 OR + EXISTS 的查询计划波动。

**搜索历史**：

```kotlin
interface SearchHistoryStore {                 // 位于 :core:data，实现用 DataStore
    val history: Flow<List<String>>            // 最近 N 条（N = 10），去重、最新的在前
    suspend fun record(query: String)
    suspend fun clear()
}
```

| 方案 | 取舍 |
| --- | --- |
| **DataStore（推荐）** | 只需有序小列表、无需索引/关联/查询 → 不占 Room；跨进程重启保留（符合「展示最近搜索词」体验）；实现为单个 `String`（JSON 数组）或 JSON 字符串，容量小。新增 DataStore key `search_history`（与 03 §6 并列，属扩展）。 |
| 仅内存 | 最简单，但**进程被杀即丢**；只能在同一会话内有效，与需求「展示最近搜索词」的持久预期不符。 |
| Room | 支持 LIKE/时间排序，但为一个 10 条的字符串列表建表纯属过度设计，且写入放大。**不采纳**。 |

**结论**：搜索历史用 **DataStore（Preferences）**，key = `search_history`（JSON 数组字符串，上限 10 条）；`record` 去重后前插，`clear` 清空（01 §9 / 页面设计 §4「可清空」）。**不进 Room**。

## 4.5 歌曲详情（实体信息 + 完整标签 + 歌词状态 + 管理的文件列表）

```kotlin
override fun observeSongDetail(entityId: Long): Flow<SongDetail> = combine(
    songDao.observeById(entityId),                                   // 实体信息 + 统计
    songArtistDao.observeArtistsOf(entityId),                        // 全署名
    tagRepo.observeTagsOfSongs(listOf(entityId), onlyMain = false),  // **完整标签**（不折叠）
    lyricDao.observeLyric(entityId),                                 // 歌词关联（null=未关联）
    musicFileDao.observeFiles(entityId)                             // 文件列表（03 §3.2，size DESC）
) { entity, artists, tagMap, lyric, files ->
    SongDetail(
        entity = entity,
        artists = artists,
        tags = tagMap[entityId].orEmpty(),
        lyric = lyric,
        files = files.map { it.toFileItem() },
        representativeFileId = files.firstOrNull { it.isRepresentative }?.id
    )
}
```

- **实体信息**：封面（`coverCachePath`）、名称、歌手、专辑、发行日期（无需在详情页展示时长 UI；时长仅在播放页）。
- **完整标签**：`onlyMain = false`（04 §6.2 / 页面设计 §3.5）；支持增删（§4.7 单曲增删路径）。
- **歌词状态**：`lyric == null` → 「未关联歌词」（一期无手动选择入口）；`lyric != null` 时由 VM 用 `StorageSource.exists(lyric.path)` 判定 → 失效则「歌词文件已失效」+「移除关联」（05 §5）。**文件存在性判定在 VM 层**，Repository 不访问文件系统读取歌词。
- **管理的文件列表**：路径 / 大小 / 格式 /（可选）时长；**代表文件标记**（`isRepresentative`，置顶并打标）；每行支持「移除文件」「物理删除文件」，支持多选批量（页面设计 §9.4）。
- **操作**：播放（`isPlayable=false` 时置灰并提示「无可用文件」）、添加到队列、下一首播放、删除歌曲。

## 4.6 `DeletionService` 三操作的完整编排

**三类删除确认级别总表（锁定决策，源自 00 §5）**：

| 操作 | 前置校验 | 确认级别 | 后置 | 磁盘 |
| --- | --- | --- | --- | --- |
| `deleteSong(entityId)` | 无（空/非空均可） | **有文件才二次确认**；无文件直接删除 | 级联清 `music_file`/`song_artist`/`entity_tag`/`lyric`/`play_history`/`queue_item`；`playback_state.current_queue_item_id` → SET NULL | **不动**（I8） |
| `unlinkFile(fileId)` | fileId 存在 | 明显提示；**若为最后一个文件，额外提示「将同时删除该歌曲」** | 删该 `music_file` 行；实体无文件→按删实体处理；否则**重选代表文件 + 刷新展示字段** | 保留 |
| `deleteFilePhysically(fileId)` | fileId 存在 | **必须确认**（破坏性、不可恢复） | **先删磁盘**（失败即中止，库不变）→ 事务内执行 `unlinkFile` 同款逻辑 | **永久删除** |

### 4.6.1 `deleteSong`

```
deleteSong(entityId):
  impact = songDeletionImpact(entityId)                   # 有文件？标签数？歌词？在队列数？
  # UI：impact.fileCount == 0 → 直接删除；> 0 → 二次确认（展示将级联删除的关联，磁盘不动）
  事务（03 §4.4「删除实体」）:
    DELETE FROM song_entity WHERE id = entityId           # 外键级联清空所有归属行
    # playback_state.current_queue_item_id 被 ON DELETE SET NULL 置空
  返回 Done
```

### 4.6.2 `unlinkFile`

```
unlinkFile(fileId):
  entityId = file.entity_id
  fileCount = musicFileDao.fileCountOf(entityId)
  isLast = (fileCount == 1)
  # UI：明显提示；isLast → 额外提示「将同时删除该歌曲」
  事务（03 §4.4「移除文件」）:
    DELETE FROM music_file WHERE id = fileId
    if 实体已无文件:  deleteSong(entityId)                # 顺带删实体 → 返回 SongDeleted
    else:             reelectRepresentative(entityId)     # 03 §4.2
                      refreshDisplayFields(entityId)       # 03 §4.3：重取专辑/发行日期，cover_cache_path 置空
  返回 Done / SongDeleted
```

### 4.6.3 `deleteFilePhysically`（**先删磁盘**，03 §4.4 顺序要求）

```
deleteFilePhysically(fileId):
  file = musicFileDao.byId(fileId) ?: return NotFound
  # UI：必须确认（破坏性）
  ok = storage.delete(file.path)                          # ① 先删磁盘
  if (!ok) return DiskDeleteFailed(file.path, cause)      # 失败 → 中止，数据库不变
  事务: 同 unlinkFile 的 ②（删行 + 重选代表 + 刷新展示 / 或删实体）
  # 若删的是代表文件 → 自动回退次大（I2/I11）
  返回 Done / SongDeleted
```

### 4.6.4 与 03 §4.4 的对接

- 三个操作**全部**下沉到 03 §4.4 定义的 `@Transaction` 写入口：`unlinkFile` / `deleteFilePhysically` / `deleteSong`。`DeletionService` 只负责**磁盘顺序、确认级别判定、结果封装**，**不自行拼 SQL**。
- **物理删除顺序不可颠倒**：先 `StorageSource.delete` 再改库；否则「库已删、磁盘残留」，用户失去清理入口。
- **删除实体不触碰磁盘**（I8）：`@Transaction` 只删表行。

### 4.6.5 删除后 UI 需要刷新什么

因所有列表来自 Room `Flow`，**数据自动重算**；需关注的是「导航/播放」侧的显式处理：

| 受影响项 | 刷新来源 / 动作 |
| --- | --- |
| 歌曲列表 / 分类歌曲列表 | `observeSongs` Flow 自动移除该行（删实体）或 `isPlayable` 翻转（移除文件后仍可用） |
| 标签列表的 `songCount` | `entity_tag` 级联删除 → `observeTags` Flow 自动重算（0 首标签仍展示） |
| 标签删除保护状态 | `songCountOfTag` 变化 → 删除按钮可用性随之更新 |
| 歌手/专辑列表 | 聚合（`GROUP BY`）重算；计数归零的歌手/专辑自然消失 |
| 播放队列 | `queue_item` 被级联删除 → 队列页 Flow 刷新；`playback_state.current_queue_item_id` 置空 |
| **当前播放项被删** | `QueueEngine` 检测当前 `queue_item_id` 失效 → 切下一首或停止（**交接 07**） |
| 歌曲详情页 | 删实体 → 页面返回上级；移除/物理删文件 → 文件列表 Flow 刷新、代表文件标记移位；代表变更 → 封面重建（§4.9） |
| 封面 | 代表变更使 `cover_cache_path` 置空 → `CoverRepository` 下次访问重建（§4.9） |

## 4.7 标签管理（CRUD、删除保护、主要分类、批量）

### 4.7.1 新建分类 / 新建标签

```
addCategory(name):                       # 幂等：同名存在 → 返回已有 id
  事务: INSERT category(name, is_main=0, is_builtin=0, sort_order=MAX+1)
  返回 id

addTag(categoryId, name):
  name 已存在（全局唯一，I5）:
    → ReuseExisting(name, existingCategoryId, existingCategoryName)   # UI 引导复用（01 §8.2）
  否则:
    事务: INSERT tag(name, category_id=categoryId, is_builtin=0) → Added(name)
  name 非法 / 分类不存在 → Rejected(reason)
```

> **预置**：数据库首次创建时 seed —— 分类 `音乐类型`(is_main=1)、`情绪`(is_main=1)、`场景`(0)、`主题`(0)（is_builtin=1）与示例标签。**内置分类/标签可删除**（删除保护只按「有无标签/有无歌曲」判定，与 `is_builtin` 无关）。

### 4.7.2 删除保护（I12）

```
deleteTag(name):
  n = songCountOfTag(name)
  n > 0 → Blocked(n)                 # 「该标签下还有歌曲，无法删除」
  否则 事务: DELETE FROM tag WHERE name=name（级联清 entity_tag 悬挂行）→ Deleted

deleteCategory(id):
  n = tagCountOfCategory(id)
  n > 0 → Blocked(n)                 # 「该分类下还有标签，无法删除」
  否则 事务: DELETE FROM category WHERE id=id → Deleted
```

- **0 首歌的标签仍展示、可由用户手动删除**（01 §8.3 / 04 §5.3）：`observeTags` 用 `LEFT JOIN`（无 `HAVING`），删除入口仅受「有歌不可删」约束。
- 删除保护命中 → `FailureKind.CONFLICT`（02 §8），UI 说明原因并禁用操作。

### 4.7.3 主要分类设置（多选、不互斥）

```
setMainCategory(id, isMain):  UPDATE category SET is_main = :isMain WHERE id = :id
```

- **多选、不互斥**：不做「单选清他项」，可同时把多个分类设为主要（01 §8.7 / 04 §2.6）。预置 `音乐类型 + 情绪` 为 `is_main=1`，用户可修改。
- 主要分类变化 → 歌曲列表的标签区随之变化（I6：列表标签 ⊆ 主要分类下标签）。`observeTagsOfSongs(ids, onlyMain=true)` 依赖 `category.is_main`，其变化会触发列表 Flow 重算。

### 4.7.4 批量给歌曲加标签 / 从标签移除歌曲

```
attachTags(entityIds, tagNames):        # 批量加标签（歌曲列表多选 → 添加到标签）
  事务: 对每个 entityId × 每个 tagName:
         tag 不存在 → 跳过或先建（由 UI 决定：新建 / 复用）
         INSERT OR IGNORE entity_tag(entity_id, tag_id, created_at)

detachTags(entityIds, tagNames):        # 批量移除（歌曲列表 / 标签歌曲列表多选）
  事务: DELETE FROM entity_tag WHERE entity_id IN (:ids) AND tag_id IN (:tags)
```

- **I6 提醒**：批量加的标签若属**非主要分类**，列表页不展示（只进详情/播放页），但数据已写入 —— 这是预期行为，UI 需在列表标签区注明「仅在详情可见」或直接不提示。

## 4.8 标签删除的调用路径与数据层对接

| 路径 | 入口 | 调用 | 说明 |
| --- | --- | --- | --- |
| 从标签入口删除（单条/批量） | 标签 → 标签歌曲列表（`SongScope.Tag`） | `detachTags(selectedEntityIds, listOf(tagName))` | tag 固定为当前标签（01 §8.6 / 04 §5.1） |
| 从歌曲页面删除标签 | 歌曲详情标签区 → 删除 | `detachTags(listOf(entityId), listOf(removedTag))` | 04 §5.2 |
| 从歌曲页面增加标签 | 歌曲详情标签区 → 增加 | `attachTags(listOf(entityId), listOf(newTag))` | 复用已有（`searchTags` 提示）或新建（`addTag`） |
| 批量添加到标签 | 歌曲列表多选 | `attachTags(selectedEntityIds, listOf(tag))` | 页面设计 §9.4 |

> **注意术语边界**：这两条路径是「**歌曲与标签的关联增删**」，**不是删除标签本身**。删除标签本体是 §4.7.2 的 `deleteTag(name)`（受「有歌不可删」保护）。

## 4.9 封面懒加载（`CoverRepository`）

**来源**：专辑封面来自音乐文件内嵌图（01 §7.2）；实体展示封面取**代表文件**内嵌图（00 §3）；缓存路径存 `song_entity.cover_cache_path`（02 §4 决策 4）。

```kotlin
private val coverMutex = KeyedMutex<Long>()          // 按 entityId 的并发去重闩
private val coverDir get() = File(context.cacheDir, "covers").apply { mkdirs() }

override suspend fun ensureCover(entityId: Long): File? {
    val entity = songDao.byId(entityId) ?: return null
    entity.coverCachePath?.let { if (File(it).exists()) return File(it) }   // 命中（含缓存被清理后自动重建）
    return coverMutex.withLock(entityId) {
        // 双检：进入锁后可能已被其它协程写好
        val fresh = songDao.byId(entityId) ?: return@withLock null
        fresh.coverCachePath?.let { if (File(it).exists()) return@withLock File(it) }
        val rep = musicFileDao.representativeOf(entityId) ?: return@withLock null   // 无文件 → 无封面
        val bytes = metadataReader.embeddedPictureBytes(FileRef(rep.path, rep.fileName, rep.size, 0))
                    ?: return@withLock null
        val out = File(coverDir, "cover_${entityId}_${rep.id}_${bytes.size}.jpg")
        out.writeBytes(bytes)
        songDao.setCoverPath(entityId, out.absolutePath)
        out
    }
}
```

**要点**：

- **提取来源 = 代表文件**（`representativeOf`）。无代表文件（不可用歌曲）→ 返回 `None`（占位图）。
- **缓存失效时机**（每次都先查 DB 路径 + 文件存在性，双保险）：
  1. **代表文件变更 / 文件增删**：03 §4.3 `refreshDisplayFields` 把 `cover_cache_path` 置空（本模块 `unlinkFile` / `deleteFilePhysically` 亦显式 `invalidateCover`）→ 下次访问重建（I11）。
  2. **缓存被系统清理 / 用户清缓存**：DB 有路径但文件不存在 → 存在性检查失败 → 重建。
  3. 文件名含 `rep.id` 与 `bytes.size` → 内容变化即换名，杜绝脏读。
- **并发去重**：`KeyedMutex<Long>`（按 `entityId`）+ **锁内双检**，保证同一实体并发请求只提取一次；`LazyColumn` 快速滚动大量 `observeCover` 请求也不会重复解码。
- **交给 Coil**：`observeCover` 返回 `Ready(File)`，UI 直接把 `File` 作为 Coil 的 `data`（Coil 磁盘缓存可再叠一层）。
- **扩展**：需给 `MetadataReader` 增加 `embeddedPictureBytes(ref): ByteArray?`（02 §5.2 目前只有 `hasEmbeddedPicture`）；这是**能力补充**，与既有接口不冲突。

## 4.10 不可用歌曲的完整处理（交接 07）

**定义（00 §1.6 / 01 §3.5）**：实体无任何可用文件 → **不可用歌曲**。

| 环节 | 处理 |
| --- | --- |
| 列表 | `isPlayable=false` → 行**置灰**并打「不可用」标记；`artistNames`/封面等仍展示 |
| 点击 | **不播放、不入队**，仅提示「无可用文件」（05 §3） |
| 入队过滤（I3） | **所有**入队路径共享同一道闸：新建队列（`playFromList`）、追加（`appendToQueue`）、下一首播放（`insertNext`）—— 07 号文档必须在入队前用 `getAvailableFileIds` / `isPlayable` 过滤 |
| 播放时文件缺失 | `NOT_FOUND` → 清理该 `music_file` 记录；代表文件被删 → 回退次大；实体再无文件 → 提示「是否删除？」（删除 / **保留并标记不可用**）（05 §6） |

**与 07 号文档的交接契约（关键）**：

```kotlin
// 07 的 QueueEngine 在构造待入队集合时必须调用：
val playable = libraryRepository.getAvailableFileIds(candidateIds)   // 一次批量
val enqueueSet = candidateIds.filter { it in playable }              // I3 闸门
```

- **单一判定源**：可播性只由 `LibraryRepository.getAvailableFileIds`（= `playableCounts > 0`）决定，07 不得自行读 `music_file`。
- **「全部播放(N)」**：`N` 展示当前列表歌曲总数，但**实际入队仅可播放子集**；若列表全为不可用，入队为空并提示。
- **不可用→可用**：文件被重新挂靠后（`AnalysisOrchestrator.attach`）Flow 自动令 `isPlayable` 翻真，无需手动刷新。

## 4.11 空状态与异常（对应 05 号文档 §3 / §4 / §6）

| 需求条目 | 触发条件（技术判定） | UI 动作 |
| --- | --- | --- |
| 05 §3 库为空 | `observeSongs(Songs)` 发射空列表 | 「音乐库还是空的」+「扫描音乐」→ 导航至 `我的 → 文件扫描` |
| 05 §3 搜索无结果 | `observeSearch(q)` 空且 `q` 非空 | 「未找到与"xxx"相关的内容」+ 清空 / 修改关键词 |
| 05 §3 筛选无结果 | 有 `SongFilter`（titleQuery/hasLyricOnly）且结果空 | 「没有符合筛选条件的歌曲」+「清除筛选」（清空 filter，保留 scope/sort） |
| 05 §3 不可用歌曲 | `isPlayable == false` | 置灰 / 标记；点击只提示「无可用文件」，不播放、不入队 |
| 05 §4 分类下无标签 | `observeTags(categoryId)` 空 | 「该分类还没有标签」+「新建标签」（该分类页可建） |
| 05 §4 标签下无歌曲 | `TagListItem.songCount == 0` | **标签照常展示、数量 0**；进入后「该标签下还没有歌曲」 |
| 05 §4 歌曲无任何标签 | 详情 `tags` 空且列表 `tags` 空 | 列表页**不显示标签区**；播放页显示「暂无标签」 |
| 05 §6 播放时文件不存在 | `StorageSource.exists(path) == false` | 「文件不存在或已被移动」→ 清理记录；代表被删→回退次大继续播；实体无文件→「该歌曲已无可用文件，是否删除？」（删除 / 保留并标记不可用） |
| 05 §6 列表中已不可用 | `isPlayable == false` | 置灰 / 标记（同 §3） |

> **区分「筛选无结果」与「库为空」**：库为空 → `observeSongs(Songs, _, filter=空)` 空；筛选无结果 → 带 filter/scope 空但整体库非空。VM 依据 `scope == Songs && filter == 空` 判定，文案与动作不同。

# 5. 状态与边界条件

## 5.1 不变量映射（引用 02 §9）

| # | 不变量 | 本模块的保证点 |
| --- | --- | --- |
| **I3** | 实体无文件 ⇒ 不可用；**不可用歌曲不得入队** | `isPlayable` 派生（§4.1）；入队闸门 `getAvailableFileIds`（§4.10，交接 07） |
| **I5** | 标签名全局唯一且必属一个分类 | `tag.name` 主键（03 §2.2）；`addTag` 重名 → `ReuseExisting`（§4.7.1） |
| **I6** | 列表标签 ⊆ 主要分类下标签 | `observeTagsOfSongs(ids, onlyMain = true)`；详情用 `onlyMain = false`（§4.1 / §4.5） |
| **I8** | 删除实体不触碰磁盘 | `deleteSong` 仅走 `@Transaction` 删表（§4.6.1 / 03 §4.4） |
| **I11** | 代表文件变更 → 专辑/封面等展示信息切换 | `reelectRepresentative` + `refreshDisplayFields` + 封面重建（§4.6 / §4.9） |
| **I12** | 分类下有标签不可删；标签下有歌不可删 | `deleteCategory` / `deleteTag` 保护（§4.7.2） |
| I2 | 每实体至多 1 代表文件 | `unlinkFile` 后重选（§4.6.2 / 03 §4.2） |
| I4 | `LINKED` 文件不可重分析 | 本模块不触发重分析（职责边界 §1.2） |

## 5.2 边界条件

| 场景 | 处理 |
| --- | --- |
| 标签 0 首歌 | **仍展示**（`LEFT JOIN` 无 `HAVING`）；删除入口可用（无歌曲） |
| 分类 0 个标签 | 展示；删除入口可用（无标签） |
| 内置分类/标签 | 仅 `is_builtin` 展示标注；**删除保护与内置无关**，可删 |
| 主要分类被清空（全不设为主要） | 允许；列表标签区为空（不显示标签区，同「歌曲无标签」） |
| 主要分类含多个 | 允许多选（不互斥）；列表取并集标签 |
| 同名标签出现在不同分类 | **不可能**（名称全局唯一） |
| 专辑同名不同歌手 | 视为不同专辑（`GROUP BY album_name, album_artist`；`IS` 处理 NULL） |
| 专辑未知名/未知歌手 | `album_name IS NULL` → 不进专辑列表（`WHERE album_name IS NOT NULL`），专辑维度不展示 |
| 从未播放的歌曲排序（最近播放） | `last_played_at IS NULL` → 排最后 |
| 歌名为空/纯空白 | `canonical_title` 非空约束；分析阶段保证 |
| 搜索关键词含 `%`/`_` | LIKE 通配符转义（`ESCAPE`），避免误匹配 |
| 删除后同一 `entityKey` 重新分析 | 生成**新实体**（不重建）；本模块无感 |
| 移除最后一个文件 | 顺带删除实体 → 返回 `SongDeleted`；UI 关闭详情页 |
| 物理删除非代表文件 | 代表不变；`isPlayable`、封面不变 |
| 物理删除磁盘失败 | **中止，数据库不变**（`DiskDeleteFailed`） |

# 6. 错误处理（映射 02 §8 `FailureKind`）

| 场景 | `FailureKind` | 自动恢复 | 用户可见动作（文案由 11 维护） |
| --- | --- | --- | --- |
| 删除保护命中（有歌的标签 / 有标签的分类） | `CONFLICT` | 否 | 说明原因，禁用操作 |
| 物理删除磁盘失败 | `IO` | 否 | 「删除失败，请重试」；库保持原样 |
| 目标实体/文件不存在（并发删除） | `NOT_FOUND` | 否 | 静默刷新列表（`NotFound`） |
| 新建标签重名 | `CONFLICT` | 否 | 引导复用（`ReuseExisting`，非错误） |
| 新建分类重名 | `CONFLICT` | 否 | 返回已有 id，提示「已存在」 |
| 输入非法（空名/超长/特殊字符） | `PARSE` | 否 | 内联校验提示 |
| 无文件系统权限（封面提取/文件存在性校验） | `PERMISSION` | 否 | 降级：展示占位图；沿用 05 §7 权限引导 |

> 本模块**不硬编码用户文案**：`DeletionService` / Repository 只返回 sealed 结果或抛出带 `FailureKind` 的 `AppError`，文案在 11 统一映射。

# 7. 性能与并发

| 关注点 | 措施 |
| --- | --- |
| **避免 N+1** | 列表装配固定 3~4 次批量查询（实体行 / 可播性 / 标签 / 歌手名），与列表长度无关（§4.1） |
| **不做分页** | V1 百~千级，`Flow<List<...>>` + `LazyColumn`（03 §5.1）；超万级再上 Paging 3 |
| **排序在 SQL** | `ORDER BY` 由 SQL 完成，禁止拉全量进内存排序（03 §5） |
| **Flow 去抖** | `observeSongs` 对实体行 `distinctUntilChanged`，避免无关重算导致重订阅 |
| **线程** | 查询/装配在 `Dispatchers.IO`；Room `suspend`/`Flow` 自调度（02 §7） |
| **写事务** | 所有跨表写（删实体、移除文件、标签增删、主要分类）包在 `@Transaction`（02 §7「写事务」/ 03 §4） |
| **单写者** | `music_file.analysis_status` 只由 `AnalysisOrchestrator` 改；本模块**只读** |
| **封面并发** | `KeyedMutex<Long>`（按 entityId）+ 锁内双检，杜绝重复解码（§4.9） |
| **封面缓存** | 落 `cacheDir/covers`，文件名含 `rep.id`+`size`；DB 存路径 + 存在性校验 |
| **大列表刷新粒度** | 标签变化仅重算受影响实体的标签 Flow（`IN (:ids)` 跟踪查询），不重取全表 |
| **搜索** | `LIKE` + `canonical_title`/`artist_name` 索引；数据量大再上 FTS4/5（02 §6.3 预留） |
