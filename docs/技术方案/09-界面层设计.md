# 1. 模块职责与边界

**做**

- 单 Activity + Navigation Compose 的**导航图**与路由契约、返回键优先级。
- 每个屏幕的 `XxxScreen`（Composable）与 `XxxViewModel`（`StateFlow<XxxUiState>` + `Flow<XxxEvent>`）。
- **统一交互三件套**：`SongRow`、`ActionSheet`（底部操作面板）、`MultiSelectState`（多选态）。
- 常驻 **mini 播放条**与**底部导航**的 `Scaffold` 布局与 insets 避让。
- 列表的通用能力（排序 / 筛选控件、加载与空状态占位、`LazyColumn` key 策略、Coil 封面）。
- 把 `../需求文档/05-空状态与异常处理.md` 的每条空状态**落位到具体屏幕**。
- 事件与副作用约定（状态用 `StateFlow`、一次性事件用 `Channel`、对话框与二次确认）。
- 可访问性要点与 Compose UI Test 要点。

**不做**

- 数据查询与事务（属 `:core:data`，界面层只消费 Repository 的 `Flow`）。
- 播放控制实现（属 `:core:playback`，界面层只调 `PlaybackController`，见 `07`）。
- LLM 调用与文件 IO（属 `:core:llm` / `:core:storage`）。
- 用户可见文案的**定义**（统一在 `11-错误处理与可观测性.md` 维护，界面层只做 `FailureKind → UiMessage` 的引用与渲染）。

**依赖**（严格单向，禁止反向依赖与 feature 间依赖，见 `02 §2`）

```
feature:* ─→ core:ui, core:playback, core:data, core:llm, core:storage, core:common
:app      ─→ 所有 feature:*（仅用于导航图与 DI 聚合）
```

> `feature:*` 之间**不互相依赖**：跨页导航通过 `NavController` 的**路由**发起，而不是直接引用对方 Composable。

## 3.2 逐屏清单（数据来源 / UiState / 事件）

### 3.2.1 音乐库 · 歌曲 `LibrarySongsScreen`

- **数据来源**
  - `LibraryRepository.observeSongs(SongScope.Songs, sort, filter): Flow<List<SongListItem>>`
    （列表行内含 `coverCachePath / title / displayArtists / albumName / tags(主要分类) / isPlayable`
    —— 字段名以 `06 §3.1` 的 `SongListItem` 为准，此处原写 `coverModel / album` 与实现不符）
  - 排序偏好：`SettingsRepository.sortPreference: Flow<SongSort>`（DataStore）
  - 当前曲目高亮：`PlaybackController.state: StateFlow<PlaybackUiState>`
- **UiState 字段**：`listState: ListUiState<SongListItem>`、`totalCount: Int`（`全部播放(N)`）、`sort: SongSort`、`filter: SongFilter`、`multiSelect: MultiSelectState`、`actionSheet: ActionSheetModel?`、`confirmation: ConfirmRequest?`、`nowPlayingId: Long?`
- **事件（`LibrarySongsEvent`）**：`OpenSongDetail(entityId)`、`OpenQueue`、`NavigateToScan`、`ShowMessage(UiMessage)`
- **交互**：行体点击=播放 / 多选态=勾选；行内快捷动作 `＋ 添加到队列`；行尾 `⋯` → 操作面板（7 项全集）；长按=进入多选；表头 `全部播放(N)` / 排序 / 筛选。

### 3.2.2 音乐库 · 歌手 `LibraryArtistsScreen`

- **数据来源**：`LibraryRepository.observeArtists(): Flow<List<ArtistListItem>>`（`name`、`songCount`）
- **UiState**：`listState: ListUiState<ArtistListItem>`
- **事件**：`OpenArtist(name)`（**是歌手名，不是 id** —— 见 `§3.1` 的偏离说明）
- **交互**：整行进入歌手歌曲列表；**行尾无 `⋯`**（纯导航入口，无批量语义，见 `页面设计` §9.4）。

### 3.2.3 音乐库 · 专辑 `LibraryAlbumsScreen`

- **数据来源**：`LibraryRepository.observeAlbums(): Flow<List<AlbumListItem>>`（`coverModel`、`albumName`、`albumArtist`、`releaseDate`、`songCount`）
- **UiState**：`listState: ListUiState<AlbumListItem>`
- **事件**：`OpenAlbum(albumName, albumArtist)`
- **交互**：整行进入专辑歌曲列表；**行尾无 `⋯`**。

### 3.2.4 音乐库 · 标签 = 分类 & 标签页 `CategoriesScreen`

- **数据来源**
  - `TagRepository.observeCategories(): Flow<List<CategoryListItem>>`（`id`、`name`、`isMain`、`tagCount`）
  - 标签搜索：`TagRepository.searchTags(query): Flow<List<TagListItem>>`（**仅此页可用**）
- **UiState**：`categories: List<CategoryListItem>`、`searchQuery: String`、`tagResults: List<TagListItem>`、`isSearching: Boolean`、`newCategoryDialog: Boolean`、`confirmation: ConfirmRequest?`
- **事件（`CategoriesEvent`）**：`OpenCategory(categoryId)`、`OpenTagSearchResult(tagName)`、`ShowMessage(UiMessage)`、`ReuseExistingTagPrompt(categoryId)`
- **交互**：分类行点击进入分类下标签列表；行尾 `⋯` → `设为/取消主要分类`、`删除分类`（有标签则灰置，`I12`）；顶部「搜索标签」；`新建分类` 对话框。

### 3.2.5 某分类下标签列表 `CategoryTagsScreen`

- **数据来源**：`TagRepository.observeTags(categoryId): Flow<List<TagListItem>>`（`name`、`songCount`、`isBuiltin`）
- **UiState**：`categoryName: String`、`listState: ListUiState<TagListItem>`、`multiSelect: MultiSelectState`（勾选=标签名）、`newTagDialog: Boolean`、`confirmation: ConfirmRequest?`
- **事件**：`OpenTag(tagName)`、`ShowMessage(UiMessage)`
- **交互**：行体=进入标签歌曲列表；行尾 `⋯` → `删除标签`；长按=进入多选；**支持多选删除标签**，受「标签下有歌不可删」保护的行不可选。

### 3.2.6 歌手 / 专辑 / 标签歌曲列表（`ArtistSongsScreen` / `AlbumSongsScreen` / `TagSongsScreen`）

- **数据来源**：`LibraryRepository.observeSongs(SongScope.Artist/Album/Tag, sort, filter)`
- **与歌曲库差异**
  - `SongScopeHeader` 显示来源（歌手名 / 专辑名 / 标签名）与 `全部播放(N)`。
  - `TagSongsScreen` 的操作面板**裁剪**为：`播放 / 下一首播放 / 添加到队列 / 查看歌曲详情 / 多选 / 从「标签」移除`（该标签特有的批量移除）；不提供删除歌曲。
  - `SongScope` 传入 `PlaybackController.playFromList`，队列来源可追溯（`02 §3.2`）。

### 3.2.7 搜索 `SearchScreen`

- **数据来源**
  - 历史：`SettingsRepository.searchHistory: Flow<List<String>>`（DataStore 的 `search_history` key，见 `03 §6`）
  - 结果：`LibraryRepository.observeSearch(query): Flow<List<SongListItem>>`（**歌曲名 + 歌手名统一列表，不分组**）。签名以 `06 §3.3` 为准 —— 此前本文写成了 `search(query)`，与模块文档不一致。
- **UiState**：`query: String`、`history: List<String>`、`resultState: ListUiState<SongListItem>`、`showHistory: Boolean`（query 为空时）、`multiSelect: MultiSelectState`、`actionSheet: ActionSheetModel?`
- **事件**：`OpenSongDetail(entityId)`、`OpenQueue`、`ShowMessage(UiMessage)`
- **交互**：进入自动聚焦；点击行=播放（`用当前结果新建队列`）；行内快捷 `＋`；行尾 `⋯` 同歌曲库；**支持多选，批量仅「加入队列」**；标签搜索不在此页。

### 3.2.8 我的 `MineScreen`

- **数据来源**
  - 权限状态：`StorageSource.canWrite(): Boolean`（启动时求值）
  - 来源：`ScanSourceDao.observeSources(MUSIC)`
  - 上次扫描：`SettingsRepository.lastScanAt: Flow<Long?>`
- **UiState**：`permissionGranted: Boolean`、`musicSourceCount: Int`、`lastScanAt: Long?`
- **事件（`MineEvent`）**：`RequestAllFilesPermission`、`OpenScan`、`OpenAnalysis`、`OpenLyricDirs`、`OpenRecentPlayed`、`OpenSettings`、`OpenAbout`
- **交互**：固定区块入口（文件扫描 / 最近分析记录 / 外部歌词目录 / 最近播放 / 设置 / 关于）。

### 3.2.9 文件扫描 `ScanScreen`

- **数据来源**：`ScanOrchestrator.state: StateFlow<ScanState>`（`IDLE→SCANNING→DIFFING→AWAITING_USER→COMMITTING→ANALYZING→DONE/DISCARDED`，见 `02 §6.2`）、`ScanSourceDao.observeSources(MUSIC)`
- **来源选择（按 QQ 音乐的真机形态定）**：主按钮走**一键扫描** —— 把常见音乐目录里实际存在的批量加成 `MUSIC` 来源，用户不必先手选目录；**自定义扫描**是底部次入口，进应用内目录浏览器。需求见 `../需求文档/01-歌曲库管理.md` §2.4
- **扫描设置**：底部次入口，放两条过滤规则（文案以 `../需求文档/01-歌曲库管理.md` §2.5 为唯一来源）：`不扫描短于 60 秒的音频` / `不扫描小于 100 KB 的文件`，各自可关；说明文案 `只影响新扫描，已入库的文件不受影响`
- **UiState**：`permissionGranted`、`sources: List<ScanSourceEntity>`、`phase: ScanPhase`、`discoveredCount: Int`、`diff: ScanDiff?`（`newCount / skippedCount / cleanedCount`）、`foundTotal: Int`、`error: AppError?`
- **事件（`ScanEvent`）**：`RequestAllFilesPermission`、`RequestAudioPermission`、`NavigateToAnalysis(runId)`、`ShowMessage(UiMessage)`
- **交互**：`选择音乐来源`、`开始扫描`、`取消`、`分析并添加`、`放弃`、`重新扫描`。

### 3.2.10 最近分析记录 `AnalysisRunScreen`

- **数据来源**
  - 摘要：`AnalysisRunDao.latest(): AnalysisRunEntity?`（`suspend`；`newCount/skippedCount/cleanedCount/analyzedOk/failedCount`）
  - 文件清单：`AnalysisRunDao.observeRunFiles(runId): Flow<List<RunFileRow>>`（`fileName`、`status`、`linkedEntityTitle`、`errorText`）
  - 进度：`AnalysisOrchestrator.analyzePending(runId): Flow<AnalysisProgress>`（事件**逐文件**上报（`AnalysisProgress.FileUpdated` 的 `status`），一批文件只是一次传输；「正在分析」的语义是**当前批次**，429 退避期间该文件保持 `ANALYZING`、不计失败）
- **UiState**：`summary: AnalysisSummary`、`listState: ListUiState<RunFileRow>`、`isAnalyzing: Boolean`、`progress: Float?`、`multiSelect: MultiSelectState`（勾选=fileId）、`actionSheet: ActionSheetModel?`、`confirmation: ConfirmRequest?`
- **事件**：`OpenSongDetail(entityId)`、`ShowMessage(UiMessage)`
- **交互**：行尾 `⋯` → `重试分析`（仅 FAILED/UNANALYZED）/ `移除记录` / `物理删除文件`；**支持多选**（重试分析 / 移除记录 / 物理删除）。
- **文件行状态文案**（Phase 4-4 落地补充）：逐行短标签一律经 `ErrorText.resolve` 取得，键为
  `analysis.row.pending` / `.analyzing` / `.linked` / `.failed` / `.retrying`；**字面只能取自
  需求 `00 §4.3` 的状态名与 `05 §2` 的「重试中」，不得在界面里新造词面**（决定 #4）。
  行内失败原因同理：键不存在时**不附原因**，绝不退化成 `ErrorText` 的 unknown 兜底文案
  （否则界面会显示「出错了，请查看详情」这种没有信息量的话）。**禁止在代码里拼文案键**
  （`"...reason.$kind"` 这种拼法取不到会静默降级）。

### 3.2.11 外部歌词目录 `LyricDirsScreen`

- **数据来源**：`ScanSourceDao.observeSources(LYRICS): Flow<List<ScanSourceEntity>>`
- **UiState**：`permissionGranted`、`dirs: List<ScanSourceEntity>`
- **事件**：`RequestAllFilesPermission`、`ShowMessage(UiMessage)`
- **交互**：`添加目录` / 移除目录（`kind = LYRICS`）。

### 3.2.12 最近播放 `RecentPlayedScreen`

- **数据来源**：`LibraryRepository.observeRecentPlayed(limit = 50): Flow<List<SongListItem>>`（由 `play_history` 派生）
- **UiState**：`listState: ListUiState<SongListItem>`
- **事件**：`OpenSongDetail(entityId)`、`OpenQueue`、`ShowMessage(UiMessage)`
- **交互**：点击播放（用最近播放列表新建队列）；行内快捷 `＋`。

### 3.2.13 设置 `SettingsScreen`

- **数据来源**：`SettingsRepository.settings: Flow<AppSettings>`（DataStore）、API Key（`EncryptedSharedPreferences`，**只回显掩码**）、`defaultPlayMode` 取自 `PlaybackRepository.state.mode`（Room 的 `playback_state`，**不进 DataStore** —— 见 `03 §6` 的「不放」）、**内置提供商预设**取自 `:core:llm` 的只读常量表（纯 Kotlin、可单测）
- **UiState**
  - 必填四项：`llmProtocol: ProtocolKind`（下拉：openai / responses / anthropic；对应 DataStore `llm_provider`，语义 = 协议类型）、`llmBaseUrl`、`llmModel`、`apiKeyMasked: String?`（只回显掩码）
  - 「高级」（默认折叠）：`llmMaxRetries`、`llmConnectTimeoutMs` / `llmReadTimeoutMs`（超时）、`llmMaxTokens`、`llmSupportsJsonSchema`

### 3.3.1 `LibrarySongsViewModel`

> `SongFilter` 的定义在 `06 §3.2`（`:core:data`），字段名与语义**以那边为准**：
> `SongFilter(titleQuery: String? = null, hasLyricOnly: Boolean = false)`。
> 本节此前另写了一份 `SongFilter(nameQuery, lyricsOnly)`，与 `:core:data` 的实际实现不符 ——
> 按项目约定**改文档**，不再在此重复定义（同一类型两处定义正是漂移的来源）。

> **落地修正（2026-09-18，`toggle` 的判定基准）**：本节示例里 `multi.update { it.toggle(id) }`
> 的写法**不成立** —— `multi` 流按设计只承载 `isActive` / `selectedIds`，`selectableIds`
> （「当前列表里可播的那些」）是每帧由列表算出来的、只存在于 UiState 上。而
> `MultiSelectState.toggle` 内部是 `if (id in selectableIds)`，拿 `multi.value` 去 toggle
> 时那个集合恒为空，**勾选会静默失效**（多选功能整体不可用）。
>
> 正确写法是**以 `state.value.multiSelect` 为判定基准，只把 `selectedIds` 回写 `multi`**：
>
> ```kotlin
> fun toggleSelect(id: Long) {
>     val applied = state.value.multiSelect.toggle(id)   // ← 带 selectableIds 的那份
>     multi.value = multi.value.copy(selectedIds = applied.selectedIds)
> }
> fun selectAll() {
>     val applied = state.value.multiSelect.selectAll()
>     multi.value = multi.value.copy(selectedIds = applied.selectedIds)
> }
> ```
>
> `selectableIds` 为什么不直接塞进 `multi`：它由列表内容派生，塞进去就得让 `multi` 反向订阅
> 列表流，与 `state` 的 `combine` 成环。**四个列表 VM（含标签列表的文件/标签多选）都按此修正**。

```kotlin
        LibrarySongsUiState(
            listState = when {
                items.isEmpty() && f.isEmpty -> ListUiState.Empty
                items.isEmpty() -> ListUiState.EmptyFiltered
                else -> ListUiState.Content(items)
            },
            sort = s, filter = f, totalCount = items.size,
            multiSelect = m.copy(selectableIds = items.filter { it.isPlayable }.map { it.entityId }.toSet()),
            actionSheet = sh, confirmation = cf, nowPlayingId = pb.currentEntityId,
        )
    }.stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), LibrarySongsUiState.initial())

    fun onSortChange(next: SongSort) { sort.value = next; multi.value = MultiSelectState<Long>() }
    fun onFilterChange(next: SongFilter) { filter.value = next; multi.value = MultiSelectState<Long>() }

    // ── 行点击：多选态=勾选；否则=播放（不可用仅提示，I3）─────────────
    fun onRowClick(item: SongListItem) = when {
        multi.value.isActive -> toggleSelect(item.entityId)
        item.isPlayable -> playbackController.playFromList(
            songs.value().map { it.entityId }, songs.value().indexOf(item))
        else -> _events.trySend(LibrarySongsEvent.ShowMessage(UiMessages.NoPlayableFile))
    }

    fun onPlayAll() {
        val ids = currentItems().map { it.entityId }
        playbackController.playFromList(ids, 0)
    }

    fun onQuickAddToQueue(item: SongListItem) {
        if (!item.isPlayable) return _events.trySend(LibrarySongsEvent.ShowMessage(UiMessages.NoPlayableFile))
        playbackController.appendToQueue(item.entityId)
        _events.trySend(LibrarySongsEvent.AddedToQueue(1))
    }

    // ── 操作面板 ────────────────────────────────────────────────
    fun onOpenActionSheet(item: SongListItem) { sheet.value = ActionSheetModel.forSong(item) }
    fun onDismissActionSheet() { sheet.value = null }
    fun onAction(item: SongListItem, action: SongAction) {
        sheet.value = null
        when (action) {
            SongAction.PLAY -> onRowClick(item)
            SongAction.PLAY_NEXT -> playbackController.insertNext(item.entityId)
            SongAction.ADD_TO_QUEUE -> onQuickAddToQueue(item)
            SongAction.ADD_TO_TAG -> openTagEditor(item.entityId)
            SongAction.VIEW_DETAIL -> _events.trySend(LibrarySongsEvent.OpenSongDetail(item.entityId))
            SongAction.MULTI_SELECT -> enterMultiSelect(item.entityId)
            SongAction.DELETE -> confirm.value = ConfirmRequest.deleteSongs(listOf(item.entityId))
        }
    }

    // ── 多选 ────────────────────────────────────────────────────
    fun enterMultiSelect(seed: Long? = null) =
        multi.update { MultiSelectState<Long>(isActive = true, selectedIds = setOfNotNull(seed)) }
    fun toggleSelect(id: Long) = multi.update { it.toggle(id) }
    fun selectAll() = multi.update { it.selectAll() }
    fun clearSelection() = multi.update { it.clearSelection() }
    fun exitMultiSelect() { multi.value = MultiSelectState<Long>() }

    fun onBatchAddToQueue() {
        val ids = multi.value.selectedIds.toList()
        ids.forEach(playbackController::appendToQueue)
        exitMultiSelect()
        _events.trySend(LibrarySongsEvent.AddedToQueue(ids.size))
    }
    fun onBatchDelete() { confirm.value = ConfirmRequest.deleteSongs(multi.value.selectedIds.toList()) }

    // ── 二次确认 ─────────────────────────────────────────────────
    fun onConfirmDelete(request: ConfirmRequest) {
        viewModelScope.launch {
            val count = request.ids.size
            request.ids.forEach { deletionService.deleteSong(it) }
            exitMultiSelect(); confirm.value = null
            _events.trySend(LibrarySongsEvent.Deleted(count))
        }
    }
    fun onDismissConfirm() { confirm.value = null }
}
```

```text
                    └────────────────────────────────────────────────────────────┘
```

### 4.1.4 覆盖页呈现方式：独立路由 vs `ModalBottomSheet`

| 维度 | 独立路由（**采用**） | `ModalBottomSheet` |
| --- | --- | --- |
| 返回栈 | 天然入栈，系统返回 / 预测性返回直接关闭 | 需手动处理 `onDismissRequest`，与 `NavController` 返回栈不互通 |
| 状态作用域 | ViewModel 随 `NavBackStackEntry` 生命周期，可 `SavedStateHandle` 恢复 | ViewModel 需挂在父级，生命周期语义模糊 |
| 子标签 / 二级 | 播放器需要 `歌曲 | 歌词` 子标签、队列需要多选态顶栏 | sheet 内嵌 Tab + 顶栏，交互层级拥挤 |
| 拖拽手势冲突 | 无冲突（进度条拖动、歌词滚动各占其位） | sheet 的纵向拖拽与进度条 / 歌词滚动抢手势 |
| 全屏沉浸 | 覆盖状态栏 / 手势区，符合"全屏播放器" | 顶部保留 scrim，无法真正全屏 |
| 免费手感 | 需自实现「下拉收起」（对顶栏 `draggable`，位移超阈值即 `popBackStack`） | 自带下拉关闭 |

**结论**：三个覆盖页（全屏播放器 / 播放队列 / 歌曲详情）**一律用独立路由 + `slideInVertically`**；全屏播放器自行实现「下拉收起」手感。**`ModalBottomSheet` 只用于 `ActionSheet`（底部操作面板）**，因为那是"临时、轻量、无需占返回栈"的场景，与覆盖页诉求相反。

## 4.2 返回键行为

**优先级（高 → 低）**，用 `BackHandler(enabled = ...)` 分层注册：

```text
① ActionSheet / 其他 ModalBottomSheet 打开  → 关闭面板
② 确认对话框打开                            → 关闭对话框（= 取消）
③ 处于多选态                               → 退出多选并清空选择（不离开页面）
④ 处于覆盖页（player / queue / song）        → 关闭覆盖页，回到来源
⑤ 处于音乐库二级页（歌手/专辑/标签歌曲列表）   → 回到上级（默认导航行为）
⑥ 处于某个非首屏 Tab 图深处                 → 回到该 Tab 首屏
⑦ 处于 Tab 首屏（songs / search / mine）     → 交给系统（退出 App / 后台）
```

```kotlin
@Composable
fun MultiSelectBackHandler(state: MultiSelectState<*>, onExit: () -> Unit) {
    BackHandler(enabled = state.isActive) { onExit() }   // ③ 优先于导航默认行为
}
```

- 多选态用**行内 `BackHandler`**（注册在页面 Composable，晚于导航图 `BackHandler`，故优先触发）。
- 覆盖页是独立路由，④ 由系统导航返回栈天然满足，无需额外 `BackHandler`。
- ① 由 `ModalBottomSheet` 的 `onDismissRequest` + `BackHandler` 兜底。

```kotlin
        // ⑤ 行尾 ⋯（多选态隐藏）
```

> **偏离原稿四处（已按实现回写）**：
> ① 封面入参 `item.coverModel` → 由本行组装 `CoverModel(item.coverCachePath, item.entityId)` ——
> `SongListItem`（`06 §3.1`）里没有 `coverModel` 字段。

### 4.3.3 `MultiSelectState`（选择态状态模型）

```kotlin
@Immutable
data class MultiSelectState<T>(
    val isActive: Boolean = false,
    val selectedIds: Set<T> = emptySet(),
    val selectableIds: Set<T> = emptySet(),   // 当前筛选结果中「可选」的 id（不可用/受保护项已剔除）
) {
    val selectedCount: Int get() = selectedIds.size
    val allSelected: Boolean get() = selectableIds.isNotEmpty() && selectedIds.containsAll(selectableIds)
    val canBatch: Boolean get() = selectedIds.isNotEmpty()

    fun toggle(id: T) = if (id in selectableIds)
        copy(selectedIds = if (id in selectedIds) selectedIds - id else selectedIds + id) else this
    fun selectAll() = copy(selectedIds = selectedIds + selectableIds)
    fun clearSelection() = copy(selectedIds = emptySet())
}
```

> **偏离原稿一处（已按实现回写）**：原稿把 id 写死成 `Set<Long>`。但 §3.2.5 要求某分类下的
> 标签列表**勾选 = 标签名**（`Set<String>`），而它同样要走这套多选交互。故放宽为泛型 `T`：
> 歌曲 / 文件 / 队列项传 `Long`，标签列表传 `String`。
> **Kotlin 没有「类型参数默认值」**，所以调用处必须显式写出 `MultiSelectState<Long>` /
> `MultiSelectState<String>`，写裸的 `MultiSelectState` 会因 `T` 无从推断而编译失败。

### 4.4.1 布局结构

```text

│                                    │
│            NavHost 内容             │   innerPadding.bottom = bottomBar 高度
│                                    │   → NavHost 消费，内容不被遮挡

│ └────────────────────────────────┘ │  │  bottomBar =
│   音乐库       搜索       我的      │  │  Column { MiniPlayerBar; NavigationBar }
│                                    │  ┘
└────────────────────────────────────┘
        ↑ Modifier.navigationBarsPadding() 避让手势区
```

### 4.4.2 根 `Scaffold`

```kotlin
@Composable
fun AiMusicApp(navController: NavHostController, miniVm: MiniPlayerViewModel) {
    val backStackEntry by navController.currentBackStackEntryAsState()
    val destination = backStackEntry?.destination
    val isOverlay = destination?.hierarchy?.any { it.isOverlayRoute() } == true

    val miniState by miniVm.state.collectAsStateWithLifecycle()

    Scaffold(
        contentWindowInsets = WindowInsets(0),          // 顶部 insets 交给各屏自己的 TopAppBar
        bottomBar = {
            if (!isOverlay) {                            // 覆盖页不显示 mini 条与导航（覆盖页自身全屏）
                androidx.compose.foundation.layout.Column(
                    // 整条 bottomBar 避让手势区，保证导航按钮可点、不被手势条压住
                    modifier = Modifier.navigationBarsPadding(),
                ) {
                    if (miniState.hasSong) MiniPlayerBar(state = miniState, onClick = {
                        navController.navigate(PlayerRoute) { launchSingleTop = true }
                    }, onOpenQueue = {
                        navController.navigate(QueueRoute) { launchSingleTop = true }
                    })
                    AppBottomNavigation(
                        current = destination,
                        onSelect = { graph -> navController.navigateToTab(graph) },
                    )
                }
            }
        },
    ) { innerPadding ->
        AppNavHost(
            navController = navController,
            // 关键：内容区消费 bottomBar 高度 + 水平安全区，防止被 mini 条/导航遮挡
            modifier = Modifier
                .padding(innerPadding)
                .consumeWindowInsets(innerPadding),
        )
    }
}
```

### 4.4.3 关键点

| 关注点 | 做法 |
| --- | --- |
| **同时容纳导航 + mini 条** | `bottomBar` 是一个 `Column`：`MiniPlayerBar` 在上、`NavigationBar` 在下（要求"mini 条在底部导航正上方"） |
| **内容不被遮挡** | `Scaffold` 的 `innerPadding.bottom` = 整个 `Column` 高度，传给 `NavHost` 并 `consumeWindowInsets`，列表最后一项加 `contentPadding` 即可滚到底 |
| **手势区避让** | 整条 bottomBar 加 `Modifier.navigationBarsPadding()`；`ModalBottomSheet` 内部再补 `windowInsetsBottomHeight(WindowInsets.navigationBars)` |
| **状态栏避让** | 各屏自带 `TopAppBar`（`TopAppBarDefaults.windowInsets` 默认含状态栏）；根 `Scaffold` 不额外加顶部 inset，避免双重内边距 |
| **多选态 / 覆盖页切换** | 多选态隐藏 mini 条、底部换成 `MultiBatchBar`；覆盖页隐藏整条 bottomBar，`innerPadding.bottom` 归零，覆盖页自身全屏 |
| **mini 条可见范围** | 仅在三个 Tab 图（`library/search/mine` 及其子路由）内显示；覆盖页不显示 |
| **无曲目时** | `miniState.hasSong == false` 时不渲染 `MiniPlayerBar`，`innerPadding` 自动收缩（开关动画用 `AnimatedVisibility`） |

```kotlin
fun <T> ListSurface(
    state: ListUiState<T>,
    key: (T) -> Any,
    contentType: (T) -> Any? = { null },
    emptyAction: (@Composable () -> Unit)? = null,
    itemContent: @Composable (T) -> Unit,
) {
    when (state) {
        is ListUiState.Loading -> LoadingPlaceholder()
        is ListUiState.Empty -> EmptyPlaceholder(title = ..., action = emptyAction)
        is ListUiState.EmptyFiltered -> FilterEmptyPlaceholder(onClear = ...)
        is ListUiState.Error -> ErrorPlaceholder(state.error, onRetry = ...)
        is ListUiState.Content -> LazyColumn(
            contentPadding = PaddingValues(vertical = 8.dp),
        ) {
            items(state.items, key = key, contentType = contentType) { item -> itemContent(item) }
        }
    }
}
```

### 4.5.3 `LazyColumn` 的 key 策略

```kotlin
LazyColumn {
    items(
        items = state.items,
        key = { it.entityId },              // 歌曲：实体 id
        contentType = { "song" },
    ) { item -> SongRow(item = item, ...) }
}
```

| 列表 | key | 理由 |
| --- | --- | --- |
| 歌曲列表 / 搜索结果 / 最近播放 | `it.entityId` | 排序切换、增删时保持滚动位置与动画正确 |
| 歌手 / 专辑 / 标签列表 | `it.name` / `(albumName, albumArtist)` / `it.name` | 名称即唯一键 |
| **播放队列** | `it.queueItemId`（**不能用 entityId**） | 队列允许重复，同一 `entityId` 会出现多次，用 `entityId` 作 key 会崩溃/错位 |
| 分析文件列表 / 歌曲详情文件列表 | `it.fileId` | 文件唯一 |

> **禁止用下标作 key**：排序 / 筛选 / 删除后下标整体错位，`LazyColumn` 会错误复用 item 的 `remember` 状态并跳滚动位置。为增删项加 `Modifier.animateItem()` 依赖稳定 key。

## 4.6 事件与副作用约定

**状态**：`StateFlow<XxxUiState>`，`stateIn(viewModelScope, WhileSubscribed(5_000), initial)`；Composable 端用 `collectAsStateWithLifecycle()`。

**一次性事件**：`Channel<XxxEvent>(Channel.BUFFERED).receiveAsFlow()`；**禁止用 `StateFlow` 传导航 / 提示**（重放会重复触发）。

```kotlin
@Composable
fun <T> CollectEvents(flow: Flow<T>, onEvent: (T) -> Unit) {
    val lifecycleOwner = LocalLifecycleOwner.current
    LaunchedEffect(flow, lifecycleOwner) {
        lifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
            flow.collect(onEvent)                        // 前台收集，退到后台自动暂停
        }
    }
}

// 使用
CollectEvents(viewModel.events) { event ->
    when (event) {
        is LibrarySongsEvent.OpenSongDetail -> nav.navigate(SongDetailRoute(event.entityId))
        LibrarySongsEvent.OpenQueue -> nav.navigate(QueueRoute)
        is LibrarySongsEvent.ShowMessage -> snackbarHostState.showSnackbar(event.message.text())
        is LibrarySongsEvent.Deleted -> { /* snackbar */ }
        else -> Unit
    }
}
```

**对话框与二次确认（`页面设计` §9.5）**

- 确认对话框**不用 `Channel`**，而作为 `UiState.pendingConfirmation: ConfirmRequest?` **状态**——这样旋转 / 重组后对话框不丢，且与触发它的选中态同源。`Channel` 只承载导航与 Toast/Snackbar。
- 删除歌曲实体、物理删除文件**统一二次确认**；批量删除**显示数量**。

```kotlin
@Immutable
data class ConfirmRequest(
    val kind: ConfirmKind,           // DELETE_SONGS / DELETE_FILE_PHYSICALLY / REMOVE_FILE / CLEAR_QUEUE / DELETE_TAG / DELETE_CATEGORY
    val ids: List<Long>,
    val title: String,
    val message: String,
    val confirmLabel: String,
    val destructive: Boolean = true,
) {
    companion object {
        fun deleteSongs(ids: List<Long>) = ConfirmRequest(
            ConfirmKind.DELETE_SONGS, ids,
            title = if (ids.size > 1) "删除 ${ids.size} 首歌曲？" else "删除这首歌？",
            message = "将移除歌曲及其标签、歌词关联与播放记录；磁盘上的音乐文件不会被删除。",
            confirmLabel = "删除",
        )
        fun deleteFilePhysically(fileId: Long) = ConfirmRequest(
            ConfirmKind.DELETE_FILE_PHYSICALLY, listOf(fileId),
            title = "物理删除该文件？",
            message = "将从磁盘永久删除，不可恢复。",
            confirmLabel = "永久删除",
        )
    }
}

@Composable
fun ConfirmDialog(request: ConfirmRequest?, onConfirm: (ConfirmRequest) -> Unit, onDismiss: () -> Unit) {
    if (request == null) return
    AlertDialog(
        onDismissRequest = onDismiss,
        title = { Text(request.title) },
        text = { Text(request.message) },
        confirmButton = { TextButton(onClick = { onConfirm(request) }) { Text(request.confirmLabel) } },
        dismissButton = { TextButton(onClick = onDismiss) { Text("取消") } },
    )
}
```

| 操作 | 确认级别（`00-总览 §5`） | 组件 |
| --- | --- | --- |
| 删除歌曲实体 | 有文件时二次确认，无文件直接删 | `ConfirmDialog` |
| 移除文件 | 明显提示；若为最后一个文件，额外提示"将同时删除该歌曲" | `ConfirmDialog` |
| 物理删除文件 | 破坏性，二次确认 | `ConfirmDialog`（`destructive`） |
| 清空队列 / 批量删除标签 / 删除分类 | 二次确认（批量显示数量 / 受保护项不可选） | `ConfirmDialog` |

## 4.7 可访问性要点

| 项 | 做法 |
| --- | --- |
| **触控目标尺寸** | 行内 `IconButton`（`＋` / `⋯`）与勾选圈命中区 ≥ 48dp（`Modifier.size(48.dp)`）；批量条每个动作 `heightIn(min = 56.dp)` |
| **语义标签** | `⋯` → `contentDescription = "更多操作"`；`＋` → `"添加到队列"`；勾选圈由整行 `semantics(mergeDescendants = true)` 提供 `selected` + `stateDescription` |
| **列表可读性** | 歌曲行合并子节点为一句（歌名 · 歌手 · 专辑），由 `mergeDescendants` 保证读屏一次念完 |
| **多选** | 多选态顶栏标题 `"已选 N"` 可被读屏播报；全选按钮 `stateDescription = "全选 / 取消全选"` |
| **滑动手势的替代入口** | **不使用左滑**：正因左滑对读屏 / 手部不便用户不可达、可发现性差，我们以「行尾 `⋯` + 底部操作面板」作为**唯一**的行级操作入口，并以「长按 + `⋯`「多选」」作为多选入口——两个手势都有等价的**可聚焦控件**入口（`⋯` 按钮、`⋯` 面板中的「多选」项） |
| **面板语义** | `ModalBottomSheet` 作为对话框，读屏焦点应移入并聚焦标题；关闭后焦点回到触发行 |
| **动画** | 尊重系统「移除动画」设置（`LocalMotionDurationScale`），覆盖页转场与列表动画随之降级 |
| **颜色不作为唯一信息** | 不可用歌曲同时置灰 **且** 保留文本；`MediaSession` 状态有图标 + 文本 |

# 6. 错误处理

界面层只做 `AppError.FailureKind → 呈现方式` 的映射，**文案集中在 `11-错误处理与可观测性.md`**，界面层不硬编码。

| `FailureKind` | 呈现 | 动作 | 出现位置 |
| --- | --- | --- | --- |
| `PERMISSION` | 内联空状态 / 引导卡片 | 「去授权」 | 我的 / 文件扫描 / 外部歌词目录 |
| `NETWORK` | 内联错误占位 或 Snackbar | 「重试」 | 最近分析记录、扫描 |
| `RATE_LIMIT`（429） | 文件行状态「重试中」 | 无（自动退避，不计失败） | 最近分析记录 |
| `AUTH` | Snackbar + 引导 | 「去设置」 | 设置 / 最近分析记录 |
| `SERVER` | 内联 / Snackbar | 「重试」 | 最近分析记录 |
| `PARSE` | 文件行「分析失败〔原因〕」 | 「重试」 | 最近分析记录 |
| `IO` | Snackbar | 「重试」 | 物理删除 / 移除文件 |
| `NOT_FOUND` | Snackbar + 确认 | 「清理记录」 | 播放时文件缺失（05 §6） |
| `CONFLICT` | Snackbar（说明原因） | 无（禁用操作） | 删除标签 / 删除分类 |

- 列表级错误 → `ListUiState.Error` → `ErrorPlaceholder`（内联，带重试）。
- 操作级错误 → `XxxEvent.ShowMessage(UiMessage)` → `SnackbarHost`（一次性，不驻留）。
- 破坏性操作失败（如物理删除磁盘失败）→ 保持数据不变并 Snackbar 提示（`03 §4.4`）。

# 7. 性能与并发

| 关注点 | 约定 |
| --- | --- |
| **状态订阅** | `stateIn(viewModelScope, WhileSubscribed(5_000), initial)`：退到后台 5s 停止上游查询，省电 |
| **重组最小化** | `UiState` 与 UI 投影模型标注 `@Immutable`；列表字段用 `kotlinx.collections.immutable` 的 `ImmutableList`，避免每次发射都触发全量重组 |
| **稳定集合** | `MultiSelectState.selectedIds` 用不可变 `Set`；`MultiSelectTopBar` 只依赖 `selectedCount / allSelected`，用 `derivedStateOf` 收敛 |
| **列表** | `LazyColumn` 稳定 `key` + `contentType`，复用 item；`items` 惰性组合，仅可见项进入组合 |
| **图片** | Coil 内存 + 磁盘缓存；`CoverImage` 固定尺寸避免布局跳动；共享 `ImageLoader` |
| **避免 N+1** | 标签在 Repository 内批量查询并 `combine` 进 `SongListItem`（`03 §5`），界面层不做逐行查询 |
| **上游线程** | 查询在 `Dispatchers.IO`；映射到 UI 模型在 `Dispatchers.Default`；主线程只做状态读取 |
| **长任务** | 扫描 / 分析交 WorkManager（`:app` 只订阅进度 Flow），播放交前台服务（`10`） |
| **Cover 懒提取** | 提取在 Coil 的 `Fetcher` 里异步执行，阻塞 IO 不占主线程 |
| **转场** | 覆盖页 `slideInVertically` 用预计算高度，避免测量两次导致的卡顿 |

**落地补充（3e 首次实践后修正）**：

- **屏幕一律拆两半**：`XxxScreen`（有状态外壳：取 ViewModel、收集事件流、把一次性事件变成权限弹窗 / snackbar 等副作用）+ `XxxContent`（无状态：只吃 UiState 与回调，回调参数大多给 `= {}` 默认值）。测试只测 `XxxContent`。上例原先传 `fakeVm` —— 那要求每个屏都维护一份假 ViewModel，而拆开之后一条用例只传它要断言的那两三个参数。
- **测试跑真机 `androidTest`**（`createComposeRule` + `debugImplementation(ui-test-manifest)`），与 `11 §8.2` 的 Room 测试同一个决定：本工程每阶段本来就要连真机跑一遍，不必再引 Robolectric 去维护第二套环境。
- **断言模板文案时用 `substring = true` 匹配片段**（如「已存在跳过 3」），不要硬编码整句：`ErrorText` 的模板随时可能改措辞，硬编码会让文案改动变成一片测试红。
- **每个新 UI 测试都要做一次变异抽查**：故意改坏一处生产代码或一条断言，确认**恰好**那条变红、再改回。UI 测试第一次跑就全绿时，"它到底断言了没有" 是无法从结果看出来的。
- 已落地：扫描页 11 条（`ScanScreenContentTest`），覆盖下表与 `11 §8.3` 中空状态 / 权限 / 降级相关的行；其余行随各自屏幕落地。
- **空状态一律做持久态**：§5.1 的每一行都是「文案 + 动作」。做成一闪而过的 snackbar，等于把动作入口也做成了闪过即逝 —— 扫描页的「未发现新文件 / 没有扫描到音乐」两条就是这么错的，已改为 `ScanUiState` 上的状态（详见 `11 §8.3` 的落地补充）。
- **空状态的用例要给出真实前提**：`when` 里 `sources.isEmpty()` 排在扫描结果之前，所以「扫完发现没有音乐」的用例必须带上非空的 `sources`，否则测到的是另一条分支。
- **ViewModel 的测试**（`ScanViewModelTest`，JVM + MockK，16 条）钉的是跨模块才暴露的编排逻辑：权限守卫、预设来源只采纳真实存在的、提交流程文案、两条过滤规则互不干扰。构造后必须让 `state` 热起来（`backgroundScope.launch { vm.state.collect {} }`）—— `stateIn(WhileSubscribed)` 没有订阅者时值停在 `initialValue`，断言读到的是默认值，是**假绿**。
- **不要在写库之后回头读 `state.value` 来做判断**：扫描页的「补完预设再判一次来源是否为空」就是这么写的，而 `state` 是 `stateIn`，写库要绕一圈才回来 —— 结果是用户点了「开始扫描」、目录加进去了，却弹出「没有找到常见的音乐目录」且**不扫描**。用写操作的返回值判断，别依赖反应式状态的时序。
