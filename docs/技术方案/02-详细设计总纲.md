```

:core:playback        Media3 封装、QueueEngine、播放会话统计、MediaSessionService
:core:ui              设计系统：列表行、⋯操作面板、多选、空状态、mini 播放条
:core:testing         公共测试夹具与假实现（`runDbTest`、`FakeStorageSource`、假 LLM provider 等），供各模块 `testImplementation` 引入
:feature:library      音乐库（歌曲/歌手/专辑/标签）
:feature:search       搜索
:feature:player       全屏播放器 / 歌词 / 队列
:feature:mine         文件扫描 / 最近分析记录 / 外部歌词目录 / 最近播放 / 设置
```

**依赖方向（严格单向，禁止反向依赖与 feature 间依赖）**

```
:app      ─→  全部 feature:* 与 core:*（仅导航图与 DI 聚合，见 09 / 10）
feature:*  ─→  core:ui, core:playback, core:data, core:llm, core:storage, core:common
core:playback ─→ core:data, core:common
core:data ─→ core:llm, core:storage, core:common
core:llm  ─→ core:common
core:storage ─→ core:common
core:ui   ─→ core:data, core:common
```

>

# 3. 分层与命名约定

## 3.1 分层

```
UI (Compose)  →  ViewModel  →  Repository / Orchestrator  →  DAO / StorageSource / LlmNormalizer
```

- **不引入 UseCase 层**：本项目用例粒度与 Repository 基本 1:1，多加一层只增样板。跨仓库的业务编排集中在 `Orchestrator`（`ScanOrchestrator` / `AnalysisOrchestrator`）与 `DeletionService`。
- **不做两套模型映射**：Room Entity 直接作为领域模型在层间传递（表结构与需求字段高度一致）；仅对列表页需要联表聚合的结果定义 `*Item` 投影模型（如 `SongListItem`）。

# 4. 数据模型（概要）

> 完整 DDL、索引、DAO 见 `03-数据层设计.md`。此处只固定表清单与语义。

| 表 | 语义 | 关键约束 |
| --- | --- | --- |
| `song_entity` | 歌曲实体（核心管理对象） | `id` 主键；`artists_key` 为身份比较键 |
| `song_artist` | 实体 ↔ 演唱者（拆行，支撑歌手维度的分组与计数） | `(entity_id, artist_name)` 联合主键 |
| `music_file` | 音乐文件，挂靠实体 | `path` 唯一；`entity_id` **可空**（未分析时为 `NULL`）、外键级联 |
| `category` | 标签分类 | `is_main` 标记主要分类 |
| `tag` | 标签，名称全局唯一 | `name` 主键；`category_id` 外键 |
| `entity_tag` | 实体 ↔ 标签（多对多） | `(entity_id, tag_id)` 联合主键 |
| `lyric` | 歌词关联 | `path` 唯一（1:1 约束） |
| `queue_item` | 播放队列项（允许重复、有序） | `position` 排序 |
| `playback_state` | 播放状态单行表 | `id = 0` 单例 |
| `play_history` | 实际播放顺序（随机模式「上一首」依据） | 保留最近 N 条 |
| `analysis_run` | 一次分析批次 | 汇总计数 |
| `analysis_run_file` | 批次 ↔ 文件（「最近分析记录」的文件清单） | `(run_id, file_id)` 联合主键；随批次与文件级联删除 |
| `scan_source` | 音乐扫描来源 / 外部歌词目录 | `kind` 区分 |
| `llm_cache` | LLM 归一化结果缓存（内容寻址） | `cache_key` 主键；**不参与级联删除** |

**关键决策**

1. `artists_key`：归一化后**排序去重**的演唱者集合，用 `\u001F`（Unit Separator）连接——确定性、可精确比较，直接承担 `entityKey` 的第二维。
2. `display_artists`：展示用全署名文本（如 `林俊杰 / 蔡卓妍`）。
3. 代表文件不单独建表，用 `music_file.is_representative` 标记（每实体至多 1 行）。
4. 封面不入库：由代表文件内嵌图懒提取到应用缓存，路径存 `song_entity.cover_cache_path`（可为空，缺失时按需重建）。

## 5.1 文件访问（`:core:storage`）

```kotlin
interface StorageSource {
    fun listFiles(roots: List<String>, exts: Set<String>, onProgress: (Int) -> Unit): Sequence<FileRef>
    fun exists(path: String): Boolean
    fun isDirectory(path: String): Boolean      // 落地补充（Phase 3c）
    fun size(path: String): Long

```

> **落地补充（Phase 3c）**：`isDirectory` 是后加的。`04 §3.4` 的 `add` 要区分「路径不存在」
> 与「路径存在但不是目录」并给出两种提示，而 `04 §1.2` 又明令禁止业务层直接碰 `java.io.File`
> —— 不补这个方法，来源校验就只能破一次边界。

`exts` 由调用方给出：音频 `mp3/flac/m4a/aac/ogg/wav/wma/ape`，歌词 `lrc`。

## 5.3 LLM 归一化（`:core:llm`）

```kotlin
interface LlmNormalizer {
    /** 一次一批（默认 20 个文件）；返回与入参等长、按索引对齐。 */
    suspend fun normalize(requests: List<NormalizeRequest>): List<NormalizeOutcome>
}

/** 批内单个文件的输入（顺序即 prompt 中的【文件 N】）；一次一批（默认 20，最后一批为余数，见 §7「分析」），同批共享一份分类 / 标签目录。 */
data class NormalizeRequest(
    val fileName: String,
    val metadata: AudioMetadata?,   // 类型在 :core:common（com.aimusic.player.common.model）；值由 :core:storage 的 MetadataReader 产出
    val categories: List<String>,   // 当前有效分类（实时读取，非快照）
    val tags: List<TagRef>          // 当前有效标签，TagRef(name, category)
)

data class NormalizeResult(
    val canonicalTitle: String,
    val artists: List<String>,        // 全部署名，已归一化、去重，未排序
    val tagAssignments: List<TagAssignment>  // (category, name)
)

sealed interface NormalizeOutcome {
    data class Success(val result: NormalizeResult) : NormalizeOutcome
    data class RateLimited(val retryAfterMs: Long?) : NormalizeOutcome
    data class Failure(val kind: LlmFailureKind, val cause: Throwable?) : NormalizeOutcome
}
enum class LlmFailureKind { NETWORK, AUTH, SERVER, INVALID_OUTPUT, TIMEOUT }
```

- **重试策略不进 provider**：由装饰器 `RetryingLlmNormalizer(delegate, policy)` 实现 429 指数退避，便于单测与替换。
- **缓存装饰器** `CachingLlmNormalizer(delegate, cache)`：逐文件查缓存，`cache_key = sha256(fileName + 元数据指纹 + model + prompt 文件哈希 + 目录指纹)`；只缓存 `Success`，`RateLimited` / `Failure` 不写缓存（表结构见 `03` §2.2）。key 必须含**目录指纹**（分类名 + 标签名规范化串）——否则用户新建分类后，同一文件会命中旧缓存、返回的标签里永远缺该分类；**prompt 文件哈希**（system / user / schema 的文件内容）**取代**原 `PROMPT_VERSION` 常量，改 prompt 即失效。
- **两个 `Tag` 引用类型不是一回事**：本节 `NormalizeRequest.tags: List<TagRef>` 用的是 **`:core:llm` 契约的 `TagRef(name, category)`**（只有标签名 + 分类名）。列表 / 详情用的**三字段投影**（多带 `categoryId`）**不是它**，另名 **`TagProjection`**（`com.aimusic.player.data.model.TagProjection`，文档见 `06 §3.1`）——因依赖守卫禁止 `:core:llm → :core:data`，LLM 契约拿不到 `categoryId`。
  - **落地修正（Phase 5 回写）**：`TagProjection` 实际放在 **`:core:data`**（以 `06 §3.1` 为准），本节原文写 `com.aimusic.player.common.model.TagProjection` 系笔误 —— 它是列表 / 详情的域投影，与归一化无关，无必要下沉到 `:core:common`。同时按本决定 #3 完成了代码侧的改名：此前它误称 `TagRef` 放在 `:core:common`，与本节的两字段 `TagRef` 同名不同形（`:core:common` 的 KDoc 还曾自称「全项目唯一的标签展示类型」，与该同名者直接矛盾）。现 `:core:common` 只保留 `NormalizeResult` / `TagAssignment`。

# 6. 状态机

## 6.1 文件分析状态机（`music_file.analysis_status`）

```
        ┌────────────┐  用户点「分析并添加」   ┌───────────┐
        │ UNANALYZED │ ─────────────────────→ │ ANALYZING │
        │  未分析     │                        │  分析中    │
        └────────────┘                        └─────┬─────┘
                                                  │
              ┌───────────────────────────────────┼────────────────────────────┐
              │ 成功                               │ 429（可重试）               │ 其他错误 / 解析失败
              ▼                                   ▼                            ▼
        ┌──────────┐                     （保持 ANALYZING，               ┌──────────┐
        │  LINKED  │                      退避等待，不计失败）             │  FAILED  │
        │  已关联   │ ←───────────── 手动重试（仅 FAILED 可重试）────────  │  分析失败 │
        │ （终态）  │                                                        └──────────┘
        └──────────┘
```

- `LINKED` 是**终态**：不再重分析（除非实体被手动删除，文件回到 `UNANALYZED`）。
- 未被关联的文件（`UNANALYZED` / `FAILED`）可被分析/重试。

## 6.2 扫描会话状态机

```
IDLE → SCANNING → DIFFING → AWAITING_USER ─┬─「分析并添加」→ COMMITTING → ANALYZING → DONE
                                           └─「放弃」────→ DISCARDED（不写库）
```
- `DISCARDED` 不产生任何持久化记录，下次扫描重新作为新文件提示。
- 扫描期间发现磁盘已删除的文件：在 `COMMITTING` 阶段清理其 `music_file` 记录（与用户选择无关，属自动清理）。

## 6.3 播放会话状态机

```
IDLE → PLAYING(song) → 切歌/自然结束/退出 → SETTLED(结算一次)
             ↑                                   │
             └──── 进程被杀 → 恢复为同一会话延续 ───┘
```
- 会话开始：`play_count + 1`，更新 `last_played_at`，写入 `play_history`。
- 会话结算：按 **最大进度位置 / 代表文件时长** 的占比落入三档（≥85% 完整、≤15% 跳过、其余中断）。
- 进程被杀**不单独结算**；会话状态随 `playback_state` 持久化，恢复后继续累计最大进度。

# 7. 并发与线程模型

| 场景 | 约定 |
| --- | --- |
| 数据库 / 文件 IO | 一律在 `Dispatchers.IO`；DAO 的 `suspend` 方法由 Room 自行调度 |
| 扫描 | **全局单例 + `Mutex`**，同一时刻只允许一次扫描；重复触发返回"扫描进行中" |
| 分析 | 单 worker 串行调用 LLM，**每批默认 20 个文件**（批语义见 §5.3）；避免并发触发限流，进度逐文件用 `Flow` 上报 |
| 写事务 | 所有跨表写入必须包在 `@Transaction` 中（挂靠、删除、标签变更） |
| UI 状态 | ViewModel 暴露 `StateFlow<XxxUiState>`（`stateIn(viewModelScope, WhileSubscribed(5s), initial)`） |
| 一次性事件 | `Channel<XxxEvent>(BUFFERED).receiveAsFlow()`，禁止用 `StateFlow` 传导航/提示 |
| 长任务 | 扫描与分析交给 WorkManager（见 `10`），前台服务承载播放 |

**单写者原则**：`music_file` 的 `analysis_status` 只由 `AnalysisOrchestrator` 修改；`queue_item` / `playback_state` 只由 `QueueEngine` 修改。其他模块通过 Repository 读取。

# 8. 错误模型

```kotlin
sealed interface AppError {
    val kind: FailureKind
    val cause: Throwable?
}
enum class FailureKind { PERMISSION, NETWORK, RATE_LIMIT, AUTH, SERVER, PARSE, IO, NOT_FOUND, CONFLICT, UNKNOWN }
```

| 场景 | FailureKind | 自动恢复 | 用户可见动作 |
| --- | --- | --- | --- |
| 无"所有文件访问"权限 | `PERMISSION` | 否 | 「去授权」 |
| 429 | `RATE_LIMIT` | **是**（指数退避） | 显示"重试中"，不计失败 |
| 网络不可达 / 超时 | `NETWORK` | 否 | 「重试」 |
| Key 无效 | `AUTH` | 否 | 「去设置」 |
| 服务端 5xx | `SERVER` | 否 | 「重试」 |
| 结构化输出解析失败 | `PARSE` | 否 | 标记失败，「重试」 |
| 文件不存在 | `NOT_FOUND` | 否 | 清理记录 |
| 删除保护命中 | `CONFLICT` | 否 | 说明原因，禁用操作 |

**文案映射原则**：错误类型 → 用户语言在 `11-错误处理与可观测性.md` 统一维护，模块内不硬编码文案。

# 9. 关键不变量（Invariants）

> 这些是代码审查与单元测试的检查清单，任何实现都不得违反。

| # | 不变量 |
| --- | --- |
| I1 | 一个音乐文件**至多**属于一个实体（`music_file.path` 唯一；`entity_id` 为 `NULL` 表示尚未挂靠） |
| I2 | 一个实体**至多**一个代表文件（`is_representative = 1` 的行数 ≤ 1，且有文件时必须恰好 1 个） |
| I3 | 实体无文件 ⇒ 不可用；**不可用歌曲不得入队**（新建队列、追加、下一首播放均需过滤） |
| I4 | `analysis_status = LINKED` 的文件不可重新分析 |
| I5 | 标签名称**全局唯一**且必属于一个分类 |
| I6 | 歌曲列表展示的标签 ⊆ **主要分类**下的标签 |
| I7 | 一个 `.lrc` **至多**关联一个实体（`lyric.path` 唯一） |
| I8 | 删除实体**不触碰磁盘**（音频与 `.lrc` 均保留） |
| I9 | 队列允许重复；「下一首播放」项按 **LIFO** 优先于随机 |
| I10 | `play_count` 仅在**会话开始时** +1；进程被杀不重复计 |
| I11 | 代表文件变更后，专辑/封面等展示信息随之切换 |
| I12 | 删除保护：分类下有标签不可删；标签下有歌不可删 |
