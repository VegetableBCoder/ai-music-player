# 1. 模块职责与边界

## 1.1 做什么

| 职责 | 落点 |
| --- | --- |
| 落地 `02 §8` 的 `AppError` sealed 层次（每个 `FailureKind` 一个子类） | `:core:common` |
| 各来源（HTTP / IOException / 解析异常 / SQLite 约束）→ `AppError` 的统一映射 | `:core:common` + `:core:data` + `:core:llm` |
| **用户文案的唯一维护点**：`AppError` → 用户语言（文案键 + 参数） | `:core:common` |
| 重试策略集中定义（429 指数退避、`Retry-After`、抖动、重试上限、绝不自动重试清单） | `:core:common`（策略） + `:core:llm`（`RetryingLlmNormalizer`） |
| `Logger` 抽象 + 分级 + 关键事件清单 + **脱敏规则** | `:core:common` |
| `DiagnosticsReporter`（本地诊断快照 + 导出文本文件分享） | 接口 `:core:common`，实现 `:app`，入口 `:feature:mine` |
| 数据库层 `CONFLICT` 的业务语义翻译约定 | `:core:data` |
| 失败与清理的衔接约定（失败记录保留、`NOT_FOUND` 清理、删除失败回滚） | 约定 + `:core:data` / `:core:playback` |

## 1.2 不做什么

- **不做** UI 布局与组件实现（属 `:core:ui` / `feature:*`）；本文只定义 `ErrorUiModel` 契约与文案。
- **不做** 各模块自身的业务状态机（属 04–10）。
- **不接入任何第三方崩溃 / 统计 SDK**（V1 自用侧载场景，无上架合规与用户量统计需求）——但**预留 `DiagnosticsReporter` 接口**，未来接入只需替换实现（§3.6 / §4.7）。
- **不硬编码文案**：任何模块不得内联错误字符串（`02 §8` 文案映射原则）；一律经 `ErrorText` 解析。

## 1.3 依赖方向（遵守 `02 §2`）

```
:feature:*  ─→ :core:ui, :core:playback, :core:data, :core:llm, :core:common
:core:playback ─→ :core:data, :core:common
:core:data  ─→ :core:storage, :core:common
```

`:core:common` 为**零业务依赖**的纯 Kotlin(Android) 模块，`AppError` / `Logger` / `RetryPolicy` / 文案键均定义于此，保证所有模块与全部单测可直接引用。

# 3. 数据结构与接口

## 3.1 错误模型落地：`AppError` sealed 层次（内容 1）

`FailureKind` 严格取 `02 §8` 的 10 项；**每个 kind 恰好一个子类**，统一携带 `cause`、可选 `retryAfterMs`、可选 `userMessageKey`，并各自补充业务上下文。

```kotlin
package com.aimusic.player.common.error

/** 02 号文档 §8 定义，10 类，不得新增 / 改名。 */
enum class FailureKind {
    PERMISSION, NETWORK, RATE_LIMIT, AUTH, SERVER, PARSE, IO, NOT_FOUND, CONFLICT, UNKNOWN
}

/**
 * 全应用统一错误模型。
 * - cause          : 底层异常，仅用于日志与诊断，**绝不直接展示给用户**。
 * - retryAfterMs   : 仅 RATE_LIMIT 允许非空；其余恒为 null。
 * - userMessageKey : 指向 ErrorText 的文案键；null 表示由调用方按上下文补默认文案。
 */
sealed interface AppError {
    val kind: FailureKind
    val cause: Throwable?
    val retryAfterMs: Long?
    val userMessageKey: String?
}

enum class PermissionScope { ALL_FILES, READ_MEDIA_AUDIO, POST_NOTIFICATIONS }
data class PermissionError(
    val scope: PermissionScope,
    override val cause: Throwable? = null,
    override val retryAfterMs: Long? = null,
    override val userMessageKey: String? = "perm.denied",
) : AppError { override val kind get() = FailureKind.PERMISSION }

enum class NetworkReason { UNREACHABLE, TIMEOUT, DNS, TLS }
data class NetworkError(
    val reason: NetworkReason,
    override val cause: Throwable? = null,
    override val retryAfterMs: Long? = null,
    override val userMessageKey: String? = "net.error",
) : AppError { override val kind get() = FailureKind.NETWORK }

enum class RateLimitSource { HTTP_429, LOCAL_BACKOFF }
data class RateLimitError(
    val source: RateLimitSource,
    override val retryAfterMs: Long?,           // 唯一允许非空的重试时长
    val attempt: Int,                            // 第几次尝试，1 起
    override val cause: Throwable? = null,
    override val userMessageKey: String? = "llm.retrying",
) : AppError { override val kind get() = FailureKind.RATE_LIMIT }

data class AuthError(
    val httpStatus: Int?,                        // 401 / 403
    override val cause: Throwable? = null,
    override val retryAfterMs: Long? = null,
    override val userMessageKey: String? = "llm.auth",
) : AppError { override val kind get() = FailureKind.AUTH }

data class ServerError(
    val httpStatus: Int,                         // 5xx
    val requestId: String? = null,               // 服务端回传的 x-request-id（可选）
    override val cause: Throwable? = null,
    override val retryAfterMs: Long? = null,
    override val userMessageKey: String? = "llm.server",
) : AppError { override val kind get() = FailureKind.SERVER }

enum class ParseTarget { LLM_JSON, LRC, METADATA }
data class ParseError(
    val target: ParseTarget,
    val snippet: String? = null,                 // 已脱敏 + 截断（≤256 字符）
    override val cause: Throwable? = null,
    override val retryAfterMs: Long? = null,
    override val userMessageKey: String? = "llm.parse",
) : AppError { override val kind get() = FailureKind.PARSE }

enum class IoOperation { SCAN, READ_METADATA, READ_COVER, DELETE_FILE, WRITE_CACHE, DB }
data class IoError(
    val op: IoOperation,
    val pathDigest: String? = null,              // 脱敏文件标识 name#hash8（§3.5）
    override val cause: Throwable? = null,
    override val retryAfterMs: Long? = null,
    override val userMessageKey: String? = "io.error",
) : AppError { override val kind get() = FailureKind.IO }

enum class MissingEntity { MUSIC_FILE, LYRIC_FILE, QUEUE_ITEM, SONG }
data class NotFoundError(
    val entity: MissingEntity,
    val pathDigest: String? = null,
    override val cause: Throwable? = null,
    override val retryAfterMs: Long? = null,
    override val userMessageKey: String? = "file.missing",
) : AppError { override val kind get() = FailureKind.NOT_FOUND }

enum class ConflictType {
    DUPLICATE_FILE, DUPLICATE_LYRIC, DUPLICATE_TAG,
    TAG_HAS_SONGS, CATEGORY_HAS_TAGS, DUPLICATE_SOURCE
}
data class ConflictError(
    val conflict: ConflictType,
    val detail: String? = null,
    override val cause: Throwable? = null,
    override val retryAfterMs: Long? = null,
    override val userMessageKey: String? = null, // 由 ConflictType 决定，见 §5
) : AppError { override val kind get() = FailureKind.CONFLICT }

data class UnknownError(
    val message: String? = null,
    override val cause: Throwable? = null,
    override val retryAfterMs: Long? = null,
    override val userMessageKey: String? = "unknown",
) : AppError { override val kind get() = FailureKind.UNKNOWN }
```

> 说明：`retryAfterMs` 只在 `RateLimitError` 上有实质取值；其余子类保留该字段仅为满足 `02 §8` 的接口统一（`AppError` 的单一读取路径），默认 `null`。

## 3.2 来源 → `AppError` 映射函数（内容 1）

```kotlin
package com.aimusic.player.common.error

object ErrorMapper {
    const val MAX_SNIPPET = 256

    /** HTTP 响应 → AppError（BYOK 直连与未来 Gateway 共用） */
    fun fromHttp(
        status: Int,
        retryAfterMs: Long? = null,
        requestId: String? = null,
        body: String? = null,
    ): AppError = when {
        status == 401 || status == 403 -> AuthError(status)
        status == 408 || status == 504 -> NetworkError(NetworkReason.TIMEOUT)
        status == 429 -> RateLimitError(RateLimitSource.HTTP_429, retryAfterMs ?: 1_000, attempt = 1)
        status in 500..599 -> ServerError(status, requestId)
        else -> UnknownError("HTTP $status")        // 其余 4xx 归 UNKNOWN，需人工排查
    }

    /** IOException 家族 → AppError */
    fun fromIo(t: Throwable, op: IoOperation = IoOperation.SCAN): AppError = when (t) {
        is FileNotFoundException, is NoSuchFileException -> NotFoundError(MissingEntity.MUSIC_FILE, cause = t)
        is SocketTimeoutException -> NetworkError(NetworkReason.TIMEOUT, t)
        is UnknownHostException -> NetworkError(NetworkReason.DNS, t)
        is ConnectException -> NetworkError(NetworkReason.UNREACHABLE, t)
        is SSLException -> NetworkError(NetworkReason.TLS, t)
        is IOException -> IoError(op, cause = t)
        else -> UnknownError(cause = t)
    }

    /** 解析异常（LLM JSON / LRC / 元数据） → PARSE */
    fun fromParse(t: Throwable, target: ParseTarget, raw: String?): AppError =
        ParseError(target, Redactor.snippet(raw, MAX_SNIPPET), t)

    /** SQLite 约束冲突 → 默认 CONFLICT，交由数据层再翻译（§6） */
    fun fromSqlite(t: SQLiteConstraintException, op: IoOperation = IoOperation.DB): AppError =
        SqliteConstraint.parse(t.message)?.let { ConflictError(it.type, it.detail, t) }
            ?: IoError(op, cause = t)
}
```

```kotlin
package com.aimusic.player.common.error

/** 解析 SQLite 约束报文，例如 "UNIQUE constraint failed: music_file.path" */
data class SqliteConstraint(val type: ConflictType, val detail: String) {
    companion object {
        private val RE = Regex(
            """(?:UNIQUE|PRIMARY KEY|FOREIGN KEY|NOT NULL|CHECK) constraint failed:\s*(.+)"""
        )
        private val IDENT = Regex("""(music_file\.path|lyric\.path|tag\.name|entity_tag|scan_source|song_entity)""")

        fun parse(message: String?): SqliteConstraint? {
            val m = message?.let(RE::find) ?: return null
            val cols = m.groupValues[1].trim()
            val type = when {
                "music_file.path" in cols -> ConflictType.DUPLICATE_FILE
                "lyric.path" in cols      -> ConflictType.DUPLICATE_LYRIC
                "tag.name" in cols        -> ConflictType.DUPLICATE_TAG
                "entity_tag" in cols      -> ConflictType.DUPLICATE_TAG
                "scan_source" in cols     -> ConflictType.DUPLICATE_SOURCE
                else                      -> ConflictType.DUPLICATE_FILE
            }
            // detail 仅保留表/列名，剔除可能含路径的值
            return SqliteConstraint(type, IDENT.find(cols)?.value ?: "constraint")
        }
    }
}
```

## 3.4 重试策略（内容 3）

```kotlin
package com.aimusic.player.common.retry

data class RetryPolicy(
    /** 429 重试上限 N，来源 DataStore.llm_max_retries，默认 3 */
    val maxRetries: Int = 3,
    val baseDelayMs: Long = 1_000,
    val factor: Int = 2,
    val maxDelayMs: Long = 60_000,
    /** 抖动比例：实际等待 = 退避 * [1-jitter, 1] 内随机 */
    val jitterRatio: Double = 0.2,
) {
    /** 第 attempt 次重试（attempt 从 1 起）的等待时长。Retry-After 优先。 */
    fun delayFor(attempt: Int, retryAfterMs: Long? = null, random: Random = Random.Default): Long {
        val backoff = (baseDelayMs.toDouble() * factor.toDouble().pow(attempt - 1))
            .toLong().coerceAtMost(maxDelayMs)
        val jittered = (backoff * (1 - jitterRatio * random.nextDouble())).toLong()
        // Retry-After 优先：服务端给的值 > 本地退避时取服务端值，仍以 maxDelayMs 封顶
        return maxOf(jittered, retryAfterMs ?: 0L).coerceAtMost(maxDelayMs)
    }

    /** 仅 RATE_LIMIT 且未超上限时自动重试；其余一律不自动重试。 */
    fun shouldRetry(kind: FailureKind, attempt: Int): Boolean =
        kind == FailureKind.RATE_LIMIT && attempt < maxRetries
}
```

**退避序列（`Retry-After` 缺省、无抖动基准值）**

| 重试序号 | 1 | 2 | 3 | 4 | 5 | 6 | ≥7 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 基础等待 | 1s | 2s | 4s | 8s | 16s | 32s | 60s（封顶） |

- **`Retry-After` 优先**：服务端 429 带 `Retry-After` 时，等待时长 = `max(本地退避, Retry-After)`，仍以 60s 封顶（避免服务端要求过长等待卡死队列）。
- **抖动**：每个等待值乘上 `[1-jitterRatio, 1]` 的随机因子（默认 20%），避免多文件分析时的同步重试尖峰。
- **重试上限 N**：`RetryPolicy.maxRetries`，默认 3，可由设置项 `llm_max_retries` 调整。

**绝不自动重试的错误**（无论重试次数）：`AUTH`、`NETWORK`、`SERVER`、`PARSE`。

| kind | 是否自动重试 | 理由 |
| --- | --- | --- |
| `RATE_LIMIT` | **是** | 限流是暂时的，退避后可恢复（`01 §3.3`） |
| `AUTH` | 否 | Key 无效，重试无意义，须「去设置」修改 Key |
| `NETWORK` | 否 | 网络不可达，自动重试会放大等待且无收益，交由用户手动重试 |
| `SERVER` | 否 | 5xx 属服务端故障，`01 §3.3` 明确「其他错误不自动处理」 |
| `PARSE` | 否 | 结构化输出不可解析，重试大概率复现，标记失败即可重试（幂等） |
| 其余 | 否 | 非瞬态错误，需人工介入 |

**手动重试入口**

| 入口 | 位置 | 行为 |
| --- | --- | --- |
| 「重试失败项」 | 分析进度页 / 分析结果摘要 | `AnalysisOrchestrator.retry(failedFileIds)`，逐个重跑 |
| 「全部重试」 | 分析全部失败的结果页 | `retry(allFailedIds)` |
| 「最近分析记录 → 重试失败 / 未分析」 | `文件扫描 → 最近分析记录` | 对最近 `analysis_run` 的文件清单重试（`03 §3.7 observeRunFiles`） |
| 「重试」 | 单文件失败行（「查看详情」完整文件列表） | 单文件重试 |

> **与 WorkManager 退避的边界**：`01 §2` 的 `BackoffPolicy.EXPONENTIAL` **只用于基础设施级偶发失败**（如进程被杀后任务重启），**不用于业务错误**——业务错误一律走本节策略，避免 429 被双重退避。

**脱敏规则（明确取舍）**

```kotlin
package com.aimusic.player.common.log

object Redactor {
    private val API_KEY   = Regex("""sk-[A-Za-z0-9_\-]{4,}""")               // OpenAI 风格
    private val BEARER    = Regex("""(?i)bearer\s+[A-Za-z0-9._\-]+""")
    private val QUERY_KEY = Regex("""(?i)(api[_-]?key|access[_-]?token)=[^&\s]+""")
    private val HASH10    = Regex("""\b[A-Fa-f0-9]{24,}\b""")                 // 疑似长密钥 / token

    /** API Key 一律 sk-**** */
    fun apiKey(s: String): String =
        s.replace(API_KEY, "sk-****").replace(BEARER, "Bearer sk-****")
         .replace(QUERY_KEY, "$1=sk-****").replace(HASH10, "****")

    /** 文件标识：⟨sourceKind⟩:文件名#hash8，不含目录结构 */
    fun digest(sourceKind: String, name: String, path: String): String {
        val h = sha1(path).take(8)
        return "$sourceKind:$name#$h"
    }

    /** 错误详情：先脱敏再截断 */
    fun detail(error: AppError, limit: Int = 512): String =
        apiKey(error.cause?.toString() ?: error.kind.name).take(limit)

    fun snippet(raw: String?, limit: Int): String? = raw?.let { apiKey(it).take(limit) }
}
```

| 目标 | 规则 | 取舍说明 |
| --- | --- | --- |
| API Key / token | 一律 `sk-****`（含请求头 `Authorization: Bearer`、URL query、疑似长 hex/base64） | 无例外，硬约束（`01 §3.1`、`03 §7`） |
| 用户文件**绝对路径** | **默认不打印全量**：改用 `⟨sourceKind⟩:文件名#hash8`（sha1(path) 前 8 位，稳定可对齐同一文件） | 牺牲「一眼看目录」的便利，换取 ① 导出/分享日志不泄露目录结构与用户名；② 同一文件仍可跨行关联。若需排查目录级问题，仅 `DEBUG` 且由设置项 `diagnostics.log_full_path`（默认**关**）显式开启全路径；即便开启，`DiagnosticsReporter` 导出时仍会剥离绝对路径段 |
| 歌词原文 / 用户输入 | 不作为日志内容 | 只记长度、匹配等级等元数据 |
| 设备标识 | 不采集（不接第三方 SDK）；诊断只含机型与 SDK 版本 | 自用场景无需设备指纹 |

`:core:common` 提供 `RingBufferLogger`：内存环形缓冲（上限 500 条，超限丢最旧）+ `Logcat` 双写；`Main` 线程调用只入队，实际格式化在单线程 `Dispatchers.IO` 上异步完成。

## 4.2 重试流程（429）

```kotlin
// :core:llm
class RetryingLlmNormalizer(
    private val delegate: LlmNormalizer,
    private val policy: RetryPolicy,
    private val logger: Logger,
    private val sleeper: suspend (Long) -> Unit = { delay(it) },
) : LlmNormalizer {

    override suspend fun normalize(requests: List<NormalizeRequest>): List<NormalizeOutcome> {
        var attempt = 0
        while (true) {
            val outs = delegate.normalize(requests)
            // 429 是批级现象：整批同命运，任一项 RateLimited 即整批退避重试
            val limited = outs.firstOrNull { it is NormalizeOutcome.RateLimited } as? NormalizeOutcome.RateLimited
                ?: return outs                                        // 无 429 → 原样返回（Success / Failure 不自动处理）
            attempt++
            val error = RateLimitError(RateLimitSource.HTTP_429, limited.retryAfterMs, attempt)
            if (!policy.shouldRetry(FailureKind.RATE_LIMIT, attempt)) return outs   // 重试耗尽 → 整批上抛
            val wait = policy.delayFor(attempt, limited.retryAfterMs)
            logger.warn(LogEvent.ANALYSIS_RATE_LIMITED, "429 退避等待", error, mapOf("attempt" to attempt, "waitMs" to wait))
            sleeper(wait)                                        // 退避期间状态保持 ANALYZING，故不计失败
        }
    }
}
```

时序（单批 429）：

```
ANALYZING ──429──▶ (attempt=1) 等待 1s ──▶ 请求 ──429──▶ (attempt=2) 等待 ~2s ──▶ …
        └─ 超过 maxRetries：整批转 FAILED，error_kind=RATE_LIMIT，可手动重试
```

## 4.3 分析失败的记录保留策略（内容 7）

- 失败文件**保留在 `music_file`**，状态置 `FAILED`，写 `error_kind` + `analysis_error`；**不自动清理**（区别于「扫描时发现磁盘已删」的自动清理）。
- `FAILED` 文件不参与队列（`I3`：仅 `LINKED` 可播）；列表与「最近分析记录」中展示为可重试项。
- 保留到以下事件之一发生：
  - 用户手动重试成功 → `LINKED`（终态，`I4`）；
  - 用户「移除记录」（`unlinkFile`）或「物理删除」；
  - 下次扫描发现磁盘已删 → 自动清理（`03 §4.4` / 需求 00 §4.5）。
- 分析批次 `analysis_run.failed_count` 如实累计；批次文件清单由 `analysis_run_file` 关联（`03 §2.2`），供「最近分析记录」回溯。

## 4.4 播放时 `NOT_FOUND` 的清理序列（内容 7，引用 `03 §4.4`）

```
播放器请求播放 fileId
   └─ StorageSource.exists(path) == false
        ├─ Logger.warn(FILE_INVALIDATED)
        ├─ 提示「文件不存在或已被移动」（文案 playback.file.missing）
        └─ 进入清理序列（对应 03 §4.4 的 unlinkFile 语义）：
             ① 取 entity_id
             ② 事务内删除该 music_file 行
             ③ 若实体仍有其它文件 → 重新选举代表文件 + 刷新展示字段（I2 / I11）
                   → 自动用新的代表文件继续播放（需求 05 §6）
             ④ 若实体已无文件 → 弹「该歌曲已无可用文件，是否删除？」
                   ├─「删除」→ deleteSong(entityId)（只删库，不触碰磁盘，I8）
                   └─「保留并标记为不可用」→ 实体保留，列表置灰不可播（需求 05 §3/§6）
```

> 边界：清理**不触碰磁盘**（磁盘文件已不存在）；`NotFoundError` 一律不自动重试（§3.4）。

## 4.5 删除失败（磁盘 IO 错误）的回滚保证（内容 7）

物理删除遵守 `03 §4.4` 的**先删磁盘、后改库**顺序：

```kotlin
// :core:data
suspend fun deleteFilePhysically(fileId: Long): DeleteOutcome {
    val file = MusicFileDao.byId(fileId) ?: return DeleteOutcome.Gone
    return when (StorageSource.delete(file.path)) {
        true  -> db.withTransaction { unlinkFileInternal(fileId); DeleteOutcome.Deleted }   // 磁盘已删 → 库内原子清理
        false -> {
            logger.error(LogEvent.DELETE_FAILED, "磁盘删除失败，已回滚", IoError(IoOperation.DELETE_FILE))
            DeleteOutcome.Failed(IoError(IoOperation.DELETE_FILE))                          // 库不变，用户可重试
        }
    }
}
```

回滚保证（三条）：

1. **磁盘删除失败 → 数据库完全不变**：先 `StorageSource.delete` 返回 `false` 时直接中止，不进入事务。用户看到「删除失败，请重试」，记录仍在。
2. **事务失败 → 记录不残留在库**：`unlinkFileInternal` 全程在一个 `@Transaction` 内（删文件行 + 选举代表 + 刷新展示字段），要么全成，要么全回滚。
3. **磁盘删成功但事务失败（极小概率）** → 库内出现「指向不存在文件」的悬挂行；由下次扫描的差异比对自动清理（需求 00 §4.5）。此为唯一允许的短暂不一致，且可自愈。

## 5.1 用户文案映射总表（内容 2，覆盖需求 05 全部条目）

## 6.1 `FailureKind` 处理约定总表

## 6.2 数据库层面的错误处理约定（内容 6）

**核心原则**：`SQLiteConstraintException` 是**实现细节**，绝不允许穿透到 `Repository` 之上；`DbErrorTranslator` 在 `:core:data` 内把它翻译成业务语义（幂等跳过 / 引导复用 / 真正的业务拒绝）。

| 约束 | 表 / 列 | 触发场景 | 若直接抛 → kind | 翻译后业务语义 | 是否上报 UI |
| --- | --- | --- | --- | --- | --- |
| `UNIQUE` | `music_file.path` | 重扫同路径文件再入库 / 重复挂靠（`I1`） | `CONFLICT` | 幂等：`AlreadyExists` → 归入「已存在跳过 M」 | 否（DEBUG 日志） |
| `UNIQUE` | `song_entity(canonical_title, artists_key)` | 两文件归一化到同一实体 | `CONFLICT` | 复用已有实体（先 `findByIdentity`，冲突兜底 → 读回已有行） | 否 |
| `UNIQUE` | `lyric.path` | 第二首关联同一 `.lrc`（`I7`） | `CONFLICT` | 跳过该候选，记 WARN；不报错 | 否（WARN 日志） |
| `PRIMARY KEY` | `tag.name` | 新建同名标签（`I5`） | `CONFLICT` | 返回 `AddTagResult.ReuseExisting(categoryId)` → UI 引导复用 | 是（引导性提示） |
| `PRIMARY KEY` | `entity_tag(entity_id, tag_id)` | 重复挂靠同一标签 | `CONFLICT` | `OnConflictStrategy.IGNORE` → 幂等（`03 §4.1`） | 否 |
| `UNIQUE` | `scan_source(kind, path)` | 重复添加同一来源目录 | `CONFLICT` | 幂等忽略 | 否 |
| `FOREIGN KEY` | 关联表 → `song_entity` | 删除竞态 | `IO`（兜底） | 由 `ON DELETE CASCADE` 正常处理，不应发生 | 否（ERROR 日志） |
| 业务级拒绝（非 DB 约束） | — | `deleteTag` 有歌 / `deleteCategory` 有标签（`I12`） | `CONFLICT` | **真正的 `CONFLICT`**：返回 `DeleteTagResult.Blocked` / `DeleteCategoryResult.Blocked`，UI 说明原因并禁用 | 是（说明原因） |

```kotlin
package com.aimusic.player.data.error

/** 所有写操作经此翻译；Repository 之上只见业务结果，不见 SQLite 异常。 */
object DbErrorTranslator {
    inline fun <T> translate(block: () -> T, onConflict: (ConflictType) -> T): T = try {
        block()
    } catch (t: SQLiteConstraintException) {
        val c = SqliteConstraint.parse(t.message) ?: throw t   // 无法识别 → 交由上层兜底
        onConflict(c.type)
    }
}

// 示例：挂靠标签（幂等）
suspend fun attachTags(entityIds: List<Long>, tagNames: List<String>) = DbErrorTranslator.translate(
    block = { EntityTagDao.insertAll(rows) },                   // OnConflictStrategy.IGNORE
    onConflict = { /* 幂等：直接返回 */ },
)
```

> `ON CONFLICT` 说明：能用 `@Insert(onConflict = IGNORE/REPLACE)` 静默处理的（`entity_tag`、`song_artist`）优先用注解；必须显式走业务分支的（`tag.name` 重名、删除保护）才走 `DbErrorTranslator` + sealed 结果。

## 6.3 兜底

- 顶层 `CoroutineExceptionHandler` / `Thread.setDefaultUncaughtExceptionHandler` 将未捕获异常转为 `UnknownError`，记 `UNEXPECTED`（ERROR），UI 展示通用文案 + 「查看详情」；**不做**进程自杀式崩溃上报（无第三方 SDK）。
- `ErrorPresenter` 对 `userMessageKey == null` 的 `AppError` 回落到 `unknown` 文案，保证永不出现空提示。

# 7. 性能与并发

| 关注点 | 约定 |
| --- | --- |
| 日志写入 | `RingBufferLogger` 在 `Main` 线程只入队，格式化与落 `Logcat` 在单线程 `Dispatchers.IO`；环形缓冲上限 500 条，超限丢最旧，避免长扫描期内存膨胀 |
| 脱敏开销 | `Redactor` 正则**预编译**为静态字段；仅在日志成形与导出时执行，不在热路径（如逐帧播放回调）调用 |
| 退避等待 | `delay()` 挂起协程，不阻塞线程；有 `Retry-After` 时封顶 60s，防止单文件长时间占住串行队列（分析为单 worker，`02 §7`） |
| 错误计数 | `ErrorCounter` 以 `LongAdder`（或 `AtomicLongArray`，按 `FailureKind.ordinal` 索引）实现，无锁、可并发自增 |
| 冲突翻译 | 走 `@Insert(onConflict=...)` 或事务内 `try/catch`，**不额外查询**判定冲突（避免 TOCTOU 与额外 IO）；确需区分时用插入返回码（`-1`）判定 |
| 诊断快照 | `snapshot()` / `export()` 在 `Dispatchers.IO` 执行；导出加 `Mutex` 防并发重复生成 |
| 单写者 | `analysis_status` 仅 `AnalysisOrchestrator` 写、`queue_item`/`playback_state` 仅 `QueueEngine` 写（`02 §7`），错误处理不得跨权限改状态 |
| UI 分发 | 一次性提示用 `Channel<XxxEvent>`；`StateFlow<XxxUiState>` 只承载可组合的错误态，禁止用 `StateFlow` 传导航（`02 §7`） |
