# 1. 模块职责与边界

**做**：

- **权限**：声明、检查、引导、降级判定（所有文件访问 / 媒体读取 / 通知）。
- **后台任务**：扫描（`ScanWorker`）与分析（`AnalysisWorker`）的 WorkManager 调度、输入输出、退避、进度上报。
- **前台服务**：`MediaSessionService` 的组件声明、生命周期、通知渠道、常驻通知，承载后台播放。
- **启动序列**：`Application.onCreate` 的初始化顺序与冷启动恢复时机。
- **依赖注入**：`DatabaseModule` / `StorageModule` / `LlmModule` / `RepositoryModule` / `PlaybackModule` / `DispatcherModule` 的划分与绑定。
- **系统侧鲁棒性**：进程被杀与恢复、`onTaskRemoved`、Doze 与后台启动限制的取舍。

**不做**：

- **播放业务逻辑**（队列引擎、播放模式、会话统计、`playback_state` 读写细节）→ 属 `07-播放器模块`，本文只写「系统侧衔接点」。
- **扫描差异比对算法、`.lrc` 索引、元数据提取** → 属 `04-文件扫描模块`。
- **LLM Prompt / 结构化输出 / 429 退避的具体实现** → 属 `05-分析与 LLM 归一化模块`；本文只写「退避发生在哪一层」。
- **错误文案正文** → 属 `11-错误处理与可观测性.md`；本文只给「映射入口」。

**依赖**（严格遵循 `02 §2` 单向依赖）：

- 后台任务层位于 **`:app`**（`com.aimusic.player.work` / `com.aimusic.player.permission`），`:app` 可依赖全部 core 与 feature。理由：WorkManager 的 `WorkerFactory`（Hilt 的 `HiltWorkerFactory`）与权限 Activity-Result 入口都在应用层聚合；`02 §2` 未定义独立的任务模块，集中到 `:app` 不新增模块、不违反依赖方向。
- 任务体只调用 `04` / `05` 定义的编排器（`ScanOrchestrator` / `AnalysisOrchestrator`），不直接触碰 DAO 或磁盘。
- 播放前台服务位于 **`:core:playback`**（`02 §2` 已明确），其 `<service>` 声明由 `:core:playback` 的 `AndroidManifest.xml` 贡献，经 Manifest 合并进入 `:app`。

# 3. 数据结构与接口

## 3.1 `AndroidManifest.xml` 完整声明清单

由 `:app/src/main/AndroidManifest.xml` 汇总（播放服务声明可来自 `:core:playback` 的 Manifest 合并）。

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:tools="http://schemas.android.com/tools">

    <!-- ========== 存储：所有文件访问（V1 锁定决策，见 01 §5） ========== -->
    <!-- 任意目录扫描 / 外部歌词目录 / 物理删除 均依赖它；
         侧载分发下由用户手动在系统设置开启（API 30+） -->
    <uses-permission
        android:name="android.permission.MANAGE_EXTERNAL_STORAGE"
        tools:ignore="ScopedStorage" />

    <!-- Android 13(API 33)+ 细粒度媒体读取：未授予"所有文件访问"时的降级路径 -->
    <uses-permission android:name="android.permission.READ_MEDIA_AUDIO" />

    <!-- Android 12(API 32) 及以下的 legacy 读取（上限 32 由系统保证不再向 33+ 申请） -->
    <uses-permission
        android:name="android.permission.READ_EXTERNAL_STORAGE"
        android:maxSdkVersion="32" />

    <!-- ========== 通知（Android 13+ 运行时权限，可选但推荐） ========== -->
    <uses-permission android:name="android.permission.POST_NOTIFICATIONS" />

    <!-- ========== 前台服务（媒体播放） ========== -->
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
    <!-- Android 14(API 34)+ 强制：前台服务类型与权限必须成对声明 -->
    <uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK" />

    <!-- 播放期间保持 CPU 唤醒（Media3/ExoPlayer 内部持有 WakeLock） -->
    <uses-permission android:name="android.permission.WAKE_LOCK" />

    <!-- BYOK 直连 LLM（01 §3）与共享缓存校验 -->
    <uses-permission android:name="android.permission.INTERNET" />

    <application
        android:name=".AiMusicApp"
        android:allowBackup="false"
        android:enableOnBackInvokedCallback="true">

        <!-- 播放前台服务：由 :core:playback 贡献，最终合并到此 -->
        <service
            android:name="com.aimusic.player.playback.MusicPlaybackService"
            android:exported="true"
            android:foregroundServiceType="mediaPlayback">
            <intent-filter>
                <!-- Media3 MediaSessionService 服务端契约 -->
                <action android:name="androidx.media3.session.MediaSessionService" />
                <!-- 兼容 MediaBrowser / Android Auto / 旧版客户端发现 -->
                <action android:name="android.media.browse.MediaBrowserService" />
            </intent-filter>
        </service>

    </application>
</manifest>
```

> **补充（非上表 8 项，仅 API ≤ 29 物理删除需要）**：`<uses-permission android:name="android.permission.WRITE_EXTERNAL_STORAGE" android:maxSdkVersion="29" />`。API 26–29 上没有 `MANAGE_EXTERNAL_STORAGE`，物理删除文件需要写权限；30+ 由「所有文件访问」覆盖。是否声明由 `04`（物理删除实现）与 `11`（降级文案）共同确认。

**易错点**：

- `android:exported="true"` 必须显式声明（API 31+ 要求带 intent-filter 的组件显式声明），否则安装即失败；系统、蓝牙、Android Auto 需要 bind 该服务。
- `foregroundServiceType` 与 `FOREGROUND_SERVICE_MEDIA_PLAYBACK` 二者缺一，Android 14 上 `startForeground()` 会抛异常（见 §5.3）。
- `MANAGE_EXTERNAL_STORAGE` 需 `tools:ignore="ScopedStorage"` 抑制 lint 报错（自用/侧载分发，见 `01 §5`）。
- 不声明 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（决策见 §5.4）。

# 4. 核心流程

## 4.1 应用启动序列（`AiMusicApp.onCreate`）

**原则：只做轻量、幂等、无 IO 阻塞的初始化；绝不在此扫库或启动前台服务。**

```kotlin
// :app  com.aimusic.player.AiMusicApp
@HiltAndroidApp
class AiMusicApp : Application(), Configuration.Provider {

    @Inject lateinit var logger: Logger                       // :core:common
    @Inject lateinit var notificationChannels: NotificationChannelInitializer  // :core:playback
    @Inject lateinit var workerFactory: HiltWorkerFactory

    override fun onCreate() {
        super.onCreate()

        // ① 日志最先：后续任何一步失败都能留痕（:core:common.Logger）
        logger.init(tag = "AiMusicApp")

        // ② 通知渠道：纯内存 + 一次系统调用，幂等，轻量
        notificationChannels.create()

        // ③ 数据库 / DataStore：不在此显式初始化。
        //    Room 实例与 DataStore 由 Hilt @Singleton 惰性提供，首读在 Dispatchers.IO 的协程内完成。
        //    → 避免主线程阻塞（02 §7：DB / 文件 IO 一律 IO 调度器）

        // ④ 播放服务：不在此 startService / bindService。
        //    MediaController 由 :feature:player 前台 UI 连接；冷启动恢复见 4.1.1。
    }

    override val workManagerConfiguration: Configuration
        get() = Configuration.Builder()
            .setWorkerFactory(workerFactory)   // 让 Worker 支持 @Inject
            .build()
}
```

**初始化顺序与理由**

| 顺序 | 步骤 | 理由 |
| --- | --- | --- |
| ① | 日志（`:core:common`） | 最先，后续步骤异常可观测 |
| ② | 通知渠道 | 轻量幂等；播放通知首次触发前必须先有渠道 |
| ③ | 数据库 / DataStore（惰性） | 首读放 IO 协程，避免 ANR；不在 `onCreate` 同步读 |
| ④ | 播放服务绑定 | 只在 UI 出现后由 `MediaController` 连接，不在 `onCreate` 强启（见 §5.3） |

### 4.1.1 冷启动恢复播放状态的时机

- 恢复数据源为 `playback_state` 单行表（`03 §2.2`），由 `PlaybackRepository.restore()` 读取，**细节归 `07`**。
- **时机**：不在 `Application.onCreate` 触发。由 `:core:playback` 在**首个前台订阅点**（mini 播放条 / 播放页 / `MediaController` 连接）拉起 `restore()`，恢复到「当前曲目 + 上次位置 + 队列快照 + 播放模式」，但**处于暂停态**。
- **系统侧约束**：恢复只写内存状态与 UI，不触发 `startForegroundService`；真正 `startForeground` 由用户点击「播放」后由 Media3 执行（见 §5.3）。

### 4.1.2 是否触发自动扫描的判断

需求（`00 §4.1`）只要求「首次使用扫描」与「用户主动重新扫描」。据此：

```kotlin
suspend fun shouldAutoScanOnLaunch(prefs: SettingsPreferences, snapshot: PermissionSnapshot): Boolean {
    if (snapshot.storageAccess == StorageAccessLevel.NONE) return false   // 无权限：先引导（05 §7）
    if (prefs.lastScanAt != null) return false                            // 非首次：仅提示，不自动跑
    return true                                                           // 首次且已授权 → 引导扫描
}
```

- `lastScanAt == null`（首次启动）→ 用户配好音乐来源后触发首次扫描。
- 之后每次启动**不自动扫描**；`last_scan_at` 仅用于在「文件扫描 → 最近分析记录」展示「上次扫描：x 天前」并给出「重新扫描」入口。
- **禁止在启动时扫库**（I/O 重、目录大时可达分钟级，必然卡启动）。
- 若来源为空（`05 §1`：无权限 / 未指定来源）→ 不启动扫描，只显示引导。

## 4.2 权限检查顺序与引导

### 4.2.1 检查顺序与判断 API

```kotlin
// :app  com.aimusic.player.permission
class PermissionChecker @Inject constructor(
    @ApplicationContext private val context: Context
) {
    fun snapshot(hintAlreadyShown: Boolean): PermissionSnapshot {
        // ① 存储访问：优先判"所有文件访问"
        val storage = when {
            Build.VERSION.SDK_INT >= Build.VERSION_CODES.R ->
                if (Environment.isExternalStorageManager()) StorageAccessLevel.FULL
                else if (hasMediaRead()) StorageAccessLevel.MEDIA_LIBRARY_ONLY
                else StorageAccessLevel.NONE
            else -> // API 26–29：无 MANAGE_EXTERNAL_STORAGE，READ_EXTERNAL_STORAGE 视为完整读取
                if (hasMediaRead()) StorageAccessLevel.FULL else StorageAccessLevel.NONE
        }
        // ② 通知（仅 33+ 是运行时权限；<33 恒为已授予）
        val notif = Build.VERSION.SDK_INT < Build.VERSION_CODES.TIRAMISU ||
            ContextCompat.checkSelfPermission(context, Manifest.permission.POST_NOTIFICATIONS) ==
            PackageManager.PERMISSION_GRANTED

        return PermissionSnapshot(storage, notif, hintAlreadyShown)
    }

    private fun hasMediaRead(): Boolean {
        val perm = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU)
            Manifest.permission.READ_MEDIA_AUDIO            // 13+
        else
            Manifest.permission.READ_EXTERNAL_STORAGE       // <13（Manifest 里 maxSdkVersion=32）
        return ContextCompat.checkSelfPermission(context, perm) == PackageManager.PERMISSION_GRANTED
    }
}
```

**顺序结论**：先存储访问（`Environment.isExternalStorageManager()` → 回退 `ContextCompat.checkSelfPermission`），再通知权限。启动、回到前台、扫描前各检查一次（`onResume` 可刷新，因用户是去系统设置里授权的）。

### 4.2.2 引导方式

```kotlin
// :app  com.aimusic.player.permission
class PermissionLauncher(private val activity: ComponentActivity) {

    // "所有文件访问"：无运行时弹窗，只能跳系统设置页
    fun openAllFilesAccessSettings() {
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.R) {
            activity.startActivity(
                Intent(Settings.ACTION_MANAGE_ALL_FILES_ACCESS_PERMISSION)
                    .setData(Uri.fromParts("package", activity.packageName, null))
            )
        } else {
            // API 26–29：回退到应用详情页
            activity.startActivity(
                Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS)
                    .setData(Uri.fromParts("package", activity.packageName, null))
            )
        }
    }

    // 运行时权限：媒体读取 + 通知（13+ 才有意义）
    private val multiple = activity.registerForActivityResult(
        ActivityResultContracts.RequestMultiplePermissions()
    ) { /* 结果回灌 PermissionChecker.snapshot() */ }

    private val single = activity.registerForActivityResult(
        ActivityResultContracts.RequestPermission()
    ) { /* POST_NOTIFICATIONS 结果 */ }

    fun requestMediaAndNotifications() {
        val perms = buildList {
            add(if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU)
                Manifest.permission.READ_MEDIA_AUDIO
            else Manifest.permission.READ_EXTERNAL_STORAGE)
            if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU)
                add(Manifest.permission.POST_NOTIFICATIONS)
        }
        multiple.launch(perms.toTypedArray())
    }
}
```

- **首选**：`ACTION_MANAGE_ALL_FILES_ACCESS_PERMISSION`（"所有文件访问"），一次引导即拿到 `FULL`（`01 §5` 的锁定决策）。
- **降级**：用户不接受时，用 `ActivityResultContracts.RequestMultiplePermissions()` 申请 `READ_MEDIA_AUDIO`（+ 通知），拿到 `MEDIA_LIBRARY_ONLY`。
- 通知权限使用 `ActivityResultContracts.RequestPermission()`，在用户首次进入播放相关界面或首次准备播放时申请。

## 4.3 未授权时的降级

| 级别 | 扫描能力 | 物理删除 | 任意目录扫描 | 外部歌词目录 | 文案/入口 |
| --- | --- | --- | --- | --- | --- |
| `FULL` | 全部 | ✅ | ✅ | ✅ | — |
| `MEDIA_LIBRARY_ONLY` | **仅 MediaStore 媒体库**（`READ_MEDIA_AUDIO`） | ❌ 置灰 | ❌ 置灰 | ❌ 置灰 | 提示「仅扫描媒体库」+「去授权」入口 |
| `NONE` | ❌ | ❌ | ❌ | ❌ | 引导「去授权 / 选择来源」（`05 §1`、§7） |

- **降级在「选通道」这一步体现，不在 `StorageSource` 实现里**（Phase 3d 修正）：`02 §5.1` 的
  `listFiles` 只返回 `FileRef`，**带不出元数据**，所以「这次不该走 `MetadataReader`」必须有
  流水线之外的人知道。`ScanOrchestrator.scan()` 开头按 `accessLevel` 选一次通道：
  `FULL` → `FileStorageSource.listFiles` + `MmrMetadataReader`；`MEDIA_LIBRARY_ONLY` →
  `MediaStoreAudioSource.query()`（一次游标查询同时给出路径与元数据，省一次解码）。
  分支只有这一处，`04 §4.5` 的流水线本身不变。`canWrite()` 仍由存储实现返回 `false`，
  物理删除与任意目录遍历返回明确的权限失败。
- **置灰入口**：物理删除、任意目录来源选择在 UI 上置灰并给出「去授权」按钮（`05 §7`）；不静默失败。

### 4.3.1 拒绝后不反复弹窗

- DataStore 键 `permission_hint_shown`（`03 §6`）记录引导是否已展示。
- 规则：`permission_hint_shown == false` 时，进入前台才主动展示一次引导；置 `true` 后**不再主动弹窗**，仅在需要该权限的操作处给出「去授权」入口（`05 §7`：「拒绝后不再反复弹窗，保留入口可再触发」）。
- 用户从系统设置返回后 `PermissionSnapshot` 刷新；若已授权则清除 `permission_hint_shown`（下一次权限失效仍可再引导一次）。

## 4.4 WorkManager 设计

### 4.4.1 `ScanWorker`（唯一工作 + `ExistingWorkPolicy.REPLACE`）

```kotlin
// :app  com.aimusic.player.work
@HiltWorker
class ScanWorker @AssistedInject constructor(
    @Assisted appContext: Context,
    @Assisted params: WorkerParameters,
    private val scanOrchestrator: ScanOrchestrator,      // 04 定义，跨仓库编排
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result {
        val sources = inputData.getStringArray(WorkKeys.KEY_SOURCES)?.toList().orEmpty()
        if (sources.isEmpty()) return Result.failure()   // 无来源：不改库

        return when (val outcome = scanOrchestrator.scan(sources)) {   // 内部全局 Mutex（02 §7）
            is ScanOutcome.Completed ->
                Result.success(ScanSummary(outcome.new, outcome.skipped, outcome.cleaned).toWorkData())
            is ScanOutcome.PermissionDenied ->
                Result.failure(workDataOf("error_kind" to FailureKind.PERMISSION.name)) // 不 retry
            is ScanOutcome.IoError ->
                Result.retry()                            // 瞬时 IO → 交给 WorkManager 退避
        }
    }
}
```

**入队**：

```kotlin
fun enqueueScan(sources: List<String>) {
    val request = OneTimeWorkRequestBuilder<ScanWorker>()
        .setInputData(workDataOf(WorkKeys.KEY_SOURCES to sources.toTypedArray()))
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.SECONDS)
        .addTag(TAG_SCAN)
        .build()
    WorkManager.getInstance(context).enqueueUniqueWork(
        WorkNames.UNIQUE_SCAN,
        ExistingWorkPolicy.REPLACE,     // ← 决策点
        request
    )
}
```

**为什么是 `REPLACE`**：

- 扫描的语义是「按**当前**来源集合与磁盘现状做一次快照」；用户两次点「重新扫描」之间可能改了来源目录（`scan_source`）。`REPLACE` 会取消旧任务、以**最新输入**重启，保证结果与用户意图一致。
- `KEEP` 会把新请求静默丢弃——用户改了来源却看不到任何动静（体验差）；`APPEND` 会串行堆积多个过期扫描，且每个都按旧来源跑。
- `REPLACE` 与 `02 §7` 的「扫描全局单例 + `Mutex`」互相兜底：即使有并发入队，同一时刻也只有一个扫描真正写库。
- **取消是安全的**：扫描只在最终 `COMMITTING` 阶段做事务写（`02 §6.2`），中途取消不会产生半写状态；`DISCARDED` 不落库。

### 4.4.2 `AnalysisWorker`

```kotlin
// :app  com.aimusic.player.work
@HiltWorker
class AnalysisWorker @AssistedInject constructor(
    @Assisted appContext: Context,
    @Assisted params: WorkerParameters,
    private val analysisOrchestrator: AnalysisOrchestrator,   // 05 定义
) : CoroutineWorker(appContext, params) {

    override suspend fun getForegroundInfo(): ForegroundInfo? = null   // 分析不申请前台

    override suspend fun doWork(): Result {
        val runId = inputData.getLong(WorkKeys.KEY_RUN_ID, -1L)
        val fileIds = inputData.getLongArray(WorkKeys.KEY_FILE_IDS)?.toList()
        if (runId < 0) return Result.failure()

        var lastFailed = 0
        analysisOrchestrator.analyzePending(runId, fileIds).collect { p ->   // Flow<AnalysisProgress>
            lastFailed = p.failed
            setProgress(workDataOf(
                WorkKeys.KEY_DONE to p.done,
                WorkKeys.KEY_TOTAL to p.total,
                WorkKeys.KEY_FAILED to p.failed
            ))
        }
        // 单文件失败已在 Orchestrator 内落 FAILED（02 §6.1），批次整体成功返回，不 retry
        return Result.success(workDataOf(WorkKeys.KEY_FAILED to lastFailed))
    }
}
```

**入队与约束**：

```kotlin
fun enqueueAnalysis(runId: Long, fileIds: List<Long>? = null) {
    val request = OneTimeWorkRequestBuilder<AnalysisWorker>()
        .setInputData(workDataOf(
            WorkKeys.KEY_RUN_ID to runId,
            WorkKeys.KEY_FILE_IDS to (fileIds?.toLongArray())
        ))
        // 关键：不设置网络约束
        .setConstraints(Constraints.Builder().build())          // ≡ Constraints.NONE
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.SECONDS)
        .addTag(TAG_ANALYSIS)
        .build()
    WorkManager.getInstance(context).enqueueUniqueWork(
        if (fileIds == null) WorkNames.analysis(runId) else WorkNames.retry(runId),
        ExistingWorkPolicy.KEEP,        // 同一批次不重复入队
        request
    )
}
```

- **`CoroutineWorker` + `setProgress`**：进度写进 WorkData，`:feature:mine` 的「分析进度」页通过 `WorkManager.getWorkInfoByIdFlow` 订阅（替代自己造进度通道）。
- **不加网络约束（有意为之）**：BYOK 下网络不通是**用户应当知道的错误**——目标是把文件落到 `AnalysisStatus.FAILED`（`LlmFailureKind.NETWORK`）让用户在「最近分析记录」里看到并手动重试；若加 `NetworkType.CONNECTED` 约束，任务会在无网时被**无限期挂起**（既不落库、也不报错），用户只能看到「分析中」卡住。因此约束为空，把「失败」显式暴露。
- **`BackoffPolicy.EXPONENTIAL` 只用于整批重试**，不承载 429 退避（见下）。

### 4.4.3 429 退避 vs WorkManager 退避（避免双重退避）

| 维度 | 429 退避（限流） | WorkManager 退避 |
| --- | --- | --- |
| 发生层 | `RetryingLlmNormalizer` 装饰器（`:core:llm`，`02 §5.3`） | `Worker` 返回 `Result.retry()` 时 |
| 粒度 | **整批的一次 LLM 调用**（默认 20 个文件为一个请求） | **整批任务** |
| 策略 | 指数 1s → 2s → 4s … 上限 60s，重试上限 `llm_max_retries`（`01 §3.3`、`03 §6`） | `BackoffPolicy.EXPONENTIAL`，起始 30s |
| 触发条件 | 收到 429（`NormalizeOutcome.RateLimited`） | 批级瞬时故障：DB busy、JobScheduler 中断等 |
| 失败落盘 | 不计失败，状态保持 `ANALYZING`（`02 §6.1`） | 不涉及单文件状态 |

**关键约束：两者语义不得叠加。** `AnalysisWorker` 对 **429 / NETWORK / AUTH / SERVER / PARSE / INVALID_OUTPUT** 一律**不返回 `Result.retry()`**：

- 429 已由 `RetryingLlmNormalizer` 在**调用内部**退避完成（粒度 = 整批的一次调用），若 Worker 再对整批 `retry()` → 双重退避，语义冲突。
- 其他错误按 `02 §8`：落 `FAILED` + 用户手动重试（`02 §6.1` 只允许 `FAILED` 重试）。
- Worker 的 `Result.retry()` **仅**保留给「不涉及业务状态」的批级瞬时故障。

### 4.4.4 前台 vs 非前台任务划分

| 任务 | 载体 | 理由 |
| --- | --- | --- |
| 扫描 | **普通 `CoroutineWorker`**（不 `setForeground`） | 用户显式触发、可被系统调度；不需要常驻通知；`02 §7` 明确「长任务交给 WorkManager」 |
| 分析 | **普通 `CoroutineWorker`** | 同上；进度用 `setProgress`，`:feature:mine` 内查看 |
| 播放 | **前台 `Service`（`MediaSessionService`）** | 需持续音频输出、持有音频焦点、媒体会话、常驻通知（`需求 02 §8.4`） |

**不混用**：不让 Worker 承担播放（Worker 无常驻音频生命周期、无 `MediaSession`）；也不让前台 Service 承担扫描/分析（会长期占用前台通知位、拉高功耗）。

## 4.5 前台服务与通知

### 4.5.1 `MediaSessionService` 生命周期

```kotlin
// :core:playback  com.aimusic.player.playback
@AndroidEntryPoint
class MusicPlaybackService : MediaSessionService() {

    @Inject lateinit var queueEngine: QueueEngine

    private var mediaSession: MediaSession? = null

    override fun onCreate() {
        super.onCreate()
        // ① 通知渠道需在播放通知出现前创建（若 Application 未建，此处兜底）
        // ② ExoPlayer + QueueEngine 组装 MediaSession
        val player = ExoPlayer.Builder(this).build().apply { queueEngine.attach(this) }
        mediaSession = MediaSession.Builder(this, player)
            .setCallback(/* MediaSession.Callback：媒体按钮 / 蓝牙 / Android Auto */)
            .build()
    }

    override fun onGetSession(controllerInfo: MediaSession.ControllerInfo) = mediaSession

    override fun onTaskRemoved(rootIntent: Intent?) {
        val player = mediaSession?.player
        if (player == null || !player.playWhenReady || player.mediaItemCount == 0) {
            stopSelf()                     // 暂停/空队列：划掉任务即停，通知随之消失
        }
        // 正在播放：不停止，前台服务 + 通知继续（与需求 02 §8.4 一致）
        super.onTaskRemoved(rootIntent)
    }

    override fun onDestroy() {
        mediaSession?.run { player.release(); release() }
        mediaSession = null
        super.onDestroy()
    }
}
```

- 生命周期由 Media3 驱动：控制器（`:feature:player` 的 `MediaController`、系统媒体会话、蓝牙）连接后由 Media3 在**允许的时机**调用 `startForeground`；队列播放期间维持前台；播放停止 / 队列清空后由 Media3 `stopSelf`，通知移除。
- `MediaController` 由 `PlaybackModule` 以 `SessionToken` 绑定（见 §5.4）。

### 4.5.2 Android 13+ `POST_NOTIFICATIONS` 未授权

- 前台服务与播放**不受阻断**：服务仍可启动、音频继续；但**通知不会出现在通知抽屉**，用户改在系统的「正在运行的应用 / 前台服务任务管理器」中查看与停止。
- 锁屏 / 快速设置的媒体控件源自 `MediaSession`，部分设备即便没有通知权限仍可见（**以真机验证为准**，列入 §8）。
- 结论：通知权限作为**可选但推荐**项——不因其被拒而禁用播放；引导时说明「开启后可获得通知栏 / 锁屏控制」（`需求 02 §8.1`）。

### 4.5.3 Android 14 前台服务类型强校验

- 必须**同时**具备：Manifest 的 `android:foregroundServiceType="mediaPlayback"`（§3.1）+ `<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK" />`。
- 缺任一项，Android 14(API 34)+ 在 `startForeground()` 抛 `MissingForegroundServiceTypeException` / `SecurityException`；必须在发布前校验（§8 测试项）。
- `mediaPlayback` 类型的启动前置条件由 Media3 内部满足（存在有效 `MediaSession` 且正在播放）。

### 4.5.4 避免 `ForegroundServiceStartNotAllowedException`

- 目标：**只在用户交互后启动前台服务**。
- **做法**：
  1. 不在 `Application.onCreate`、`BroadcastReceiver`、Worker 中 `startForegroundService`。
  2. 播放起始必须源于**用户可见交互**（点击播放 / 播放全部 / 通知上的控制按钮 / 蓝牙媒体键）——此时 `:feature:player` 在前台，Media3 调 `startForeground` 属于允许场景。
  3. 冷启动恢复的曲目处于**暂停态**（§4.1.1），不触发前台服务；等用户点「播放」。
  4. 媒体按钮 / 蓝牙触发时，Android 对媒体播放有豁免，由 `MediaSessionService` 处理，我们不做额外的后台启动尝试。
- 反例（禁止）：在「扫描完成」通知里点击后直接后台起播放服务；在开机广播里恢复播放。

# 5. 状态与边界条件

## 5.1 权限状态边界

| 状态 | 触发 | 行为 |
| --- | --- | --- |
| `FULL` | `isExternalStorageManager() == true`（或 API<30 有 `READ_EXTERNAL_STORAGE`） | 全功能扫描、任意目录、物理删除、外部歌词目录 |
| `MEDIA_LIBRARY_ONLY` | 只有 `READ_MEDIA_AUDIO` | 仅扫 MediaStore；删除/任意目录/外部歌词置灰 + 「去授权」 |
| `NONE` | 无任何读取权限 | 引导「去授权 / 选择来源」，不启动扫描（`05 §1`、§7） |
| 用户从设置返回 | `onResume` 重查 | 刷新快照；已授权则清 `permission_hint_shown` |
| `permission_hint_shown == true` | 曾引导过 | 不再主动弹窗，仅操作点给入口（§4.3.1） |

## 5.2 任务入队边界

| 场景 | 处理 |
| --- | --- |
| 重复点「重新扫描」 | `REPLACE` 取消旧任务、以新来源重启（§4.4.1） |
| 扫描进行中再次触发 | 同上（`REPLACE` + `Mutex` 双保险），UI 显示「扫描进行中」 |
| 同一 `runId` 重复入队分析 | `KEEP`：保持已在跑的任务，不重复 |
| 重试失败项 | `WorkNames.retry(runId)` + `KEEP`，输入只带失败/未分析 `fileIds` |
| 无来源 | `ScanWorker` 直接 `Result.failure()`，不改库 |
| 任务被系统中断 | `Result.retry()` 走 `BackoffPolicy.EXPONENTIAL`；不涉及单文件状态 |

## 5.3 前台服务边界

| 场景 | 处理 |
| --- | --- |
| 播放中划掉任务卡 | `onTaskRemoved` 不停止，继续前台播放 |
| 暂停态划掉任务卡 | `stopSelf()`，通知消失 |
| Android 14 缺 FGS 类型声明 | `startForeground` 抛异常（§4.5.3）→ 发布前静态校验 |
| 后台尝试启动 FGS | 禁止（§4.5.4）；只在用户交互后 |
| 通知权限被拒 | 服务仍运行，通知抽屉无条目（§4.5.2） |

## 5.4 Hilt DI 模块划分

| `@Module` | 所在模块 | 提供 / 绑定 | 作用域 |
| --- | --- | --- | --- |
| `DispatcherModule` | `:core:common` | `@IoDispatcher` `@DefaultDispatcher` `@MainDispatcher` | `@Singleton`（Dispatcher 无状态，单例即可） |
| `StorageModule` | `:core:storage` | `@Binds StorageSource ← FileStorageSource`；`MetadataReader` 实现 | `@Singleton` |
| `DatabaseModule` | `:core:data` | `MusicDatabase`（Room）、13 个 DAO、`SettingsPreferences`（DataStore） | `@Singleton` |
| `RepositoryModule` | `:core:data` | `@Binds LibraryRepository / TagRepository / PlaybackRepository` 实现；`DeletionService`、`ScanOrchestrator`、`AnalysisOrchestrator` | `@Singleton` |
| `LlmModule` | `:core:llm` | `LlmNormalizer` 装配链：`CachingLlmNormalizer(RetryingLlmNormalizer(DirectProvider))`（缓存最外层，命中即零网络；与 `05 §4.2` 一致）；`OkHttpClient` / `Retrofit` | `@Singleton` |
| `PlaybackModule` | `:core:playback` | `@Binds PlaybackController` 实现；`SessionToken`（指向 `MusicPlaybackService`）与 `MediaController` 工厂 | `@Singleton` |
| （聚合） | `:app` | `AiMusicApp`、`HiltWorkerFactory` 注入、`MusicPlaybackService` 的 `@AndroidEntryPoint` | — |

**关键绑定说明**：

```kotlin
// :core:storage
@Module
@InstallIn(SingletonComponent::class)
abstract class StorageModule {
    /** 关键：业务只依赖 StorageSource 抽象；未来上架换 SAF 时，仅替换此绑定为 SafeStorageSource（01 §5 迁移路径） */
    @Binds @Singleton
    abstract fun bindStorageSource(impl: FileStorageSource): StorageSource
}
```

- **`StorageSource` 绑定 `FileStorageSource`** 是 `01 §5` 迁移路径的落点：换 SAF 时业务层零改动。
- **`@Singleton` 的适用范围**：无状态或需全局唯一的对象（DB、DataStore、Repository、Dispatcher、播放控制器、LLM 链）。**Worker 本身不加 `@Singleton`**（由 WorkManager 每次执行新建）；它对编排器的依赖通过 `@HiltWorker` + `HiltWorkerFactory` 注入。
- **`AnalysisOrchestrator` 不放进 `:core:llm`**：`02 §5.3` 明确 LLM 层不依赖 data，分类/标签清单由调用方传入；编排器位于能同时依赖 `:core:data` 与 `:core:llm` 的层（`05` 定稿的模块），本文只固定 Worker 对它的调用契约。

## 5.5 进程被杀与恢复

| 场景 | 系统侧行为 |
| --- | --- |
| 前台服务被系统回收（低内存） | 通知随服务消失；`PlaybackRepository` 已持久化的 `playback_state`（当前曲目 / 位置 / 会话最大进度）是唯一恢复来源；不单独结算会话（`需求 02 §6.4`、`02 §6.3`） |
| 用户划掉任务卡（`onTaskRemoved`） | 播放中 → 继续；暂停/空队列 → `stopSelf`（§4.5.1） |
| 冷启动恢复 | `restore()` 读 `playback_state`，恢复为暂停态（§4.1.1）；细节归 `07` |
| 恢复的当前文件已不存在 | `NOT_FOUND`（§6）；按 `00 §4.5`：回退次大文件，无文件则提示「保留并标记为不可用」 |
| 会话衔接 | 恢复后视为同一会话延续：`play_count` 不重复计，继续累计 `session_max_position_ms`（`02 §6.3`、不变量 I10） |

> 本文只固定**系统侧衔接点**（谁在何时读 `playback_state`、进程被杀后由谁恢复）；`playback_state` 的字段语义、写入时机、结算算法归 `07-播放器模块`。

# 6. 错误处理

沿用 `02 §8` 的 `AppError` / `FailureKind`。系统集成层产生的错误映射如下（**文案正文归 `11`，本文只给入口**）：

| 场景 | `FailureKind` | 自动恢复 | 用户可见动作 | 文案入口 |
| --- | --- | --- | --- | --- |
| 无「所有文件访问」，仅有媒体权限时点物理删除 / 任意目录 | `PERMISSION` | 否 | 「去授权」（跳 `ACTION_MANAGE_ALL_FILES_ACCESS_PERMISSION`） | §11 权限文案 |
| 无任何读取权限即触发扫描 | `PERMISSION` | 否 | 「去授权 / 选择来源」 | §11 权限文案 |
| 扫描时发现文件已从磁盘消失 | `NOT_FOUND` | 否 | 自动清理该 `music_file` 记录（`00 §4.5`，不打扰用户） | §11 文件失效文案 |
| 播放 / 恢复时文件不存在 | `NOT_FOUND` | 否 | 清理记录；回退次大文件；无文件则提示删除/保留 | §11 文件失效文案 |
| 通知权限被拒 | （非错误） | — | 不阻断播放；提示「开启后可获得通知控制」 | §11 权限文案 |
| Worker 遇到未知异常 | `UNKNOWN` | 否 | 记录日志，「重试」 | §11 兜底文案 |

- **权限类失败的统一入口**：`PermissionChecker.snapshot()` + DataStore `permission_hint_shown` → `:core:ui` 的空状态组件 → 文案取自 `11`。**模块内不硬编码文案**（`02 §8`）。

# 7. 性能与并发

| 关注点 | 约定 |
| --- | --- |
| 启动不阻塞主线程 | `Application.onCreate` 只做日志 + 通知渠道；DB / DataStore 惰性初始化；**不扫库**（`02 §7`） |
| 线程调度 | 所有 DB / 文件 IO 在 `Dispatchers.IO`（`DispatcherModule` 提供）；Room `suspend` 由 Room 自调度 |
| 扫描并发 | 全局单例 + `Mutex`（`02 §7`）；`REPLACE` 保证同一时刻仅一个扫描任务 |
| 分析并发 | 单 worker 串行调用 LLM（避免并发触发限流，`02 §7`）；进度用 Flow → `setProgress` |
| 退避不叠加 | 429 在 `RetryingLlmNormalizer` 内部退避；WorkManager 退避只用于批级重试（§4.4.3） |
| 通知开销 | 播放通知 `IMPORTANCE_LOW`，不打扰；分析通知可选，默认关闭 |
| 前台服务功耗 | 仅播放期间运行，播放停止即 `stopSelf`（§4.5.1），不长时间占用前台位 |
