# 1. 前置决策（已定）

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 平台 | 仅 Android，原生 Kotlin | 需求只要求安卓适配，跨端无收益 |
| LLM 接入 | **客户端直连 + 用户自填 Key（BYOK）** | 零服务端运维；Key 不落 APK，无被反编译提取的风险；隐私最好 |
| 服务端 | **V1 不建 server** | 本期 LLM 仅"文件名+元数据 → 归一化 + 标签"的单次结构化输出，无多轮 / 无工具调用 / 无多用户共享，server 无业务增量 |
| 分发 | 自用 + 分享给朋友（侧载） | 权限策略可放宽；上架合规暂不是约束 |

**未来需要 server 的触发条件**（满足其一再上，接口已预留）：
1. 不想让用户自填 Key；
2. 想不发版就调 prompt / 换模型；
3. 需要跨用户结果缓存（同曲归一化结果共享，省 token）；
4. 远期：联网搜索补全歌曲信息、向量检索 + 实体合并。

# 3. LLM 接入（BYOK 直连）

## 3.1 配置
- 设置页提供：**供应商 / Base URL / Model / API Key**（OpenAI 兼容优先，便于一次接入多家：DeepSeek、通义、智谱、Kimi、OpenAI、Gemini 兼容端点等）。
- **API Key 用 `EncryptedSharedPreferences`（Android Keystore）加密存储**，不落明文、不进日志。

## 3.2 接口抽象（关键）
定义 `LlmNormalizer` 接口与请求 / 响应契约，V1 实现 `DirectProvider`；未来网关只需新增 `GatewayProvider`，业务代码不动。

- 输入：文件名、内嵌元数据（标题 / 歌手 / 专辑 / 时长等）、**当前有效的分类与标签列表**（每请求动态拼装，非固定快照）。
- 输出：**结构化 JSON** —— 归一化标题、归一化歌手集合（全署名、分隔符统一、去重排序）、标签集合（仅新增，不动分类）。
- 结构化输出优先用 `response_format: json_schema`（不支持该能力的模型退化为提示词约束 + JSON 解析容错）。

## 3.3 调用策略（与需求文档一致）
- **触发**：扫描比对后用户点「分析并添加」才开始，逐文件调用。
- **429**：自动指数退避 1s → 2s → 4s … 上限 60s，可配重试次数。
- **其他错误**：不自动处理 → 标记「分析失败」→ 手动重试。
- **本地结果缓存**：key = hash(文件名 + 元数据)，命中则跳过调用；重扫 / 重试不重复消耗 token。
- 不可用歌曲不参与队列（与播放需求一致）。

# 4. 播放与系统行为

**用 Media3，不自己造轮子。** 需求中的后台播放、防系统回收、通知栏播放控制、锁屏原生媒体控制、音频焦点丢失、耳机拔出暂停，`MediaSessionService` 基本全部覆盖。

自研部分仅限业务逻辑：
- 三种播放模式（顺序 / 列表循环 / **随机 = 每次"下一首"即时重摇**）；
- 队列模型（允许重复、`下一首播放` 强制插入且 **LIFO**、不可用歌曲剔除）；
- 播放会话与统计（进度比例 85% / 15% 边界，持久化当前曲目与播放位置）。

**锁屏**：仅使用 Android 原生媒体控制，不做 QQ 音乐式自定义海报（已定）。

# 5. 文件存储与权限

**V1 方案：`MANAGE_EXTERNAL_STORAGE`（"所有文件访问"）+ 直接 `java.io.File` API。**

- 理由：自用 / 侧载分发，上架合规不是约束；而需求需要**任意目录扫描**、**读取同源 `.lrc` 与外部歌词目录**、**物理删除文件**——SAF 树权限在扫描速度与路径表达上都更别扭。
- 首次启动引导用户到系统设置授予"所有文件访问权限"（`ACTION_MANAGE_ALL_FILES_ACCESS_PERMISSION`），并给出未授权时的降级提示（见空状态文档）。

**迁移路径**：把文件访问封装为 `StorageSource` 抽象，未来若上架商店，替换为 **SAF 树（`ACTION_OPEN_DOCUMENT_TREE` + 持久权限）** 实现即可，业务层不受影响。

> 注：分区存储是系统级限制，与分发方式无关；侧载下 `MANAGE_EXTERNAL_STORAGE` 需用户手动开启，属可接受的一次性引导。

# 6. 数据存储设计

## 6.1 结论：DataStore 不够，必须上 SQLite（Room）

DataStore 是**键值 / 整块快照**存储：没有索引、没有查询、没有关联、没有事务。而本 App 的数据模型里恰好全是它做不了的事：

| 判断依据 | Room（SQLite） | DataStore |
| --- | --- | --- |
| 多对多 / 一对多关联（歌曲↔标签、歌曲↔文件） | JOIN + 外键 | 不支持，只能全量读进内存手动维护 |
| 列表排序 / 筛选（名称 / 最近播放 / 完播次数 / 按歌词） | `ORDER BY` / `WHERE` + 索引 | 全量加载 + 内存排序 |
| 级联删除（删实体连带标签关联、播放记录，磁盘文件保留） | `ON DELETE CASCADE` | 手写一致性，易漏 |
| 后台写入 + UI 读取并发 | 事务 / WAL | 单文件整体重写 |
| 数据量（百~千首歌 + 关联行） | 有索引无压力 | 每次读写全量序列化 |

## 6.2 分工

| 存储 | 放什么 |
| --- | --- |
| **Room（SQLite）** | 歌曲实体、音乐文件、标签、分类、实体-标签关联、歌词关联、播放队列、播放统计、分析记录、扫描来源 |
| **DataStore** | 全局设置：排序偏好、播放模式、上次扫描时间、LLM 供应商 / 模型 / BaseURL（Key 除外） |
| **EncryptedSharedPreferences** | LLM API Key（Keystore 加密） |

> 不要用裸 `SQLiteDatabase`，用 Room（官方、KSP、Flow 支持、类型安全、迁移工具）。纯 Android + Kotlin 的项目也没必要引入 SQLDelight。

## 6.3 表结构草案

```sql
song_entity(
  id, canonical_title, artists_key, display_artists,
  album, release_date, cover_ref,
  play_count, complete_count, skip_count, interrupt_count, last_played_at,
  playback_position_ms, playback_updated_at
)
music_file(
  id, entity_id → song_entity(id) ON DELETE CASCADE,
  path UNIQUE, size, format, duration_ms, is_representative,
  analysis_status, analysis_error, added_at
)
category(id, name, is_main)
tag(name PRIMARY KEY, category_id → category(id))              -- 标签名全局唯一
entity_tag(entity_id, tag_id, PRIMARY KEY(entity_id, tag_id))  -- 多对多
lyric(id, entity_id → song_entity ON DELETE CASCADE, path, source, match_kind)
queue_item(id, position, entity_id, is_forced)                 -- 有序、允许重复
analysis_run(id, started_at, finished_at, new_count, skipped_count, cleaned_count, failed_count)
scan_source(id, path, kind)                                    -- music | lyrics
```

要点：

- `artists_key` = 归一化后排序去重的歌手集合（**比较键**）；`display_artists` = 展示用全署名。
- 删除实体走 `ON DELETE CASCADE`；磁盘音频与 `.lrc` 不在库里，天然保留。
- `analysis_status`：未分析 / 分析中 / 已关联 / 失败。
- 搜索先用 `LIKE` 足够；数据量大再上 FTS4/5。
- 队列放 Room（有序且允许重复）；若嫌重，退化为 DataStore 里一个 JSON 快照也可接受，但一致性要自己保证。

# 7. 模块划分（建议）

```
:app                    # 入口、导航、主题

```

# 8. 关键风险与对策

| 风险 | 对策 |
| --- | --- |
| "所有文件访问"权限用户不授权 | 分级降级：仅 READ_MEDIA_AUDIO 时只扫媒体库，功能置灰并明确提示 |
| 大库扫描 / 元数据读取慢 | 后台 WorkManager + 分批；元数据解析并行；结果缓存 |
| LLM 结构化输出不稳定 | json_schema 优先；解析失败按"分析失败"处理，可重试 |
| 供应商差异（是否支持 json_schema / 多模态） | Provider 能力标记，按能力降级提示词方案 |
| 未来上架商店 | `StorageSource` 预留 SAF 实现 |
