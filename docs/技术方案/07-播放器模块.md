# 1. 模块职责与边界

## 1.1 做

- 封装 **AndroidX Media3**（`ExoPlayer` + `MediaSession` + `MediaSessionService`），承载前台服务与系统媒体控制。
- 维护**播放队列**（内存权威 + Room 镜像），实现点击播放 / 播放全部 / 添加到队列 / 下一首播放（强制插队）。
- 实现**四种 `PlayMode`** 的推进算法（顺序 / 列表循环 / 单曲循环 / 随机）。
- 实现**播放会话与统计**（`PlaySession` 的最大进度累计、85% / 15% 结算、被杀恢复不重复计）。
- 实现**播放状态持久化与恢复**（当前歌、位置、队列、模式、历史、会话最大进度）。
- 处理**音频焦点、耳机拔出、文件失效、后台播放、通知栏**。

## 1.2 不做

- 不扫描 / 不分析文件（属 `:core:storage` / `:core:llm`）。
- 不直接读写 Room 的其它表；**不是** `song_entity` / `music_file` 的写者。
- 不做歌词同步展示（属 `:feature:player` + 08 歌词模块），只把当前 `entityId` / 进度通过 `PlaybackUiState` 暴露。
- 不做自定义锁屏海报（**已定**：只用 Android 原生媒体控制，见需求 §8.6）。
- 不做均衡器 / 音效 / 变速（需求 §9 暂不包含）。

## 1.3 依赖

```
core:playback ─→ core:data（PlaybackRepository / LibraryRepository / 队列 DAO）
              ─→ core:common（Result / Dispatchers / Logger / 错误类型）
feature:*     ─→ core:playback（通过 PlaybackController + PlaybackUiState）
```

`core:playback` **不反向**依赖任何 `feature:*`。UI 文案不进入本模块（走 `11-错误处理与可观测性.md` 的映射）。

| 锁定决策（需求 02） | 本文落地章节 |
| --- | --- |
| 队列单元 = 歌曲实体，允许重复、不去重、不限长度 | §3.2、§4.2 |

| 随机 = 每次下一首即时重摇、不预生成乱序表、不做短期防重复；上一首按真实历史回退 | §4.4.4、§4.4.5 |
| 三种模式：顺序 / 列表循环 / 单曲循环（每完整一轮 = 一次会话） | §4.4、§4.6.4 |
| 会话 = 成为当前曲 → 切歌 / 自然结束 / 退出 / 进程被杀；被杀不单独结算，恢复算同一会话延续 | §4.6 |
| 占比 = 会话最大位置 / 代表文件时长，封顶 100%；≥85% 完整、≤15% 跳过、其余中断；`play_count` 仅会话开始 +1 | §4.6.3、§4.6.5 |
| 不可用歌曲不入队；播放中变不可用自动跳下一首 | §4.3.1、§4.7、§5.1 |
| 音频焦点：短暂丢失→暂停并自动恢复；永久丢失→暂停不自动恢复；不做 ducking；耳机拔出→自动暂停不自动恢复 | §4.8.2、§4.8.3 |
| 后台播放用前台服务 + 常驻通知；锁屏只用原生媒体控制 | §4.8.4、§4.8.5 |

> **说明（枚举口径）**：需求 `02` §4 锁定**三种播放模式**——**列表循环 / 单曲循环 / 随机**。`03-数据层设计.md` §2.3 的 `PlayMode` 已据此修正为 3 个值（`LIST_LOOP` / `SINGLE_LOOP` / `SHUFFLE`，默认 `LIST_LOOP`）。本文中"顺序推进（不环绕）"的算法描述仅作为实现参考，V1 **不**暴露为可选模式。

# 4. 核心流程

## 4.1 Media3 集成结构

### 4.1.1 `MediaSessionService` 子类（前台服务 + 通知 + 会话持有）

```kotlin
@AndroidEntryPoint
class PlaybackService : MediaSessionService() {

    @Inject lateinit var controller: PlaybackControllerImpl   // 单例，注入同一 ExoPlayer
    private var mediaSession: MediaSession? = null

    override fun onCreate() {
        super.onCreate()

        // ① 通知渠道 + 通知样式（Media3 自动生成常驻通知）
        val provider = DefaultMediaNotificationProvider.Builder(this)
            .setChannelId(CHANNEL_ID)
            .setChannelNameRes(R.string.playback_channel_name)
            .setNotificationId(NOTIFICATION_ID)
            .build()
            .apply { setSmallIcon(R.drawable.ic_notification) }
        setMediaNotificationProvider(provider)

        // ② ExoPlayer：音频属性 + 焦点由我们自管（见 4.8.2）
        val player = ExoPlayer.Builder(this)
            .setAudioAttributes(
                AudioAttributes.Builder()
                    .setUsage(C.USAGE_MEDIA)
                    .setContentType(C.AUDIO_CONTENT_TYPE_MUSIC)
                    .build(),
                /* handleAudioFocus = */ false          // 焦点自行处理，避免 Media3 默认 duck 行为
            )
            .setHandleAudioBecomingNoisy(false)          // 耳机拔出自行处理（见 4.8.3）
            .setWakeMode(C.WAKE_MODE_LOCAL)
            .build()

        controller.attach(player)

        // ③ MediaSession：与通知栏 / 锁屏 / 蓝牙共用同一会话
        mediaSession = MediaSession.Builder(this, player)
            .setSessionActivity(PendingIntent.getActivity(
                this, 0, Intent(this, MainActivity::class.java), PendingIntent.FLAG_IMMUTABLE))
            .setCallback(PlaybackSessionCallback(controller))   // 见 4.5.4 onPlaybackResumption
            .build()

        controller.onServiceReady(mediaSession)
    }

    override fun onGetSession(controllerInfo: MediaSession.ControllerInfo) = mediaSession

    // 用户划掉任务 = 「退出应用」→ 结算当前会话（进程被杀不会回调这里，故不结算，符合需求 §6.4）
    override fun onTaskRemoved(rootIntent: Intent?) {
        controller.settleOnExit()
        super.onTaskRemoved(rootIntent)
    }

    override fun onDestroy() {
        controller.detach()
        mediaSession?.run { player.release(); release() }
        mediaSession = null
        super.onDestroy()
    }
    companion object { const val CHANNEL_ID = "playback"; const val NOTIFICATION_ID = 1001 }
}
```

### 4.1.2 ExoPlayer 创建与复用

- **全进程唯一 `ExoPlayer` 实例**，由 `PlaybackService.onCreate` 创建、`onDestroy` 释放；`PlaybackControllerImpl` 通过 `attach(player)` 持有引用。**不**在 ViewModel / Activity 层另建 player。
- 播放列表用 `player.setMediaItems(items, startIndex, startPositionMs)` 一次性灌入，**队列与 `player.mediaItemCount` 保持同步**（队列是权威，player 只是渲染器）。
- **播放控制全部委托给 player**：`play/pause/seekTo/seekToNext/seekToPrevious`；切歌决策（下一首是谁）由 `QueueEngine` + `PlaybackModeResolver` 决定后再 `player.seekTo(index, pos)`，**不使用 `ExoPlayer` 自带的 repeat/shuffle 模式**（需求要求自研模式，见 `01` §4）。
- 进度监听：`player.addListener` 的 `onIsPlayingChanged` + 定时器（或 `player.currentPosition` 轮询，见 §4.5.2）。

### 4.1.3 `MediaSession` 配置

- `MediaSession.Builder(context, player)`，设置 `sessionActivity` 让点击通知进入播放页。
- 通知栏 / 锁屏 / 蓝牙指令（播放、暂停、上/下一首、进度拖动）**由 MediaSession 自动映射到 ExoPlayer 默认命令**（`COMMAND_SEEK_TO_NEXT` 等），**无需额外代码**（见 §4.8.5）。
- 需要拦截的只有「下一首 / 上一首」的**模式语义**：override `MediaSession.Callback.onPlayerCommandButton` 或使用自定义 `SessionCommand`，把系统 next/previous 转到 `PlaybackControllerImpl.skipToNext/skipToPrevious`（见 §4.4）。

## 4.2 `QueueEngine`：内存队列与 `queue_item` 表的同步

### 4.2.1 权威与写入节流（单写者）

- **内存列表是运行时权威**：播放顺序、下一首决策、LIFO 演算全部以内存 `items` 为准（毫秒级响应，不受 IO 阻塞）。
- **Room 是持久化镜像**：只在崩溃 / 被杀 / 冷启动时作为恢复来源。
- **单写者**：`queue_item` 与 `playback_state` **只由 `QueueEngine` 修改**（02 §7），其它模块只读。`PlaybackRepository.persist` 是数据层 API，但**唯一调用方是 `QueueEngine`**，因此单写者约束在逻辑层成立。
- **写入节流**：

| 触发 | 落库策略 |
| --- | --- |
| 队列结构变更（insert/append/remove/clear） | **去抖 300ms** 合并写（Trailing 一次） |
| 当前项指针变化（切歌） | **立即**写 `playback_state.current_queue_item_id`（与队列同事务） |
| 暂停 / seek 结束 / `onTaskRemoved`（退出）/ `onDestroy` | **立即** flush（含 `position_ms`、`session_max_position_ms`） |
| 播放中进度心跳 | 每 **15s** 兜底写一次（见 §4.5.2） |

理由：去抖避免拖动队列 / 快速连点 next 时高频写库；而「切歌 / 暂停 / 退出」是必须零丢失的关键点，同步落库。`session_max_position_ms` 单调递增，心跳丢失的中间值只会**低估少量占比**，对 85/15 分档影响可忽略。

### 4.2.2 队列写入算法（对应 `03` §4.6）

```kotlin
class QueueEngine(
    private val repo: PlaybackRepository,     // persist / restore
    private val queueDao: QueueDao,
    private val library: LibraryRepository,   // 可播性批量判定
    private val scope: CoroutineScope
) {
    private val mutex = Mutex()                       // 串行化所有队列变更
    private var items: MutableList<QueueItem> = mutableListOf()
    private var currentIndex: Int = -1                // 当前项在 items 中的指针
    private var flushJob: Job? = null

    // 追加末尾（需求 §3.4）
    suspend fun append(songId: Long) = mutex.withLock {
        if (!library.isPlayable(songId)) return@withLock   // I3：不可用不入队
        val pos = (items.maxOfOrNull { it.position } ?: -1) + 1
        items += QueueItem(id = 0, position = pos, entityId = songId, isForced = false)
        scheduleFlush()
    }

    // 下一首播放（需求 §3.5；LIFO）
    suspend fun insertNext(songId: Long) = mutex.withLock {
        if (!library.isPlayable(songId)) return@withLock   // I3
        val anchor = if (currentIndex >= 0) items[currentIndex].position else -1
        insertPosition(anchor + 1, songId, forced = true)
        scheduleFlush()
    }

    private fun insertPosition(pos: Int, songId: Long, forced: Boolean) {
        items.filter { it.position >= pos }.forEach { it.position += 1 }  // 尾段整体 +1 腾位
        items += QueueItem(id = 0, position = pos, entityId = songId, isForced = forced)
        items.sortBy { it.position }
        // 当前项指针不变（当前项 position < pos，未被移动）
    }

    fun current(): QueueItem? = items.getOrNull(currentIndex)
    fun peekNextForcedIndex(): Int? = items.indices
        .filter { it > currentIndex && items[it].isForced && isAvailable(items[it].entityId) }
        .minOrNull()                                  // 最小 position = 最后插入（LIFO 顶）
}
```

> **落库实现**：flush 在一个 `@Transaction` 中执行——新行 `@Insert`（Room 返回自增 id 并回填内存 `QueueItem.id`）、位置变化 `@Update`、删除项 `@Delete`；随后写 `playback_state`（含指向新的 `current_queue_item_id`）。队列长度在 V1 为百级，整体事务开销可忽略。**新增 DAO 方法**：`QueueDao.upsert(item)` / `updatePosition(id, position)`（03 §3.6 只定义了 `all/maxPosition/clear/remove`）。

### 4.2.3 `position` 整数间隔插入算法

- 用**密集整数**（0,1,2,…）表示顺序，**不用浮点 ε、不用大间隔**；每次「插入到某位置 p」= `p` 及其之后的所有项 `position += 1`，再在 `p` 落新项。插入后顺序始终为稠密整数（`0..n-1`）。
- 相对 `03` §4.6 的「`currentPosition + ε`」：用「整数 +1 腾位 + 尾段整体 +1」实现同一语义，避免浮点误差与精度耗尽。
- 复杂度 O(n) / 次插入；V1 队列为百级，无需稀疏间隔。若未来队列上千，可切换为**稀疏间隔（STEP=1024，取中点）**，对外语义不变（记入 §7 性能）。

### 4.2.4 LIFO 强制项的确切实现

**规则：`insertNext` 一律插到「当前项 position + 1」**。后插入者占据更靠前的位置，先前插入者被整体 +1 后移，因此**从当前项往后顺序播放即为 LIFO**。

**演算（需求 §3.5 示例：当前 A B C，先 D 后 E）**

| 步 | 操作 | `items`（position:entity） | current | 说明 |
| --- | --- | --- | --- | --- |
| 0 | 初始 | `0:A 1:B 2:C` | A | current index=0 |
| 1 | `insertNext(D)` | `0:A` · **`1:D`** · `2:B 3:C` | A | 锚点=A.pos+1=1，尾段 `≥1` 全部 +1 |
| 2 | `insertNext(E)` | `0:A` · **`1:E`** · `2:D 3:B 4:C` | A | 锚点仍=A.pos+1=1；D 被 +1 后移到 2 |
| 3 | `next()` | 播放 `1:E`，current=1 | E | 最小 index>0 的强制项 = E（LIFO 顶） |
| 4 | `next()` | 播放 `2:D`，current=2 | D | 剩下强制项 D |
| 5 | `next()` | 播放 `3:B` | B | 无强制项 → 进模式规则（此例顺序） |

**结果播放序：A E D B C** ✔（与需求 §3.5 完全一致）

- 允许**同一首插入多次**（不去重）：例如 `insertNext(D)` 两次 → `0:A 1:D 2:D 3:B 4:C`，连按两次 next 都听到 D。
- **随机模式下的强制插队**：见 §4.4.5，`next()` 第一步永远先消费强制项，再考虑随机（保证 I9）。

### 4.2.5 当前项指针维护

- 内存用 `currentIndex`（指向 `items`）；持久化为 `playback_state.current_queue_item_id`。
- 变更 `items` 时同步修正指针：
  - 在 current 之前插入/删除 → `currentIndex` 随之 `+1 / -1`（保当前项不变）；
  - 删除当前项 → 尽量落到**下一个可用项**（并触发会话结算 + 新会话开始，见 §4.6.2），无可用则 `currentIndex = -1`；
  - 播放推进（next/previous/自然结束）→ 重新定位 `currentIndex` 并立即 flush 指针。
- 实体被删除 → DB 级联清掉 `queue_item` 行、`playback_state.current_queue_item_id` 置 NULL（03 §4.4）；恢复时若指针为空 → 从队列第一个可用项开始或进入 idle。

## 4.3 各入口的队列构建

### 4.3.1 `playFromList(songs, startIndex)`（点击播放 / 播放全部；需求 §3.3）

语义：**用当前列表新建队列**（该列表全部歌曲按当前顺序），**从被点击曲目开始**；「播放全部」= `startIndex = 0`。**没有「清空队列只播一首」这种操作**（已废弃）。

```kotlin
suspend fun playFromList(entityIds: List<Long>, startIndex: Int) = mutex.withLock {
    // 1. I3 过滤：剔除不可用（无任何可用文件）
    val available = entityIds.filter { library.isPlayable(it) }
    if (available.isEmpty()) { emit(PlaybackEvent.NoPlayableInList); return@withLock }

    // 2. 「起点跳过不可用」：把原 startIndex 映射到过滤后的可用起点
    val original = entityIds.getOrNull(startIndex)
    val targetIndex = run {
        if (original != null && library.isPlayable(original))
            available.indexOfFirst { it == original }          // 起点本身可用 → 精确落位
        else {
            // 起点不可用（或越界）→ 向后找第一个可用；向后没有则向前找最后一个可用
            val anchor = entityIds.take(startIndex).count { library.isPlayable(it) } // 起点前的可用数
            when {
                anchor < available.size -> anchor                  // 起点之后还有可用 → 从下一个可用开始
                else -> available.lastIndex                        // 尾巴都是不可用 → 用最后一个可用
            }
        }
    }

    // 3. 重建内存队列（旧队列整体废弃；等价「新建队列」）
    items = available.mapIndexed { i, id -> QueueItem(0, i, id, isForced = false) }.toMutableList()
    currentIndex = targetIndex

    // 4. 落库（先清空旧队列，再写新队列，同事务）、重置队列相关 playback_state
    repo.replaceQueue(items, currentItemId = items[targetIndex].id)

    // 5. 灌入 player 并从起点开始
    loadIntoPlayer(startIndex = targetIndex, startPositionMs = 0)
    // 6. 会话：为起点曲 recordSessionStart；SHUFFLE 下起点曲先播、之后进入随机（§4.4.4）
    startSession(items[targetIndex].entityId)
}
```

- `startIndex` 语义：**在原始列表中**的点击下标；过滤后由上面的映射决定实际起点，**不因过滤而静默地从头播**。
- 全不可用：**不入队**（I3），发 `NoPlayableInList` 事件，UI 提示「无可用文件」。

### 4.3.2 `appendToQueue(songId)`（添加到队列；需求 §3.4）

- 保留当前播放状态；`position = maxPosition + 1`；`isForced = false`；允许重复。
- 不可用 → 忽略并提示（I3）。
- 若队列为空且**当前无播放**：可由产品决定是否顺手开始播放；默认**只入队不播放**（符合「追加末尾、不动播放状态」）。

### 4.3.3 `insertNext(songId)`（下一首播放；需求 §3.5）

- 见 §4.2.2 / §4.2.4：插到 `当前项 position + 1`，`isForced = true`，多次 LIFO。
- 允许同一首插入多次。
- 队列为空 / 无当前项：等价于 `appendToQueue`（落到队首作为待播）。
- **随机模式也必须真的插队**（I9）：见 §4.4.5，强制项优先于随机重摇。

### 4.3.4 `clearQueue()`

```kotlin
suspend fun clear() = mutex.withLock {
    settleCurrentIfAny()                 // 先结算（若在播）
    items.clear(); currentIndex = -1
    repo.clearQueueAndState()            // 删 queue_item 全部 + playback_state 复位（mode 保留）
    player.clearMediaItems(); player.pause()
}
```
- 只清队列与状态；**不清历史**（`play_history` 保留）；`mode` 保留。

### 4.3.5 `removeFromQueue(queueItemId)`

- 定位该项；修正当前指针（§4.2.5）。
- 若删的是**当前项** → 触发结算 + 交由 `next()` 选下一个可用项（或 idle）。
- 落库删除该行（`queueDao.remove`），去抖 flush。

## 4.4 三种播放模式的状态推进算法

推进决策集中在**无副作用的纯函数** `PlaybackModeResolver`，返回「下一个播放项」或 `Stop` / `Repeat`，由控制器落执行：

```kotlin
sealed interface NextDecision {
    data class PlayIndex(val index: Int, val reason: Reason) : NextDecision
    data object Stop : NextDecision
}
enum class Reason { FORCED, SEQUENTIAL, LOOP_WRAP, REPEAT, RANDOM, HISTORY_BACK }
```

### 4.4.0 统一前置规则（所有模式）

**`next()` 永远先消费「当前项之后的强制项」**，取其中 **position 最小者**（= 最后插入 = LIFO 顶）：

```kotlin
fun resolveNext(items, currentIndex, mode, isAvailable): NextDecision {
    // ① 强制项优先（LIFO；需求 §3.5 / §4.3，I9）
    val forcedIdx = items.indices
        .filter { it > currentIndex && items[it].isForced && isAvailable(items[it].entityId) }
        .minOrNull()
    if (forcedIdx != null) return PlayIndex(forcedIdx, Reason.FORCED)

    // ② 按模式推进（下列各分支）
    ...
}
```

### 4.4.1 `LIST_LOOP`（列表循环；需求 §4.1）

```kotlin
// 从当前项向后找第一个可用；找不到则从头环绕找（跳过当前项）
val after = (currentIndex + 1..items.lastIndex).firstOrNull { isAvailable(items[it].entityId) }
val wrap  = (0..currentIndex - 1).firstOrNull { isAvailable(items[it].entityId) }
return (after ?: wrap)?.let { PlayIndex(it, LOOP_WRAP) } ?: Stop
```
- `A → B → C → A → B → C`（需求 §4.1）。单元素队列 → 恒环绕同一首。

### 4.4.2 `SINGLE_LOOP`（单曲循环；需求 §4.2）

```kotlin
return PlayIndex(currentIndex, Reason.REPEAT)   // 恒重播当前项
```
- **自然结束触发本轮重播时** → 视为「一个完整会话结束」，先**结算该轮**（§4.6.4）再**重开新一轮会话**。
- 若存在强制项 → 被 §4.4.0 拦截，**先插队**（强制项优先于单曲循环）。

### 4.4.3 `SHUFFLE`（随机；需求 §4.3）—— 重点

**核心规则**

1. **强制项优先**：`next()` 先走 §4.4.0，把所有 `insertNext` 项按 LIFO 播完，**才**进入随机（需求 §4.3「优先播放插队/指定的歌曲，播完再进入随机」）。
2. **即时重摇**：进入随机后，**每次都重新抽样**，不预生成乱序表、不做「短期不重复」历史窗口（需求 §4.3）。
3. **不抽到不合适的项**：抽样池 = **队列中所有可用项**（`isAvailable` 过滤，I3），并**排除「当前项」**（当池非空时）——避免按「下一首」无任何反馈。这只排除「当前这一项」，**不涉及历史窗口**，与「不做短期防重复」不冲突。
4. **允许重复**：抽样可命中同一首歌在队列中的任意一份（队列允许重复）；跨「当前/上一首」的重复不设防。

```kotlin
// SHUFFLE 分支
val pool = items.indices.filter { it != currentIndex && isAvailable(items[it].entityId) }
if (pool.isNotEmpty()) {
    return PlayIndex(pool.random(), Reason.RANDOM)          // 即时重摇
}
// 池为空：仅剩当前项（且可用）
return if (isAvailable(items[currentIndex].entityId)) PlayIndex(currentIndex, Reason.REPEAT)
       else Stop
```

**`next()` 在随机下的完整判定顺序**

```
next():
  ① 有强制项（index>current 且 isForced 且可用）？ → 播它（LIFO 顶），current 前移，结束
  ② 否则抽池 = { 可用项 } \ { 当前项 }
        池非空 → pool.random() 落地播放
        池为空 → 若当前项仍可用 → 重播当前；否则 Stop
```

> 「点击歌曲新建队列」时被点击的**起点曲先播**（§4.3.1：它成为当前项），其播完后 `next()` 进入①② → 随机。这与需求 §4.3「优先播放指定的歌曲，播完再进入随机」一致。

### 4.4.4 `previous()`（上一首）—— 随机按真实历史回退

- **`LIST_LOOP`**：回到 `currentIndex - 1` 的可用项，在 0 处环绕到队尾可用项。
- **SINGLE_LOOP**：`seekTo(0)` 重播当前（不结算、不新会话，会话继续累计 max）。
- **SHUFFLE**：按**真实播放历史**回退（需求 §4.3）。实现：`QueueEngine` 维护**内存导航栈** `sessionHistory: MutableList<Long>`（有序 entityId，冷启动由 `play_history` 最近 N 条重建）与游标 `historyCursor`。

```kotlin
fun resolvePreviousShuffle(): Int? {
    while (historyCursor > 0) {
        historyCursor--
        val entityId = sessionHistory[historyCursor]
        val idx = items.indexOfFirst { it.entityId == entityId }   // 该歌可能已被删/不可用
        if (idx >= 0 && isAvailable(entityId)) return idx
    }
    return null   // 已到历史起点 → 保持当前 / seekTo(0)
}

// 「成为当前曲目」的回调（向前推进）：
fun onBecameCurrentForward(entityId: Long) {
    while (sessionHistory.size > historyCursor + 1) sessionHistory.removeLast()  // 截断重做分支
    sessionHistory += entityId
    historyCursor = sessionHistory.lastIndex
    // 最近播放：另写一条 play_history（展示用），见 §4.6.2
}
// 「上一首」回退：只移动游标，不回写历史（避免 A↔B 乒乓）
```

- 为什么用内存栈而非每次查库：`play_history` 是**追加日志**，直接查库做「上一条」会被「上一首产生的记录」污染成乒乓；内存栈 + 游标给出浏览器式回退，且**冷启动由 `play_history` 重建**，本质仍是「按真实播放历史回退」。
- `play_history`（DB）与 `sessionHistory`（内存）分工：前者供「最近播放」展示（术语 → `PlayHistoryDao.recentSongs`），后者供导航回退。

## 4.5 播放状态持久化与恢复

### 4.5.1 持久化字段与时机

| 字段 | 更新时机 | 频率 |
| --- | --- | --- |
| `current_queue_item_id` | 切歌 / 增删队列影响指针 | **立即**（关键点） |
| `mode` | `setMode` | 立即（低频） |
| `position_ms` | 暂停 / seek 结束 / 切歌前 / 退出 / 进程进入后台 + 心跳 | 事件驱动 + **15s** 心跳 |
| `session_max_position_ms` | 每 1s 进度回调在内存 `max()`；持久化同上 | 内存每秒、落库事件驱动 + 15s |
| `session_started_at` | 会话开始 / 结算清空 | 事件驱动 |

### 4.5.2 进度落库方案（不每秒写；给出理由）

**方案：内存按 1s 进度回调维护 `sessionMaxPositionMs`（零 IO），落库只在关键点 + 15s 心跳。**

```kotlin
// 每秒更新（纯内存）
player.addListener(object : Player.Listener {
    override fun onEvents(player: Player, events: Player.Events) { /* ... */ }
})
ticker(1s) {                       // 或 MediaSession VolumeProvider 之外的轻量轮询
    val pos = player.currentPosition
    session.maxPositionMs = maxOf(session.maxPositionMs, pos)   // 单调不减
    uiState.updatePosition(pos)
    if (now - lastHeartbeat >= 15_000) { repo.persist(progressPatch()); lastHeartbeat = now }
}
// 关键点立即写
fun onPause()      { repo.persist(progressPatch()) }
fun onSeekEnd()    { repo.persist(progressPatch()) }
fun beforeTrackChange() { repo.persist(progressPatch()) }   // 切歌前
```

**理由**

- **不每秒写**：Room + WAL 下每秒 1 次写虽可承受，但在「高频 seek + 大库」下会放大 IO 与 WAL 抖动，收益（最多少丢 1s 进度）极低。
- **15s 心跳**：把「进程被杀丢失量」控制在 ≤15s；而 `session_max_position_ms` **单调不减**，丢的是中间小值 → 只会**轻微低估**占比，对 85% / 15% 分档几乎无影响。
- **关键点同步写**：暂停 / seek / 切歌 / 退出必须零丢失（这些是用户可感知的状态点）。
- **结算不依赖心跳**：真实结算发生在明确事件（切歌 / 自然结束 / 退出），此时已同步写盘（§4.6）。

### 4.5.3 冷启动恢复流程

```
1. Service/App 启动 → PlaybackRepository.restore():
   - 读 playback_state（单行 id=0）+ queue_item（ORDER BY position）。
2. 内存重建 items；若空 → idle（currentIndex = -1）。
3. 定位当前项：currentQueueItemId 有效且可用 → 用它；
   指针为空 / 指向已删除项 / 不可用 → 选第一个可用项；全不可用 → idle。
4. 用 LibraryRepository 批量取每项的代表文件，MediaItemFactory 造 MediaItem 列表。
5. player.setMediaItems(items, startIndex = currentIndex, startPositionMs = position_ms)  — 灌入但不播放（§5.5：恢复但不自动播）。
6. 重建会话：sessionStartedAt = playback_state.session_started_at；session.maxPositionMs = session_max_position_ms；
   restoredFromKill = (sessionStartedAt != null)   // 见 §4.6.6，用于避免重复 +1。
7. 重建 SHUFFLE 导航栈：sessionHistory = play_history 最近 N 条（entityId，按 played_at 升序），cursor = lastIndex。
8. 不请求音频焦点（未播放）；注册 MediaSession。
```

### 4.5.4 系统触发的恢复入口（Media3）

- 实现 `MediaSession.Callback.onPlaybackResumption(...)`：系统在**进程被杀后**（例如用户从蓝牙/通知恢复）会调用它；返回「队列 + 当前项 + 位置 + 是否播」`ListenableFuture<MediaItemsWithStartPosition>`。
- 该回调内部即调用 §4.5.3 的恢复逻辑；该路径属用户主动恢复，恢复后可 `play()`（§5.5）。

## 4.6 会话统计的完整实现

### 4.6.1 调用点全景

| 事件 | `recordSessionStart` | `settleSession` |
| --- | --- | --- |
| `playFromList` 起点曲成为当前 | ✔ | — |
| `next()` / 自然结束 → 新曲成为当前 | ✔（新曲） | ✔（旧曲） |
| `previous()` → 回到历史曲 | ✔（新曲） | ✔（旧曲） |
| 强制项（`insertNext`）成为当前 | ✔ | ✔（旧曲） |
| `SINGLE_LOOP` 自然结束一轮 | ✔（同曲，新一轮） | ✔（本轮） |
| 暂停 / 拖动进度（seek） | ✘（同一会话延续） | ✘ |
| **进程被杀** | ✘ | ✘（**不单独结算**，需求 §6.4） |
| 退出应用（`onTaskRemoved`）/ service `onDestroy` | ✘ | ✔（结算一次） |
| 清空队列 / 删除当前项 | ✘ | ✔ |

```kotlin
class PlaybackSessionTracker(private val repo: PlaybackRepository) {
    fun recordSessionStart(entityId: Long) = repo.recordSessionStart(entityId)   // play_count+1 / last_played_at / play_history
    fun settleSession(entityId: Long, ratio: Float) = repo.settleSession(entityId, ratio)
}
```

### 4.6.2 会话开始：`recordSessionStart(songId)`

```kotlin
// PlaybackStateRepositoryImpl（唯一调用方：PlaybackSessionTracker）
override suspend fun recordSessionStart(songId: Long) = db.withTransaction {
    songDao.bumpPlayCount(songId, now)                 // I10：play_count 只在此 +1
    historyDao.addHistory(PlayHistoryEntity(...))       // 最近播放 / 随机上一首的依据
    historyDao.pruneHistory(keep = 500)                 // 02 §4：保留最近 N 条
    playbackStateDao.put(state.copy(sessionStartedAt = now, sessionMaxPositionMs = 0))
}
```

### 4.6.3 最大进度累计（含「seek 后退」的正确处理）

- **只取历史最大值**，`session.maxPositionMs = maxOf(session.maxPositionMs, player.currentPosition)`，**绝不因用户后退 seek 而减小**。
- **占比** = `min(1.0f, sessionMaxPositionMs / representativeDurationMs)`，封顶 100%。
- 分母 = **代表文件时长**（`music_file.is_representative = 1` 的 `duration_ms`；需求 00 §3）。若代表文件在会话中变更（文件失效回退），以**结算时**的代表文件时长为准。

### 4.6.4 `settleSession` 与单曲循环「每轮结算」

```kotlin
override suspend fun settleSession(songId: Long, ratio: Float) = db.withTransaction {
    val r = ratio.coerceIn(0f, 1f)
    songDao.bumpSessionResult(                     // 03 §3.1
        id = songId,
        c = if (r >= 0.85f) 1 else 0,              // ≥85% 完整
        s = if (r <= 0.15f) 1 else 0,              // ≤15% 跳过（含 ==0.15）
        i = if (r > 0.15f && r < 0.85f) 1 else 0   // 15%~85% 中断
    )
    playbackStateDao.put(state.copy(sessionStartedAt = null, sessionMaxPositionMs = 0))  // 清空会话
}
```

**单曲循环每轮**：`SINGLE_LOOP` 自然结束触发重播时，`PlaybackControllerImpl` 执行
`settleSession(旧曲, 本轮占比)` → `recordSessionStart(同曲)` → `player.seekTo(0); player.play()`。
因此**每一完整轮 = 一次会话 = 一次完整播放结算**（需求 §4.2、§6.2），且 `play_count` 每轮 +1。

**边界值**：`ratio == 0.85` → 完整；`ratio == 0.15` → 跳过；`0.15 < ratio < 0.85` → 中断。

### 4.6.5 结算写入的字段

`settleSession` 只改 `song_entity` 的 `complete_count` / `skip_count` / `interrupt_count`（`bumpSessionResult`），并把 `playback_state` 的会话字段清空。`play_count` / `last_played_at` 在**会话开始**时已写（§4.6.2）。

### 4.6.6 进程被杀后恢复「不重复计数」的实现细节

- **不结算**：进程被杀不会回调 `onTaskRemoved` / `onDestroy` → 天然不触发 `settleSession`（需求 §6.4）。
- **不重复 +1**：`play_count` 只在会话开始 +1。恢复时若 `playback_state.session_started_at != null` 且当前项与原会话同曲 → `restoredFromKill = true`，恢复逻辑**不调用 `recordSessionStart`**（I10）。
- **延续累计**：`session.maxPositionMs` 从 `session_max_position_ms` 接着累计（只取 max）；`sessionStartedAt` 不变。
- **直到真正切歌 / 退出**才结算一次，且用**整个（跨被杀）会话**的最大进度算占比。
- 判定「同曲」：比对 `current_queue_item_id` 的 `entity_id` 与最后一条 `play_history`/内存会话的 `entityId`；一致 → 延续，否则视为新会话（先结算旧、再开始新）。

## 4.7 文件失效处理（需求 05 §6；00 §1.3/§1.6）

**触发**：播放时 `ExoPlayer` 报 `PlaybackException.ERROR_CODE_IO_FILE_NOT_FOUND`（或代表文件 `StorageSource.exists == false`）→ 映射 `FailureKind.NOT_FOUND`（02 §8）。

```kotlin
fun onPlayerError(e: PlaybackException) {
    if (e.errorCode != PlaybackException.ERROR_CODE_IO_FILE_NOT_FOUND) { handleOther(e); return }
    val entityId = current().entityId
    val badFileId = representativeOf(entityId).id

    // ① 清理缺失记录（走数据层删除序列，同 03 §4.4「移除文件」）
    deletionService.unlinkFile(badFileId)          // 删 music_file 行；必要时重选代表文件

    val filesLeft = library.filesOf(entityId)
    when {
        // ② 实体仍有其它文件 → 自动用次大文件继续播放
        filesLeft.isNotEmpty() -> {
            val newRep = reelectRepresentative(entityId)     // 体积次大者
            rebuildMediaItem(entityId, newRep)               // 重建 MediaItem（新 uri）
            player.seekTo(currentIndex, session.positionMs.coerceAtMost(newRep.durationMs ?: 0))
            emit(PlaybackEvent.FileMissingFallback(entityId)) // UI：「文件不存在或已被移动」，已自动续播
        }
        // ③ 实体再无文件 → 变不可用；提示删除或保留
        else -> {
            emit(PlaybackEvent.SongBecameUnavailable(entityId))  // UI 弹「该歌曲已无可用文件，是否删除？」（删除 / 保留并标记不可用）
            // ④ 当前曲自动跳下一首（不阻塞）
            skipToNextInternal(skipUnavailable = true)
        }
    }
}
```

规则：

- **不可用歌曲不得入队**（I3）：在队列构建 / 追加 / 插队时过滤（§4.3）；**运行中变不可用**的项在 `next()` 抽样 / 步进时用 `isAvailable` 跳过（§4.4）。
- 「保留并标记不可用」→ 实体 `music_file` 数为 0，`isPlayable = false`（派生，不落库，03 §5.3）；列表置灰（05 §3）。
- 「删除」→ 走 `DeletionService.deleteSong(entityId)`（级联清关联，不碰磁盘，I8）。
- 某队列项文件失效但**非当前项** → 不立即处理，等播放到它时按同流程处理。

### 4.8.2 音频焦点（短暂→暂停并自动恢复；永久→暂停不自动恢复；不做 ducking）

```kotlin
class AudioFocusController(
    private val am: AudioManager,
    private val onFocusGain: () -> Unit,
    private val onFocusLoss: (permanent: Boolean) -> Unit
) {
    private var resumeOnGain = false

    private val listener = AudioManager.OnAudioFocusChangeListener { change ->
        when (change) {
            AudioManager.AUDIOFOCUS_GAIN -> {                    // 短暂丢失后恢复
                if (resumeOnGain) onFocusGain()                  // 自动继续
                resumeOnGain = false
            }
            AudioManager.AUDIOFOCUS_LOSS_TRANSIENT -> {          // 来电 / 短暂提示音
                resumeOnGain = true; onFocusLoss(permanent = false)  // 暂停，记下需恢复
            }
            AudioManager.AUDIOFOCUS_LOSS -> {                    // 其它播放器开始
                resumeOnGain = false; onFocusLoss(permanent = true)  // 暂停，不自动恢复
            }
        }
    }

    private val request: AudioFocusRequest =
        AudioFocusRequest.Builder(AudioManager.AUDIOFOCUS_GAIN)
            .setAudioAttributes(audioAttributes)             // USAGE_MEDIA / CONTENT_TYPE_MUSIC
            .setAcceptsDelayedFocusGain(false)
            .setWillPauseWhenDucked(true)                    // ★ 关键：不 ducking，等价于瞬时丢失→暂停
            .setOnAudioFocusChangeListener(listener, Handler(Looper.getMainLooper()))
            .build()

    fun request(): Boolean = am.requestAudioFocus(request) == AudioManager.AUDIOFOCUS_REQUEST_GRANTED
    fun abandon() = am.abandonAudioFocusRequest(request)
}
```

- `setWillPauseWhenDucked(true)`：使 `AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK` **不会**下发，统一按瞬时丢失处理 → **不做「压低音量继续」**（需求 §8.2）。
- 只在**打算开始播放**时 `request()`；被拒（`AUDIOFOCUS_REQUEST_FAILED`）→ 保持暂停并提示。
- `resumeOnGain` 标志区分「短暂 → 恢复」与「永久 → 不恢复」。

### 4.8.3 耳机拔出：`ACTION_AUDIO_BECOMING_NOISY`

```kotlin
class BecomingNoisyReceiver(private val onNoisy: () -> Unit) : BroadcastReceiver() {
    override fun onReceive(c: Context, i: Intent) {
        if (i.action == AudioManager.ACTION_AUDIO_BECOMING_NOISY) onNoisy()   // 自动暂停，不自动恢复
    }
}
// Service.onCreate: registerReceiver(receiver, IntentFilter(ACTION_AUDIO_BECOMING_NOISY))
// onNoisy 回调：player.pause(); focus.resumeOnGain = false; persist(progress)
```
- **不自动恢复**（需求 §8.3）。为防止与 ExoPlayer 内建行为重复，`ExoPlayer` 侧 `setHandleAudioBecomingNoisy(false)`。

### 4.8.4 前台服务与常驻通知

- `MediaSessionService` 在播放开始时**自动 `startForeground`**，并托管 **Android 14 强制的前台服务类型 `mediaPlayback`**（`foregroundServiceType="mediaPlayback"` + `FOREGROUND_SERVICE_MEDIA_PLAYBACK` 权限）。
- 通知由 `DefaultMediaNotificationProvider` **自动生成**：标题=歌名、副标题=歌手、动作=播放/暂停/上一首/下一首、封面=`MediaMetadata.artworkUri`，状态与 player **实时同步**（需求 §8.5）。
- `POST_NOTIFICATIONS`（13+）在首次进入相关流程时引导授权；未授权时前台服务仍可运行，但通知不可见（系统限制，UI 提示）。

### 4.8.5 蓝牙 / 锁屏控制

- **无需额外代码**：`MediaSession` + 由它派生的 `MediaButtonReceiver` / MediaBrowser 会话，自动响应锁屏媒体控件、蓝牙 AVRCP（播放 / 暂停 / 上/下一首 / 拖动进度）。
- 唯一自研点：把系统「下一首 / 上一首」命令**路由到本模块的模式语义**（`skipToNext/skipToPrevious`），通过 `MediaSession.Callback` / 自定义 `SessionCommand` 完成。锁屏**只用系统原生控制**，不做自定义海报（需求 §8.6）。

# 5. 状态与边界条件

## 5.1 空状态 / 异常分支

| 场景 | 行为 | 事件 / UI |
| --- | --- | --- |
| 列表全不可用，`playFromList` | **不入队**，保持原状态 | `NoPlayableInList` → 「无可用文件」 |
| `appendToQueue` / `insertNext` 目标不可用 | 忽略 | 提示「无可用文件」（05 §3） |
| 队列只有 1 个可用项 + `SHUFFLE` | 池为空 → 重播当前项 | — |
| 单曲循环 + 队列为空 | 无当前项 → idle，不播 | `isEmpty` |
| 单曲循环 + 队列有 1 首 | 恒重播该首，每轮结算 | — |
| 运行中当前项文件缺失 | §4.7 回退 / 提示 / 跳下一首 | `FileMissingFallback` / `SongBecameUnavailable` |
| 当前项被删除（实体级联） | 指针置 NULL → 落到下一个可用项或 idle | — |
| 恢复时指针悬空 | 从第一个可用项开始，或 idle | — |

## 5.2 队列耗尽 / 循环终点的差异

| 模式 | 到达末尾 | 到达开头 previous |
| --- | --- | --- |
| `LIST_LOOP` | 环绕到首个可用 | 环绕到末尾可用 |
| `SINGLE_LOOP` | 重播（不移动） | `seekTo(0)` |
| `SHUFFLE` | 重摇（无「末尾」概念） | 历史回退 |

## 5.3 时长未知（`duration_ms` 为 null）时的占比计算

- 分母优先级：**① 播放时 `player.duration`**（ExoPlayer 多数格式能在解码头后给出）→ **② 代表文件 `music_file.duration_ms`** → **③ 都未知**。
- 都未知时的兜底：
  - **自然播放结束**（`Player.STATE_ENDED`）→ 视为**完整播放**（能自然到头即 100%）。
  - **用户中途切歌 / 退出**（非自然结束）→ 归类**播放中断**（既非完整也非跳过，无法证明其占比）。
- `PlaybackUiState.durationMs = null` 时，进度条展示为不确定态（UI 处理，本模块只如实透出 null）。

## 5.4 会话与统计边界

| 边界 | 结论 |
| --- | --- |
| `ratio == 0.85` | 完整（`≥85%`） |
| `ratio == 0.15` | 跳过（`≤15%`） |
| `0.15 < ratio < 0.85` | 中断 |
| 会话内 seek 后退 | `sessionMax` 不回退（取历史最大值） |
| 暂停 / seek | 不结算、不新会话 |
| 进程被杀 | 不结算、不重复 +1，恢复沿用同一会话（§4.6.6） |
| 退出应用（`onTaskRemoved`） | 结算一次 |
| `playFromList` 起点曲 | 会话开始 +1（`playFromList` 也算「成为当前曲」） |

## 5.5 冷启动恢复策略（已定）

**结论：恢复但不自动播。**

`restore()` 恢复队列 + 当前项 + `position_ms`；UI 显示「继续播放 03:21」，**播放条为暂停态**，用户点击才出声。

理由：不突然出声、不抢其它应用的音频焦点、不触发 Android 12+「后台启动前台服务」限制，符合「打开 App ≠ 想听歌」的预期。需求 `02` §5.2 示例里的「继续播放 03:21」指**播放位置被恢复**，不代表自动出声。

**例外**：系统侧 `MediaSession.Callback.onPlaybackResumption(...)`（用户从蓝牙 / 通知栏显式发起恢复）属**用户主动意图**，该路径恢复后可 `play()`。

**Q2（已定）**：按需求 `02` §4 锁定为**三种**模式——`PlayMode = { LIST_LOOP, SINGLE_LOOP, SHUFFLE }`，不提供第 4 个"顺序播放"模式。

# 6. 错误处理（映射 `02` §8 的 `FailureKind`）

| 场景 | `FailureKind` | 自动恢复 | 动作 | UI 文案（由 11 维护） |
| --- | --- | --- | --- | --- |
| 播放中文件不存在 | `NOT_FOUND` | 是（回退次大文件自动续播） | 清理记录 + 回退 / 提示 | 「文件不存在或已被移动」 |
| 实体再无文件 | `NOT_FOUND` | 否 | 提示删除 / 保留不可用；跳下一首 | 「该歌曲已无可用文件，是否删除？」 |
| 解码失败 / 格式不支持 | `PARSE`（本次运行内标记不可播） | 否 | 跳过该曲、**不删文件**（避免误删） | 「无法播放该文件」 |
| 音频焦点被拒 / 丢失 | —（非 `FailureKind`） | 短暂时是 | 暂停 / 自动恢复见 §4.8.2 | — |
| 播放服务异常终止 | `UNKNOWN` / `IO` | 否 | 记日志，恢复为暂停态 | 通用错误提示 |

- 原则（02 §8）：**错误类型 → 用户语言**统一在 `11` 维护，**模块内不硬编码文案**；`NOT_FOUND` 的**自动恢复**（回退代表文件）是本模块特有，需在 `11` 中登记。
- 遥测 / 日志：`PlaybackError` 事件与 `FailureKind` 一并上报 `core:common.Logger`（不落敏感信息）。

# 7. 性能与并发

| 方面 | 约定 |
| --- | --- |
| 线程 | 所有队列变更经 `QueueEngine` 的 `Mutex` 串行；DB / 文件 IO 在 `Dispatchers.IO`（02 §7） |
| 单写者 | `queue_item` / `playback_state` **只由 `QueueEngine`** 写（02 §7）；`play_history` 由 `PlaybackRepository` 在会话开始时写 |
| 队列落库 | 结构变化**去抖 300ms** 合并；切歌 / 暂停 / 退出 / seek **立即** flush（§4.2.1） |
| 进度落库 | 内存每秒 `max()`；落库**事件驱动 + 15s 心跳**，不做每秒写（§4.5.2） |
| 插入复杂度 | `insertNext` 尾段整移 O(n)；V1 队列百级可忽略；上千级可切稀疏间隔（STEP=1024 取中点），语义不变 |
| 队列重建 | 冷启动一次 `ORDER BY position` 读 + 批量取代表文件；`setMediaItems` 一次灌入 |
| UI 状态 | `PlaybackUiState` 用 `StateFlow`，`stateIn(scope, WhileSubscribed(5s), initial)`（02 §7）；进度高频字段用独立 `Flow` 合并，避免整份 UI state 每 1s 重发 |
| 一次性事件 | `Channel<PlaybackEvent>(BUFFERED).receiveAsFlow()`，**禁止** `StateFlow`（02 §7） |
